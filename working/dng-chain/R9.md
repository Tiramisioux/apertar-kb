# R9 — what each stack asks libcamera for, and the PiSP back-end serial cycle that limits 4K 50 fps SDR and 4K 30 fps Clear HDR

Reader: R9 (research worker), 2026-11-01. Read-only. Trees and commits:
Apertar-Core `92d0970` (drop-frames), apertar-ui `e061be8`, cinemate `4990afc`, cinepi-raw `63a08d5`, cinemate-handbook `c99ff77`,
apertar-kb `1899e8d`, upstream raspberrypi/libcamera `c682979` (2026-10-09, shallow clone made for this report; the Apertar fork
`6b0b49f` and cinemate's fork `bfe0b76` are not available here, so fork-specific lines are quoted from the kb's earlier reads).
Labels: **confirmed** = read in source / measured in a log; **probable** = inferred, reason given; **unconfirmed** = needs the Pi.
Observations (§1-§7) are separate from conclusions (§8-§10).

## 0. Short answer

1. **Both stacks ask libcamera for the same two streams**: one YUV420 `VideoRecording` stream of 1280x720 (Rec709) that feeds every
   preview, plus one `Raw` stream at the sensor mode size. cinepi-raw aliases its "lores" to stream 0 when a raw stream exists
   (`cinepi-raw/core/rpicam_app.cpp:614-622,660-675@63a08d5`); Apertar hard-codes `{VideoRecording, Raw}` with a 1280x720 preview
   (`Apertar-Core/src/camera/CameraController.cpp:7901-7906,7945-7956,1241-1242@92d0970`). **Confirmed.** No stack configures a
   full-resolution main stream; no stack omits the ISP output.
2. **The raw format differs, and libcamera's PiSP rule decides it.** Apertar requests `SRGGB12_CSI2P` for 12-bit
   (`CameraController.cpp:2466-2479`); the PiSP handler turns a CSI2-packed request into **PISP_COMP1** (1 B/px, 8.3 MB per 4K frame)
   (`raspberrypi/libcamera src/libcamera/pipeline/rpi/pisp/pisp.cpp:1212-1221@c682979`, **confirmed upstream, probable for the Apertar
   fork**; Core's own COMP1 decode path confirms it runs that way: `src/cdng/CdngEncoder.cpp:836-845,929-943`). cinemate launches
   `--mode W:H:12:U` (`resources/sensors.json` imx585 `"packing": "U"`), which cinepi-raw maps to `SBGGR12` unpacked
   (`rpicam_app.cpp:109-137`) and the same rule turns into a **16-bit unpacked container** (2 B/px, 16.6 MB per 4K frame). **Confirmed**
   (code; the handbook says the same: `architecture/cinepi-raw.md:62-72@c99ff77`). So in 4K SDR cinemate moves twice Apertar's bytes on the
   CFE write and the encoder read, while Apertar's back end reads a compressed frame.
3. **The one difference that cuts the back-end serial cycle is the tuning file.** cinemate's installer overwrites libcamera's `imx585.json`
   with `resources/tuning_files/imx585.json`: **five algorithms** (`rpi.black_level, rpi.awb, rpi.agc, rpi.ccm, rpi.contrast`), **no
   `rpi.denoise`, so no TDN, SDN or CDN**, and no `rpi.dpc/geq/alsc/sharpen/cac/hdr` (`cinemate/cinemate-install.sh:1551-1585@4990afc`,
   `cinemate/src/module/tuning_files.py:96-118`, `cinepi_multi.py:388-450,634-635`, the file itself, 135 lines). **Confirmed** in the
   installer and launcher; **probable** on the operator's camera (the handbook reports a ~1008-line uncommitted `imx585.json` change in
   `/home/pi/libcamera`, which is what the overwrite looks like: `cinemate-handbook/open-threads.md:358-375@c99ff77`). libcamera enables TDN
   iff the tuning's `rpi.denoise` has a `tdn` key (`src/ipa/rpi/controller/rpi/denoise.cpp:55@c682979`); the `NoiseReductionMode` control only
   distinguishes Off from everything else (`src/ipa/rpi/pisp/pisp.cpp:567-570@c682979`), so cinepi-raw's `cdn_fast` default changes nothing.
   Apertar never sets `NoiseReductionMode` (grep) and loads `/home/pi/Tuning-Files/defaults-pisp/imx585.json` (`_clearHDR.json` in Clear
   HDR); whether that file has `tdn` is **unconfirmed** (the file is not in any repo here; the kb's "probable on" rests on files that cinemate's
   installer replaces).
4. **Back-end bytes per frame (q1 method).** 4K SDR 12-bit, 3840x2160: Apertar (COMP1 CFE, TDN on) **29.0 MB**, TDN off **10.6 MB**;
   cinemate (16-bit container, no TDN) **19.8 MB** (with TDN it would be 56.5 MB). Clear HDR 16-bit 3840x2200 (both unpacked): TDN on **57.6 MB**,
   off **20.0 MB**. Budgets: 20.0 ms at 50 fps, 16.67 at 60, 33.33 at 30, 40.0 at 25. **Probable** (arithmetic on confirmed formats; the only
   measured back-end figure is 13.4 ms idle / 34.6 ms recording for the 57.6 MB case, `apertar-kb/lessons/hardware-log.md:190`).
5. **The T34 M3 loss (2616-2632 of ~2974-2987 at 50 fps, steady single-frame gaps of 40 ms, unchanged with 8 raw buffers) is the signature
   of a serial cycle of ≈ 22.7 ms against a 20 ms budget** (1000/44.1 fps; one frame lost every 20/(22.7-20) ≈ 7.4 frames = 5.9/s, which is
   what was counted: 355-358 in ~60 s). **Probable.** Not the link, not the RP1 cap, not the sensor (§6): the probe lists 3840x2160 at
   60 fps and the pre-roll delivered 60.0 fps from sensor timestamps (`hardware-log.md:830,842-853`).
6. **Verdict:** cinemate's configuration would make 4K 50 fps SDR *more* achievable than Apertar's only through the TDN-less tuning (back end
   19.8 vs 29.0 MB per frame, and no TDN read-modify-write inside the serial stage); its raw path is otherwise heavier (16.6 vs 8.3 MB on the CFE,
   a 16→12 pack pass on the encoder). **No counted 4K 50 or 60 fps SDR take exists in cinemate's docs, changelog or handbook** (grep, §7); its
   4K 12-bit "Max FPS" 43.98 / 67.13 are `--list-cameras` ceilings at a 1039.5 MHz link (`cinemate/docs/sensors.md:32-42`), and the 50/60 fps
   per link frequency in `sensors.json` are copied from the driver README and marked "advisory until measured on this stack". The operator's
   belief is unsupported by any record; the mechanism that could make it true on cinemate (no TDN) is the same change Apertar can make with a
   tuning copy and no build.

## 4. The libcamera rules that decide the back-end cycle (upstream `c682979`; fork lines from the kb)

- Raw packing: `if (bayer.packing == CSI2 || bayer.bitDepth != 16) { packing = CSI2 ? PISP1 : None; bitDepth = 16; }`
  (`src/libcamera/pipeline/rpi/pisp/pisp.cpp:1212-1221`). For 14/16-bit sensors compression is then disabled (`:1229-1239`). **Confirmed upstream.**
- CFE format = the raw stream's format when a raw stream exists (`:1461-1465`); **BE input, TDN in/out and stitch in/out are set to that same
  format** (`:1493-1498`). So TDN is compressed when the raw is COMP1 and 16-bit unpacked when the raw is 16-bit (fork: `pisp.cpp:1901-1905,
  2566-2602@6b0b49f`, kb q1 rows 7, 43). **Confirmed.**
- 16-bit sensor → `Needs16bitEndianSwap` (`:1468-1476`). **Confirmed.**
- TDN on iff `"tdn"` is present under `rpi.denoise` (`denoise.cpp:55`); `NoiseReductionMode` Off disables SDN/TDN/CDN, every other value is
  `ColourHighQuality` (`ipa/rpi/pisp/pisp.cpp:567-570`; `denoise.cpp:136-137,188-191`). The IPA sets `TDN + TDN_OUTPUT (+ TDN_INPUT)` bits
  from `tdn.status` (`ipa pisp.cpp:426-428,773-803`). **Confirmed.**
- One frame in flight: `tryRunPipeline` gate on `Idle`; the raw buffer returns on BE input dequeue; `requestCompleted` runs inside the cycle
  (kb `q2-pipelining.md` §1, `pisp.cpp:3112-3117,2272-2284@6b0b49f`, `pipeline_base.cpp:1525-1542`). **Confirmed by the kb's reads.**
- Measured stages (Clear HDR 16-bit 30 fps, before L1): BE start→done 13.4 ms idle, 34.6 ms recording (thread-seen upper bound); cycle 36.2 ms
  (`apertar-kb/lessons/hardware-log.md:185-192`); L1 cycle 34.7-36.2 ms, L2 35.5-38.0 ms (`:210,:225`; `research-30fps-answer.md` §1). **Confirmed in the log.**

## 6. Sensor and link side of 4K 50 fps SDR (addendum)

Facts (confirmed in the kb / handbook / cinemate files; driver lines are the kb's):

- Apertar rig: `dtoverlay=imx585,cam0,link-frequency=891000000` (1782 Mbps/lane, 4 lanes) + `rp1-clk-333mhz`
  (`apertar-kb/architecture/drivers.md:114`; `working/clearhdr-design.md:120`). cinemate's colour rig (the operator's `cinepi`): the same
  891 MHz + `dtoverlay=rp1-overclock` (`cinemate-handbook/lessons/hardware-log.md:1104-1111@c99ff77`). cinemate's shipped default is
  720 MHz / 1440 Mbps with the overclock overlay commented out (`cinemate/docs/sensors.md:84-99`, `docs/config-txt.md:23,127-130`,
  `resources/sensors.json` imx585 `link_frequency.default_hz 720000000`); the dev-rig recommendation was "1440 Mbps / stock clock"
  (`hardware-log.md:985`). So **no link or RP1 difference between the two stacks on the operator's rigs**; cinemate's defaults are slower.
- D-PHY clamp (handbook 2026-08-27, `hardware-log.md:743-749,761-775`): `rp1_cfe/dphy.c` logs `DPHY: Datarate %u Mbps out of range` for
  mbps > 1500 but **does not return**; the hsfreqrange lookup loop runs to `ARRAY_SIZE(table)-1` and falls through to the last bucket
  `{1500, 0b111100}`, so **1782 and 2079 are programmed with the 1500 Mbps calibration bin** (1440 lands on bucket `{1449}`). Consequence:
  receiver margin, not refusal: 1782 held full row counts ~5 min and 16/16 short takes (`:765,:958`); 2079 degraded a mode over minutes
  (1090 → 5 → 47 valid rows) (`:761-766`). The PHY setting is mode-invariant (`:771-775`). Both rigs run with this warning in `dmesg`.
- Driver timing: `HMAX_table_4lane_4K_12bit` 660 at 720 MHz, 550 at 891 MHz (`imx585.c:293-294@18c1eb2`, kb `q7-cinemate.md` §1);
  Clear HDR floors HMAX at 550 and doubles VMAX (`drivers.md:65-66`); `pixel_rate = width × 74.25 MHz / HMAX` (`drivers.md:67`).
  dmesg on the Apertar Pi: `3840x2200 -> VMAX=4500 HMAX=550` at 891 MHz (`clearhdr-design.md:120`); the Core probe (after `configure()`,
  so including the IPA's pixel-rate bound) lists 3840x2160 SRGGB10/12 at **60.0 fps**, crops 62.85-85.66 (`working/sensor-capabilities.md:51`,
  `hardware-log.md:830`). 60.0 = 74.25e6 / (550 × 2250): HMAX 550, VMAX 2250 for SDR 4K at 891 MHz. **Confirmed by arithmetic + probe.**
- RP1 pixel-rate cap: Apertar's libcamera computes 333.33 MHz × 2 − 20 = **646.7 MPix/s** (kb `q7` §1, `controller.cpp:59-64,135-145@7e9fef0`);
  cinemate passes `--max-pixel-rate 580` with the overlay, 380 stock (`rp1_regime.py:70-72`). 4K needs 3840 / 7.407 µs = **518.4 MPix/s**.

Conclusions for §6 (probable unless marked):
- 4K 50 fps 12-bit SDR is inside the link envelope (70 % of 1782, 87 % line occupancy during active lines) and the RP1 envelope (80 % of the

- The stack-independent risk at 1782 is the D-PHY running on the 1500 bin; the handbook saw it as row truncation over minutes at 2079 and

## 8. Verdict (conclusions)

1. Streams, sizes and the preview stream are the same in both stacks; the BE renders one 1280x720 output either way. **Confirmed.** The
   "no main stream during takes" and "smaller preview" ideas buy nothing (q1: −4 %, and the BE runs into internal buffers without a preview
   buffer).
2. The decisive configuration difference for the serial BE cycle is **TDN** (and SDN/CDN/dpc/geq/alsc/sharpen) **off in cinemate's installed
   imx585 tuning**. In 4K SDR that is 19.8 MB per BE frame for cinemate against 29.0 MB for Apertar if Apertar's tuning has `tdn` (probable,
   unconfirmed); in Clear HDR 16-bit it is 20.0 against 57.6 MB. **Confirmed mechanism, unconfirmed Apertar-side state.**
3. cinemate's raw path is otherwise *heavier* in SDR (16-bit container: 2× CFE bytes and a 16→12 pack pass; q7 found the Clear HDR per-frame
   totals ~5 % heavier than Apertar's). So "cinemate did 4K 50 fps without drops" is not something its configuration makes more likely than
   Apertar's, **except** through the TDN-less tuning — and no counted record of such a take exists anywhere in cinemate's repos or handbook.
   **Confirmed (absence of record); probable (mechanism).**
4. For Apertar, the T34 M3 numbers fit a BE-bound serial cycle of ~22.7 ms at 3840x2076 50 fps with TDN on; with TDN off the estimate is
   8-11 ms. The same copy-of-the-tuning change is the cheapest test for both 4K 50 fps SDR and 4K 30 fps Clear HDR 16-bit, and should also
   widen the margin at 25 fps Clear HDR (short-take losses). **Probable.**
5. Link and RP1: inside the envelope on both rigs (70 % link, 80 % RP1 at 50 fps), identical hardware configuration, shared D-PHY clamp. Not
   the separator. **Confirmed arithmetic.**

## 9. Leads (concrete, with how to test on the Pi; `working/tools/be_cycle.py` exists)

L1 (cause + improvement). **Read the active tuning, then run without `tdn`.**
- Read-only first: `journalctl -u apertar-core -b | grep -i 'tuning file'` → the path; then
  `python3 -I -c "import json,sys;d=json.load(open(sys.argv[1]));print([list(a['rpi.denoise'].keys()) for a in d['algorithms'] if 'rpi.denoise' in a])" <path>`
  for both `imx585.json` and `imx585_clearHDR.json`. If the output has `tdn`, TDN is on (kb q1 row 13 check, never run).
- Make copies without the three `tdn` objects (keep `rpi.denoise` so SDN/CDN switch to their `*_no_tdn` values, `denoise.cpp:62-70`):
  `imx585_notdn.json` and `imx585_clearHDR_notdn.json` in `/home/pi/Tuning-Files/`. Select with the UI tuning option or socket
  `set_tuning_file` (`CameraController.cpp:10916`), or `APERTAR_TUNING_FILE` in the service drop-in (`scripts/start-apertar-core.sh:16-17`).
  Note: a user-picked file is used as given (`:6903-6909`), so switch the copy by hand when switching Clear HDR, or add a Core option that
  derives a no-tdn copy automatically the way `makeProresIspTuning` already derives the log-preview tuning (`src/color/ProresIspProfile.cpp:118-210`).
- Measure: one `LIBCAMERA_LOG_LEVELS=RPI:0,RPiStream:0` window idle and one recording, `python3 -I be_cycle.py <log>` → S2 (BE) and cycle,
  before/after; then 60 s takes at 4K SDR 12-bit 50 fps (3840x2160 and 3840x2076) and Clear HDR 16-bit 25 and 30 fps; count DNGs against
  elapsed × fps. Prediction (probable): S2 falls roughly with bytes (SDR 29→10.6 MB, HDR 57.6→20 MB); 50 fps SDR and 30 fps HDR deliver
  ≥ 49.8 / 29.8 fps. Rule-out: S2 within 15 % of the TDN-on value → the BE is not memory-bound and the limiter is elsewhere.
- Side effect: preview a little noisier; DNGs unchanged (the BE only reads the raw buffer).

L2 (assessment). **Measure the SDR back-end cycle at 50 fps directly** with `be_cycle.py` (no change): if median S2 ≥ 17 ms while recording,
the BE is the limiter and L1/L3 apply; if S2 ≤ 12 ms with a cycle still > 20 ms, the loss is software latency (S1/S3/S4) — then L4.

L3 (improvement). **Compressed TDN for Clear HDR 16-bit** (libcamera patch, kb q1: TDN nodes get `PISP_COMP1`, −33 %: 57.6→38.8 MB). In SDR the
TDN is already COMP1 (format follows the CFE), so only L1 helps there.

L4 (cause). **WebUI MJPEG encode inside the serial cycle.** `captureWebPreviewFrame` downsamples and JPEG-encodes on libcamera's completion
thread whenever a browser is viewing, up to 30 fps (`ApertarCoreApp.cpp:9352-9355,80`). Candidate for the 2026-10-31 "short takes lose 2-10
frames in the first seconds with the WebUI open" (`hardware-log.md`, drop-frames README open item 1). Fix: post the slot to a worker (copy the
≤640x360 downsample there) or cap at 10-15 fps while recording. Test: 60 s Clear HDR 25 fps with the WebUI open vs closed, then with the
change; `be_cycle.py` S4 median open vs closed.

L5 (assessment). **A counted 4K SDR take at 50 and 60 fps on `92d0970`** (3840x2160, COMP1, lossless and uncompressed), 60 s, DNG index vs
expected; the pre-roll's "60.0 fps, 115 frames in 2.0 s" is not a gap count (`hardware-log.md:842-853`). Also settles whether the
3840x2076 crop in M3 behaved differently from 3840x2160.

L6 (assessment, link). Confirm the RP1 cap and link state once: libcamera's pixel-rate log line (expect 646.7 MPix/s), `dmesg | grep -i 'DPHY\|imx585'`
(expect the 1782 out-of-range warning and `HMAX=550`), and `csi2_errors` before/after a 50 fps take (q6). A diagnostic take at
`link-frequency=720000000` (1440) at 48-50 fps isolates D-PHY margin from the BE (50.0 is the sensor ceiling there).

L7 (improvement, lower priority). Fewer per-frame controls: Apertar already sets none in normal running; nothing to cut. BE decimation / raw-only
configuration need libcamera patches (kb q1 X4 traps); not worth a take before L1.
