### 2.2 Copy worker (one thread, `APERTAR_RAW_COPY_WORKERS` 1..2, nice 0, no affinity; `CC:4774-4830`)

pop (`copyMutex_`) -> `acquireRawBuffer(size)` (`mutex_`, §2.1) -> `dmabufCpuSync(fd, START)` -> `memcpy` (16.6 MB Clear HDR / 8.3 MB SDR COMP1) -> `dmabufCpuSync(fd, END)` -> **`releaseHeldRequest`** (`--heldRequests_`, release callback -> `requeueRequest` under shared `sessionSettingsMutex_` and `controlsMutex_` -> `camera_->queueRequest`, `:4832-4843`, `:8224-8229`, `:8540-8575`) -> Log table pass **or** `compressClearHdrFrame` (never both, `:4800-4817`) -> `enqueue` (`mutex_`; the second `drop[queue-full]` site, `:4657-4668`) -> `frameQueued_` (audio). The request is held from the completion callback until the memcpy ends: measured ~6 ms per 16-bit frame for sync + copy (`351a3ee` message; kb b3 "copy ~4 ms / sync ~4 ms", `apertar-kb/working/compare-raw/b3-core-completion.md:35-36`). The LUT runs after the release, so Log/CCMP never hold camera buffers; they do hold the copy worker.

`dmabufCpuSync` = `ioctl(DMA_BUF_IOCTL_SYNC, READ|START/END)` (`CC:3583-3594`), copy worker only. Each sync walks the whole buffer once per mapped attachment (CFE Output0 and BE Input: 2), ≤ 0.5 ms each (kb q3 §1, probable).

### 2.4 Capture-gap detection (confirmed, `CC:9475-9528`)

Sensor-timestamp arithmetic only: `dt = ts - last`; `nominal` = the frame's own `FrameDuration` else `1e6/fps`; if `dt > 1.5 x nominal` add `round(dt/nominal) - 1` to `recordingGapEstimate_`, print `drop[capture-gap]` (first, every 30th, or multi-frame). Blind during the fps-ramp grace: `max(10, requests_.size() + 6)` frames of the slower rate after **any** fps change, including the pre-roll's two (`:9210-9245`): with 8 requests that is 14 frames = **0.56 s at 25 fps**. No `FrameBuffer::metadata().sequence` is read anywhere (grep); `buffer->metadata().status` (FrameError) is not checked (R7 §3.1). The timestamps are stamped by the CFE frame-start ISR (R7, web), so a late libcamera thread never shows as a gap; only a frame the CFE did not write does. Core cannot tell "its own held requests" from "libcamera's queue" from "CSI-2 loss"; `drop[copy-slot]` bounds its own share and none appear in the operator's logs (`HL:140, 784-785`).

cinepi-raw does the same arithmetic on the encode worker from `SensorTimestamp` (`DE:2126-2135`: `raw_elapsed >= 2` -> `dropped_frames_ += raw_elapsed - 1`), plus a `"Frame Drop!!!!!"` LOG(1) when measured fps deviates > 1 from `FrameDuration` (`cinepi-raw/cinepi/cinepi_recorder.hpp:92-96`). Neither stack reads sequence numbers.

### 2.5 Writers and the sync thread (relevant here only for the DRAM/CPU they add)

4 uncompressed writers on exFAT/ext4 (`MediaProfile.hpp:148-152`; `CC:4116-4122`), nice 0 (`setpriority` only for lossless/lossy and only when > 0, `CC:4919-4930`). Per DNG: `open|O_TRUNC`, `fadvise(SEQUENTIAL)`, row memcpy/pack into a 64-row scratch, 36 `write()`, `fadvise(DONTNEED)`, `close` (`CE:1749-1783, 1866-1908`), then `startWriteback` (`open` + `sync_file_range(WRITE)` + `close`, default on, `CC:4495-4511, 4978-4979`), `noteWrittenFile`; the sync thread fsyncs every file of the last second and the folder (`CC:4525-4549`). Per 16-bit frame Core's threads move 99.5 MB (memcpy r+w, scratch memcpy r+w, kernel `copy_from_user` r+w) against cinepi-raw's 66 MB (R3 §2, confirmed from both sources); Log adds a fourth pass (+33 MB). Dirty pages stay at 3-11 MB (`HL:745, 763`).

- **Harms**: (1) a 4K SDR 12-bit uncompressed pre-roll at 60 fps writes ~120 x 12.0 MB ≈ 1.43 GB -> **a full `fstrim` is queued right after** (runs when idle; a `record_start` within 5 s waits ≤ 2 s then SIGTERM/SIGKILLs it, `APP:11173-11196`), i.e. a trim or a killed trim may sit right before the operator's take; a Clear HDR 16-bit 25 fps pre-roll (~830 MB) or the measured lossless one (688 MB) stays **below 1 GiB: no trim, and the freed clusters are reused untrimmed** (SSD erase-before-write; probable, SSD mechanics); (2) two fps changes -> the capture-gap counter is **blind for `max(10, N+6)` = 14 frames (0.56 s at 25 fps)** if a take starts inside the grace (hides, does not create, gaps); (3) each `applyControls` takes `sessionSettingsMutex_` unique for < 1 ms (est.) while the completion thread wants it shared; (4) the unlink burst and a `syncfs` on the pre-roll thread; (5) ~5-11 k freed clusters per pre-roll and the clip number reused (fragmentation: outside this lens, R2/R4).
- Not warmed: libcamera (no reconfigure, no new buffers), CPU clocks (fall back within ms), the BE.

Evidence so far: none either way. A0/A1 predate the pre-roll (Core `a40112a`); whether the 10-31 short-take build ran an automatic pre-roll (and a trim) at boot before the short takes is unconfirmed (`HL:779-793`; the pre-roll is in the `d44b177` squash).

## 11. Hypotheses, ranked (ids S2-n)

Each: claim, mechanism, evidence for/against, the single test, expected effect, risk. "(kb)" marks a restatement of a kb finding.

### S2-1 — cause (both operator cases): the serial IPA -> BE -> completion cycle exceeds the frame period, and TDN is its largest removable term (kb, extended to 50 fps)
- **Claim.** 4K 50 fps SDR 12-bit loses ~6 frames/s because the per-frame cycle is ~22.7 ms against 20 ms; 4K Clear HDR 16-bit 25 fps sits ~4-5 ms inside its 40 ms budget while recording, so any added ms on the completion thread or any DRAM spike skips a frame.
- **Mechanism.** §1: one frame in flight (`LC pisp.cpp:2327-2330`); the BE's DMA (raw 1.1x + TDN read + TDN write + output) runs inside the stage and stretches under the recording's DRAM load; buffers only delay the first skip; each overrun of a full period makes the CFE skip exactly one frame (SOF-stamped timestamps show dt = 2 periods).
- **For.** T34 M3 signature (steady single-frame gaps, 44 of 50 fps, queue 2-3/12, 8 buffers no help, writers idle, `HL:582-597`); the measured 30 fps Clear HDR mechanism (36.2 ms cycle, 217 ms queue, `HL:172-202`); L2 freed the thread and gained nothing (`HL:219-232`); byte arithmetic puts Apertar SDR COMP1 TDN-on at 19-23 ms (R9 §5); 1080p50 is clean (`HL:489-501`).
- **Against.** The 50 fps BE time was never measured; the mode was the 3840x2076 crop on `4d5fdd1`, pre-trim, drive 78-82 % full; the raw packing of that take is unrecorded; whether Apertar's tuning has `tdn` is unconfirmed.
- **Test (one restart, read-only first).** `grep -c '"tdn"' /home/pi/Tuning-Files/defaults-pisp/imx585*.json`; then `LIBCAMERA_LOG_LEVELS=RPI:0,RPiStream:0 LIBCAMERA_LOG_FILE=/dev/shm/rpi0.log` drop-in, 5 s preview-only and 10 s recording windows at 4K SDR 12-bit 50 fps (3840x2160, uncompressed) and at Clear HDR 16-bit 25 fps, `python3 -I working/tools/be_cycle.py /dev/shm/rpi0.log` -> S2 (BE) and cycle medians. Then copies of both tuning files without the `tdn` objects (keep `rpi.denoise`), selected with `set_tuning_file` or `APERTAR_TUNING_FILE`, same windows, then 60 s takes counted as DNGs vs elapsed x fps.
- **Expected.** TDN on: S2 ≥ 17 ms at 50 fps while recording, cycle ≈ 22-23 ms. TDN off: S2 falls roughly with bytes (29 -> 10.6 MB SDR; 57.6 -> 20 HDR), 50 fps SDR delivers ≥ 49.8 fps over 60 s, Clear HDR 25 fps gains ~10 ms of margin and 30 fps becomes possible. Rule-out: S2 within 15 % of the TDN-on value -> the BE is not memory-bound and the limiter is software latency (S2-4) or the link (S2-8).
- **Risk.** Preview a little noisier (SDN/CDN switch to `*_no_tdn` values); DNGs unchanged (the BE only reads the raw). Low.
- Refs: `LC pisp.cpp:1212-1221, 1493-1498, 2327-2330`; `LC pipeline_base.cpp:1499-1516`; `LC denoise.cpp:55-70`; `HL:172-202, 582-597`; `apertar-kb/working/research-30fps/q1-backend.md:22-35, 193-196`; R9 §5. Priority 1.

### S2-2 — cause (Clear HDR 16-bit 25 fps short takes with the WebUI open): the MJPEG downsample on libcamera's completion thread, reading a non-cacheable buffer, inside the serial cycle
- **Claim.** With a browser on `/preview.mjpeg`, every frame at 25 fps adds a 0.5-3 ms uncached read pass to the serial cycle, on a stage that has ~4-5 ms of margin; together with the HTTP threads (`/api/state` 1 Hz under `commandMutex_`, `/api/buffer` 4 Hz) and the JPEG thread it produces occasional one-frame skips.
- **Mechanism.** `APP:9354-9355` ("This runs on libcamera's completion thread"), `APP:9418-9423` three `downsampleNearestPlane` calls over an `mmap` of libcamera's preview dma-buf (vb2-exported -> MT_NORMAL_NC, kb q3 §1), ≈ 691 KB read per frame; `kWebPreviewMaxFps = 30` (`APP:80`) so every frame at 25 fps; it runs before `state_ = Idle`.
- **For.** All four lossy 10-31 short takes had the WebUI open; A0/A1 (clean, 10 min) did not (`HL:779-793`); the one-frame dt ≈ 80 ms signature is the cycle-overrun signature; the kb's critic listed it as H2 (`research-30fps-answer.md` §3). cinepi-raw does its MJPEG on a detached thread (`post_processor.cpp:107-136`).
- **Against.** The 10-31 gaps clustered at 2-4 s into the take, not steadily; the takes were confounded (reboot minutes before, an ssh journal query overlapped one); the cost is estimated, never profiled; A2's WebUI state is unknown.
- **Test.** The kb's two-take test: 60 s Clear HDR 16-bit 25 fps with every browser tab closed, then with the WebUI open and left alone; `ss -tnp state established | grep apertar-core` during each to count MJPEG clients; `be_cycle.py` S4 median open vs closed; `usample.py <pid> <CameraManager tid>` for `downsampleNearestPlane`.
- **Expected.** Open: 2-10 one-frame gaps per minute, S4 median +0.5-3 ms; closed: 0 gaps. Fix (S2-I2): hand the slot index to `mjpegThread_` and downsample there (or copy the 640x360 planes on that thread), or cap the web preview at 10-15 fps while recording.
- **Risk.** Low; the fix is ~50 lines in `ApertarCoreApp.cpp`.
- Refs: `APP:78-80, 7848-7897, 9347-9444`; `WebControlPage.cpp:19402, 15894-15910`; `HL:779-793`; kb `q3-bandwidth.md` §1. Priority 2.

### S2-3 — cause (first take after a (re)configure) / improvement: the cold raw pool zero-fills 16.6 MB under `DngRecordingQueue::mutex_` while the completion thread waits in `hasCapacityForFrame`
- **Claim.** For the first ~6 frames of the first take after Core start or a mode change (pool cleared at `CC:8191`), and whenever more than 6 copy vectors are in flight, `acquireRawBuffer` allocates `std::vector<uint8_t>(16.6 MB)` under `mutex_` (`CC:4625-4636`); the completion thread's `hasCapacityForFrame` (`CC:4572`) blocks for the zero-fill + ~4,050 page faults (3-8 ms est.) inside the serial cycle.
- **Mechanism.** §2.1 lock table. Also: every `recycleRawBuffer` refusal frees 16.6 MB (`munmap` or heap trim) on a writer thread.
- **For.** Code only; "3 of 4 first takes after a (re)configure were lossy, later ones clean" on 10-26 (`clearhdr-design.md:119`, pre-T25, when the copy was on the completion thread, so not the same path); the 10-31 short takes were first takes after a reboot.
- **Against.** The 10-31 first gaps came at 2-4 s, after the pool is warm (6 frames = 0.24 s); with `peak_queue` 2/12 the pool never thrashes in steady state; a 3-8 ms wait alone does not overrun a 40 ms period unless added to S2-1/S2-2.
- **Test.** Compare the first take after a mode change with the second (same length, WebUI closed); add a timed-wait log around `hasCapacityForFrame` (or `perf trace -e syscalls:sys_enter_futex -t <CameraManager tid>`); `perf stat -e page-faults -p <core pid>` during a take.
- **Expected.** First-take-only gaps in the first second; none on the second take. Fix (S2-I3): allocate outside `mutex_`, pre-fill the pool in `startAtFolder` to `workers + queue + 2`, no value-initialisation.
- **Risk.** Low; +6-18 x 16.6 MB resident.
- Refs: `CC:4570-4602, 4623-4645, 5132-5155, 5232-5245, 8191`; R3 L4; R7 L3; kb b3 §6.2. Priority 5.

### S2-4 — cause (both cases, secondary): scheduling latency of libcamera's software stages on a 4-core box with ~20 Core threads, IRQs on CPU0 and no RT or affinity
- **Claim.** S1 (IPA thread, nice 0), S3 (BE-done interrupt -> CameraManager wake) and S4 (completion) wait behind writers, the copy worker, the sync thread, WebUI threads and the 250 ms pollers; nice -5 on one thread (if the drop-in is even installed) is a weight, not a guarantee; cinemate's FIFO 70 + `taskset -c 1-3` removes that latency.
- **Mechanism.** §2.6, §5. Cores 59/44/48/38 % busy while recording at 30 fps (`HL:163`); the kb estimated S1+S3+S4 at ~1.6 ms idle, up to ~5 ms under load (critic H2/H11).
- **For.** cinemate runs its whole process RT and off CPU0; the IRQ core carries all RP1 interrupts; Core's `LimitNICE=-5` drop-in has no install path (grep) so the thread may be nice 0 on the Pi.
- **Against.** The 30 fps loss did not move when the thread's own work was removed (L2); no run-queue delay has been measured; a spinning FIFO thread can lock a core.
- **Test.** `journalctl -u apertar-core -b | grep 'capture scheduling'` (nice -5 achieved or "normal priority retained"); `systemctl show apertar-core -p LimitNICE`; `perf sched latency -t <CameraManager tid>` (or `/proc/<pid>/task/<tid>/schedstat` run-delay deltas) during a 60 s take; then A/B the start script with `chrt -f 70 taskset -c 1-3` behind `APERTAR_RT=1` and a `LimitRTPRIO=80` drop-in, WebUI open (the failing case).
- **Expected.** If run-delay p99 ≥ 2 ms, RT removes it and the short-take gaps shrink; if < 0.5 ms, scheduling is not the lever.
- **Risk.** Medium: a stuck RT writer or a spinning thread starves the UI; RT throttling (950 ms/s) still applies.
- Refs: `CC:8590-8601, 4919-4930`; `config/apertar-core-capture-priority.conf`; `cinemate/src/module/cinepi_multi.py:83-92, 272-296`; `cinemate-autostart.service:27`; `HL:163`. Priority 4.

### S2-5 — cause (secondary, DRAM): Core moves each 16-bit frame through memory one more time than cinepi-raw (two with Log), stretching the memory-bound BE
- **Claim.** +33 MB/frame (scratch memcpy) and +33 MB/frame (in-place Log LUT) of CPU streaming overlap the BE's DMA and lengthen S2.
- **Mechanism.** §6 DRAM table; IPC drop with constant misses (`HL:161-162`); "dd to tmpfs costs frames, dd oflag=direct does not" (`HL:86-88`).
- **For.** Measured contention; cinepi-raw's single assembly pass folds LUT/pack into the one read (`DE:1210-1263, 1423-1434`).
- **Against.** The average is 34-58 % of DRAM capacity; the effect size per 33 MB is unmeasured.
- **Test.** For 16-bit unpacked (`rowBytes == stride`) write 64-row chunks straight from `job.rawBytes` (skip `writeDngRowBytes`), and for Log fold the LUT into `packDng12Row`; A/B 10 x 60 s takes at 25 fps with WebUI closed; `be_cycle.py` S2 before/after; `perf stat -e bus_access -t <CameraManager tid>`.
- **Expected.** S2 shorter by a few % per 33 MB removed; most visible at 30 fps HDR or 50 fps SDR as delivered fps.
- **Risk.** Low (encoder change only).
- Refs: `CE:1045, 1855-1857, 1866-1908`; `CC:4800-4817`; kb `q3-bandwidth.md:17-60`; R8 O2/O3, L6. Priority 6.

### S2-6 — cause (Clear HDR 16-bit + Log residual): Log changes nothing on the serial cycle but halves the copy worker's budget and adds DRAM traffic; its one measured take is confounded

## 12. Assessments

**better_in_general.** Established: the queue-full class (bursts after ~0.9 TB written without a trim) is gone on a trimmed drive (A0 15001/15001, 10 min, defaults; the synthetic 48 + 23-run series; Core's trim at mount measured 0.47 s). The capture-gap class is **untouched by any drop-frames change**: nothing in `d44b177` (trim, Log, ram buffer, safety stop, fps max from the probe, pre-roll) runs on libcamera's thread or shortens the serial cycle; Log adds a pass on the copy worker. Inferred: the drop-frames build should be at least as clean as `a40112a` in long 25 fps Clear HDR takes with the WebUI closed, because the only new per-frame work is off the serial thread. Unknown: no take of either operator case on `d44b177` or later longer than ~14 s exists; the four short takes lost 2-10 frames at capture with the WebUI open; 4K 50 fps SDR has not been run since T34 M3 (`4d5fdd1`, pre-trim, 2076 crop). The one thing that would make 50 fps better — a tuning without `tdn` — is not in the build. Verdict: better for the drive-state failure; unproven for the operator's two named cases.

**preroll_effect.** Established: both stacks run a 2 s take at the sensor maximum and delete it; neither author states a mechanism; neither stack has a measurement of its effect on the next take; Apertar's runs at the pinned period (60.0 fps measured once). Inferred from code: it warms the raw copy pool (6 x 16.6 MB) and exFAT metadata pages, nothing in libcamera; it leaves the capture-gap counter blind for 14 frames (0.56 s) after it ends; a 4K SDR 60 fps uncompressed pre-roll (~1.43 GB) queues a full `fstrim` right before the next take (killed after 2 s if a take starts within 5 s), a Clear HDR or lossless one (< 1 GiB) leaves its freed clusters untrimmed. Prior: low either way for the capture-gap class (the gaps are a per-frame cycle deficit, not a cold start) and neutral-to-slightly-negative for the storage class. Unknown: everything measurable; the kb's step 0b (COLD/WARM/SECOND, 6 pairs) plus a third arm "pre-roll then wait for the trim to finish" is the test. Honest default until then: off for the automatic triggers.

**clearhdr16_residual.** Established: 25 fps uncompressed is clean for 10 min on a trimmed drive with the WebUI closed (A0, A1, pre-drop-frames build); the serial cycle while recording at 30 fps is ~36 ms, so at 25 fps the margin is a few ms; four short takes with the WebUI open lost 2-10 frames each as one-frame SOF gaps 2-4 s in; A2 lost 10 % with no fsync and no `sync_file_range` (one run, mechanism not as the kb stated). Inferred: the residual gaps are cycle overruns of a few ms on a stage with a few ms of margin; the candidates with code behind them, in order, are the MJPEG downsample on the completion thread reading an uncached buffer (S2-2), scheduling latency of S1/S3/S4 under Core's ~20 nice-0 threads plus HTTP pollers (S2-4), the extra DRAM passes incl. Log (S2-5/6), and the cold pool at first take (S2-3); TDN off (S2-1) widens the margin regardless of which it is. Unknown: the WebUI state of A2; the actual S4 cost with a browser; whether `LimitNICE=-5` is in effect; whether Apertar's `imx585_clearHDR.json` has `tdn`. Log is not a plausible cause by itself (off the serial thread, ≤ 25 ms of a single worker's 40 ms) but has never been measured over a long take.

**sdr50_residual.** Established (T34 M3, 2026-10-28, `4d5fdd1`, 3840x2076, pre-trim, drive 78-82 %): 355/358 frames of ~2980 lost at capture in 60 s, delivery 44 of 50 fps, steady one-frame gaps of 40 ms, queue 2-3/12, 0 write failures, unchanged with 8 raw buffers; the drive sustained 525 MB/s; 1080p50 clean; the sensor probe allows 60 fps at 3840x2160 (the kb says a 3840x2160 50/60 fps take has never been run). Inferred: a 22.7 ms serial cycle against a 20 ms period, matching the TDN-on COMP1 BE arithmetic (≤ 17.4 ms recording + 2-5 ms software); not storage, not buffers, not the link (70 %), not the RP1 cap (80 %); nothing in the drop-frames build changes it; cinemate has no counted 50 fps take and its own SDR path moves twice the bytes, so its only edge would be the TDN-less tuning and FIFO scheduling. Unknown: the BE time at 50 fps (never measured), the raw packing of M3 (COMP1 expected), whether 3840x2160 behaves like the 2076 crop, whether Apertar's `imx585.json` has `tdn`. The two cheap measurements: preview-only delivery at 50 fps (`ipa_rate.py`: 50.00 idle and ~44 recording means recording load lengthens the cycle; ~44 idle means a sensor/timing limit) and one `RPI:0` window with `be_cycle.py` while recording; then the TDN-less copy.
