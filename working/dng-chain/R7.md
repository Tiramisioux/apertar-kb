## 0. Short answers to the orchestrator's questions

| Question | Answer | Status |
| --- | --- | --- |
| How is a capture gap detected? | Sensor-timestamp arithmetic only. `trackRecordingCadence` keeps the last recorded frame's `SensorTimestamp` (µs); if `dt > 1.5 × nominal` it adds `round(dt/nominal) − 1` to `recordingGapEstimate_` and prints `drop[capture-gap]`. `nominal` = the frame's own `FrameDuration` metadata (normalised), else `1e6/fps`. No sequence numbers are read anywhere in Core. | confirmed `src/camera/CameraController.cpp:9480-9528@92d0970`; `grep -n sequence` finds only clip-number code (`:1210-1234`) |
| Where does the timestamp come from? | libcamera `cfeBufferDequeue`: `sensorTimestamp = buffer->metadata().timestamp` of the CFE raw buffer → `controls::SensorTimestamp`. The kernel stamps the buffer in the **frame-start** ISR (`cfe_sof_isr_handler`: `node->ts = ktime_get_ns(); node->cur_frm->vb.vb2_buf.timestamp = node->ts`). So a late libcamera thread does not move the timestamps of frames that were captured; only a frame the CFE never wrote shows as a gap. | confirmed (web, verbatim quotes) |
| Can Core tell "CFE skipped the frame for lack of a buffer" from "libcamera's thread was late"? | **No, not from its own data.** A late thread by itself produces no gap. A gap means the CFE did not deliver a sensor frame to the raw node; the two kernel causes are (i) `cfe_check_job_ready`: a node with an empty `dma_queue` → `"has no buffer, unable to schedule job"`, frame not captured, `fs_count` still advances; (ii) a CSI-2 discard/overflow (`csi2_errors` debugfs). Within (i) Core cannot see **who** held the buffers: its own copy worker (bounded to N−2; overflow is logged as `drop[copy-slot]`) or libcamera's internal queues (`requestQueue_`/`cfeJobQueue_`, measured 6-7 frames deep at 30 fps while recording). What Core *can* say: with zero `drop[copy-slot]` lines it never held more than N−2 requests, so libcamera+CFE always had ≥ 2 raw buffers; a gap then means libcamera held both (serial cycle > period) or the frame was lost on the link. | confirmed logic; the discriminating evidence is kernel-side (rp1_cfe dynamic debug, `csi2_errors`) or libcamera `RPI:0` timing |
| Are sequence numbers available? | Yes, unused. `vb.sequence = node->fs_count − 1`, `fs_count++` in the SOF ISR **unconditionally** (also when `next_frm` is NULL). libcamera uses it for `delayedCtrls_->get(buffer->metadata().sequence)` and exposes it as `FrameBuffer::metadata().sequence`. Core could count gaps exactly as `seq − lastSeq − 1` on the raw buffer, independent of fps ramps. `Request::sequence()` is libcamera's request counter, not the frame. | confirmed (web) + confirmed Core does not read it |
| How many requests are queued to the camera during a take? | N requests, one per raw buffer (each also carries one preview buffer). N = `rawCameraBufferCount`: Clear HDR 8, SDR 4, +2 only for FAT/NTFS (exFAT +0), env `APERTAR_RAW_CAMERA_BUFFERS` 3..16. Copy worker holds ≤ N−2 (6 / 2). libcamera+CFE therefore hold ≥ 2 at all times; how many of those are queued **at the CFE** (vs. waiting in libcamera's serial loop) is not visible to Core. | confirmed `:1245-1249, :1363-1371, :8224-8229, :8336-8345@92d0970`; `src/util/MediaProfile.hpp:141-150@92d0970` |
| When exactly is a request requeued? | Preview-only or a frame not taken: at the end of `requestComplete`, on libcamera's thread (`:8670`). A recorded raw frame: **after the memcpy** on the copy worker (`releaseHeldRequest` → release callback → `requeueRequest` → `camera_->queueRequest`, `:4797-4800, :4832-4844, :8224-8229, :8569`). A dropped frame (`copy-slot`, `queue-full` before copy, cadence gate): at once on libcamera's thread. `Camera::queueRequest` posts to the pipeline handler with `ConnectionTypeQueued` (web, verbatim), i.e. the V4L2 QBUF to the CFE happens later on libcamera's CameraManager thread, behind whatever that thread is doing. | confirmed |

## 3. Capture-gap detection, exactly (confirmed `:9480-9528@92d0970`)

```
if (inFpsRampGrace(ts)) { last = ts; return; }                 // blind for max(10, N+6) frames of the slower rate after ANY fps change (:9221-9234, :9236-9244, 7170-7171)
if (!haveLast) { last = ts; return; }                          // first recorded frame: no gap possible
if (ts <= last) { last = ts; return; }                         // non-monotonic: reset, not counted
dt = ts - last; last = ts;
nominal = normalizeFrameDurationToUs(FrameDuration) || 1e6/fps // the frame's own period from metadata (:8912-8916, :3604-…)
if (dt > nominal*3/2) { est = (dt + nominal/2)/nominal - 1; if (est > 0) { recordingGapEstimate_ += est; dropWarning_.markDropped(); print if total==1 || total%30==0 || est>1 } }
```

- Runs only for frames that pass the cadence gate **and** are recorded (`recordRawFrame` `:8918`; ProRes `:9717`; H.264 `:9752`); preview-only gaps are invisible. The frame that follows a gap is itself recorded; nothing is renumbered: `nextFrameIndex = max(counter, round((ts − first)·fps))` so a gap leaves a hole in the DNG numbering in normal takes (`:4462-4470`), not in speed-ramp takes (`countOnly`).
- Printed as `ApertarCore drop[capture-gap]: +<est> frame(s) estimate dt_us=<dt> nominal_us=<nominal> total_estimate=<total>`; at stop `ApertarCore capture stats: dropped_gap_estimate=<n> requeue_failures=<m>` (`:7353-7357`), only when either is > 0.
- `drop[requeue-failed]` = `camera_->queueRequest(request) < 0` `:8569-8574` (libcamera refused the request).
- `markDropped` is a per-clip latch → one `recording_health` event (`:9949-9953`), muted during a pre-roll (`RecordingDropWarning.hpp:17-23`).

### 3.1 What each mechanism does to the counter

| Mechanism | Produces a gap? | Why |
| --- | --- | --- |
| (a) copy worker behind → requests held | only through the CFE: when Core holds N−2 **and** libcamera holds the remaining 2 at a SOF. Core logs the cap overflow as `drop[copy-slot]` (frame not copied, request requeued at once) — none in the operator's logs (kb hardware-log `:140`, `:784-785`) | `enqueueCopy` `:4758-4766` |
| (b) libcamera thread descheduled / serial cycle longer than the period | **yes**, after the buffers absorb the deficit: CFE-complete frames pile up in libcamera's queue (217 ms ≈ 6-7 frames measured, `hardware-log.md:191`), the CFE finds no raw buffer at a SOF and skips one frame; the delivered frames keep their SOF timestamps so the skip shows as dt = 2×period | kb measurements `hardware-log.md:166-170, :177-200@1899e8d`; kernel `cfe_check_job_ready` (web) |

What the code makes plausible (all **unconfirmed**, mechanism named):
- Warms: (1) `rawPool_` — the first take after Core start or a mode change otherwise allocates its first ~6 copy vectors (16.6 MB zero-fill + page faults) **under `DngRecordingQueue::mutex_`** while libcamera's thread may be waiting in `hasCapacityForFrame`; after a pre-roll the pool is full (it survives takes, `:4649-4655, :8191`). (2) glibc's mmap threshold (first free of a 16.6 MB chunk raises it, later allocations come from the heap). (3) exFAT metadata in the page cache: the bitmap/FAT blocks for the region about to be allocated (`exfat_alloc_cluster > exfat_ent_set > __bread_gfp` were the kb's stall stacks) — the next take re-allocates the same freed clusters. (4) NVMe out of a low-power (APST) state. Not warmed: libcamera (no reconfigure), CPU clocks (fall back within ms of the pre-roll ending).
- Harms: (1) a ≥ 1 GiB pre-roll queues a **full fstrim** right before the operator's next take (or kills it at `record_start`, leaving the FTL mid-discard); (2) two fps changes → the capture-gap counter is blind for `max(10, N+6)` frames (0.4-0.6 s at 25 fps) if a take starts inside the grace (hides, does not create, gaps; `:9221-9244`); (3) the unlink burst and a `syncfs` on the pre-roll thread; (4) ~5-11k freed clusters per pre-roll and the `C####` number reused — fragmentation neutral if the allocator reuses the freed run (exFAT allocator behaviour: outside R7).
- Evidence so far: none either way. The clean A0/A1 10-minute takes predate the pre-roll (Core `a40112a`, `hardware-log.md:757`); the 2026-10-31 short-take drops are on "the drop-frames build before the safety stop" — whether that build had the automatic pre-roll (and ran one 3 s after the mount at boot) is **unconfirmed** (`hardware-log.md:779-793`; the pre-roll is in the `d44b177` squash `:11418-11424`).

## 9. Conclusions

1. Since T25 (`351a3ee`) libcamera's thread does, per raw frame: metadata reads, five short mutexes, the preview descriptor, the cadence arithmetic, two queue checks, and the MJPEG downsample when a browser streams. The copy, syncs and LUTs are on the copy worker. The only blocking hazard left on that thread is `DngRecordingQueue::mutex_` while the copy worker allocates a fresh 16.6 MB vector (pool cold after a reconfigure, or queue deeper than 6).
2. A capture gap in Core is a SOF-timestamp jump of ≥ 1.5 periods between two recorded frames. It is produced only by frames the CFE never delivered; libcamera lateness is invisible until it starves the CFE. Core cannot attribute the starvation (its own held requests, libcamera's queue, CSI-2 loss); its logs bound only its own share (`drop[copy-slot]`).
3. Requests: N = 8 (Clear HDR) / 4 (SDR) on exFAT; held ≤ 6 / 2; requeue of a recorded frame happens after the memcpy on the copy worker and is then processed asynchronously by libcamera's thread.
4. The 50 fps SDR and 30 fps HDR losses match a serial-cycle deficit (kb's measured mechanism) or a link loss; Core-side holding is ruled out by the absence of `drop[copy-slot]` lines and by the 8-buffer repeat. The 2026-10-31 short-take gaps have, in Core's code, two time-correlated candidates: the WebUI stream's per-frame downsample on libcamera's thread plus its HTTP threads, and first-take cold starts (pool allocation under the queue mutex; a boot-time full fstrim and/or a pre-roll-triggered trim finishing shortly before).
5. Nothing in Core uses SCHED_FIFO or affinity; the one priority boost (nice −5 on the callback thread) depends on a drop-in whose installation is unverified.
