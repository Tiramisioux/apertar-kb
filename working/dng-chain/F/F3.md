## 2. Budget tables

### 2.1 Per-frame DRAM traffic by actor

(368,640 / 491,520 B) is counted cache-resident (0) with its spill bound given; dma-buf cache-maintenance walks move no bytes (q3 row 12/29).

Comparison: (B) linear 5.20 GB/s = 30 % of the interface, 43-52 % of practical; (B) Log 5.83 = 34 % / 49-58 %; (A) 4.35 = 25 % / 36-44 %.
The averages do not saturate DRAM in any mode. The kb's measured facts say the mechanism is latency, not saturation: with ~5 GB/s of average
load the CameraManager thread's cycles per frame rose 25 M → 36 M at the same instructions and the same 0.57 M L3 refills (HL:159-162), the swap
pass stretched 6.1 → 9.9 ms, and the BE's start→done went 13.4 → 34.6 ms (HL:188-191). A buffered `dd` at 561 MB/s with Core idle (page-cache
copy + writeback + reclaim; no camera copy at all) took the CFE from 25.00 to 21.71 fps while an O_DIRECT `dd` at 759 MB/s cost nothing
(CHD:125-133): the CPU-side page-cache stream is the measured aggressor, and it is rows 9-10 of the tables above.

Checks against the kb's prior estimates: q3 §3 (195.5 MB at row step 4; 208.2 before L1) reproduces exactly for (B) once the scratch is counted
cache-resident; q5 §4.2 "5P = 82.9 MB of recording traffic" holds for the pre-6ef0ddc writer only as an upper bound and is now 3P for linear 16-bit
with the direct path (q5's option A "zero-copy + buffered" was 3P; 6ef0ddc reaches the same byte count while keeping the copy worker's hold short).

### 2.2 CPU time per frame per thread

Reference measurement (the only per-thread CPU data in the kb): 4K Clear HDR 16-bit at a 30 fps setting while recording uncompressed, Core
`351a3ee` (copy worker build, 4 writers, scratch path), system libcamera: CameraManager thread 54 % busy at 26.45 fps delivered = **20.4 ms per
frame**; "five other Core threads at 18-20 % each" (= 4 writers + 1 copy worker, probable) = 0.95 core; cores 59/44/48/38 % busy = **1.89 cores
total** (HL:159-164). Per delivered frame that is 71 ms of system CPU, of which Core's threads 56 ms (CameraManager 20.4, copy + writers 36).

## 4. What would settle it on the Pi

The decisive measurement for this dimension is one 60 s take per mode with per-thread CPU and the CameraManager thread's PMU read at the same
time, WebUI closed, then repeated with the WebUI open:

1. `top -H -b -d 1 -n 60 -p $(pidof apertar-core) > top.txt` (or `ps -L -o tid,comm,pcpu,ni,cls,psr -p $(pidof apertar-core)` once per second):
   the `%CPU` of `CameraManager`, the copy worker, the four writers, the sync thread and `mjpeg`; `NI`/`CLS`/`PSR` show the priorities actually in
   effect (expect NI −5 on CameraManager, or `FF` with `APERTAR_RT_CAPTURE_PRIORITY`). Decision: every thread below ~80 % of a core and the sum
   below ~300 % → CPU is not the limiter; a writer above 80 % in (A) → the COMP1 decode / exFAT term is real and (A) needs lever 8/9 reversed
   (more writers or a NEON decoder); the copy worker above 60 % with Log → Log is CPU-marginal.
2. `python3 -I working/tools/hwcount.py $(pidof apertar-core) <CameraManager tid> 20` preview-only, then recording: IPC, `stall_backend`,
   `bus_access`. Decision: IPC falling toward 1.3 with `stall_backend` > 20 % while recording (the 10-26 signature, HL:159-162) → DRAM contention is
   active in that mode; repeat with Log off/on and with `APERTAR_WEB_PREVIEW_RECORDING_FPS=0` to see which lever moves it. In (A) this reading does
   not exist yet at all.
3. `sudo perf stat -a -e armv8_cortex_a76/event=0x19/,armv8_cortex_a76/event=0x2a/ -- sleep 10` idle vs recording (`bus_access`,
   `l3d_cache_refill`, system-wide; q3 row 66 names: no `bus_access_rd/wr` aliases on this PMU). Model prediction for the CPU-side bytes of §2.1
   (B linear: swap 33.8 + stats 16.9 + copy 33.2 + kernel copy 33.2 = 117 MB/frame x 25 = 2.9 GB/s → ~46 M bus accesses/s of 64 B, ±10 % per
   q3's calibration row 16); a reading ≈ 2x the model means read-for-ownership or scratch spills and the DRAM table above is low.
4. `/proc/<pid>/task/<tid>/schedstat` (fields: run ns, **wait ns**, timeslices) for the CameraManager and IPA tids once per second → run-queue wait
   per frame = Δwait / Δslices. Below 0.5 ms per frame → scheduling is eliminated and levers 3/9 can be skipped (V/H15 §5.2).
5. `/proc/pressure/cpu`, `/proc/pressure/memory`, `/proc/pressure/io`: PSI is compiled (`CONFIG_PSI=y`) but **disabled by default**
   (`CONFIG_PSI_DEFAULT_DISABLED=y`, **web**: https://raw.githubusercontent.com/raspberrypi/linux/rpi-6.12.y/arch/arm64/configs/bcm2712_defconfig);
   it needs `psi=1` on `cmdline.txt` and a reboot (Patrik). Then `some avg10` for cpu and `full avg10` for memory/io during the take: `memory full > 0`
   means reclaim stalls (the `DONTNEED=off` risk), `cpu some > 5 %` means run-queue contention worth lever 3/9.
6. `vmstat 1` (si/so, wa) and `/proc/vmstat` `nr_dirty`, `nr_writeback`, `pgsteal_kswapd` before/after; `swapon --show` once.
7. The stats lines: `recording stats: … dropped_queue_full= … dropped_copy_slot= … peak_queue=` (`CC:4310-4320`) and `capture stats:
   dropped_gap_estimate= requeue_failures=` (`CC:7435-7438`, printed only when > 0), plus frames written against WAV seconds x fps.

Minimum duration: 60 s per arm (the first gap in the lossy 10-31 takes came 2-4 s in; 60 s = 1,500 / 3,000 frames and a steady-state `top`
average); the 10-minute take only as the acceptance run after the levers are chosen. Record alongside every take: WebUI clients
(`ss -tnp state established '( sport = :8080 )'`), `fps_speed_ramp` from `get_state` (frame numbering is count-based with it on), trim state
(`media_trim_last_*`), pre-roll state (`storage_preroll_active`, and whether a pre-roll ran since Core start), the tuning file in use
(`journalctl -u apertar-core -b | grep -i 'tuning file'` and `grep -c '"tdn"' <file>`), whether this is the first take after a (re)configure,
which libcamera is loaded (`grep libcamera /proc/$(pidof apertar-core)/maps | head -3`), `systemctl show apertar-core -p LimitNICE -p LimitRTPRIO`,
`journalctl -u apertar-core -b | grep 'capture scheduling'`, `swapon --show`, the HDMI mode (`cat /sys/class/drm/card*-HDMI-A-*/modes | head -1`),
and the knob environment (`systemctl show apertar-core -p Environment`).
