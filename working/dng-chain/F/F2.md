# F2 — libcamera's serial per-frame cycle (CFE dequeue → IPA → PiSP back end incl. TDN → Core callback → requeue)

Analyst F2, 2026-11-01. Build under study: Apertar-Core `6ef0ddc` (/home/user/Apertar-Core). Upstream libcamera `c682979`
(/home/user/raspberrypi/libcamera); **the Apertar libcamera fork (`6b0b49f` on qbc `7e9fef0`) is not local**: fork lines are the kb's
(q1/q2/R9) and are marked so. Modes: (A) 4K SDR 12-bit 50 fps, budget **20.0 ms**; (B) 4K Clear HDR 16-bit 25 fps, budget **40.0 ms**.
Labels: **measured** (log line cited) / **derived** (arithmetic shown) / **estimated** (model named, weakest assumption named) / **unverified**.
Status: COMPLETE (2026-11-01).

Stage names (be_cycle.py, `working/tools/be_cycle.py:1-20`): **S1** "Signalling IPA" → "Input re-queue to ISP" (IPA thread + two hand-offs);
**S2** "Input re-queue" → BE done timestamp (libpisp Prepare + QBUFs + BE hardware: an upper bound on hardware time); **S3** BE done → "ISP Input
buffer complete" log (done latency on libcamera's thread); **S4** that log → next "Signalling" (request completion incl. Core's callback and
requeue). cycle = S1+S2+S3+S4 when frames are backlogged; otherwise cycle = sensor period.

## 1. Verdict

**(A) 4K SDR 12-bit 50 fps: MARGINAL, bracket −2.7 ms to ≥ +3 ms, confidence LOW.** The only long counted take (T34 M3, 60 s, 3840x2076, build
4d5fdd1, uncompressed) delivered 44.0 fps ⇒ a 22.7 ms cycle, 2.7 ms **outside** (derived from measured loss). The only observation on the current
code (pre-roll on d44b177, 3840x2160 lossless, 60 fps, 115 frames) had **zero skips** ⇒ mean cycle ≤ 17.0 ms, ≥ 3 ms inside the 20 ms budget
(derived, 1.9 s window). The corrected byte model puts the SDR cycle at 10-14 ms with TDN on (estimated), so the model no longer predicts M3's
loss; the R9 figure of 19-23 ms was an over-prediction (it scaled a thread-latency-contaminated 16-bit figure; Appendix A.4). Nothing in the
record measures the SDR cycle directly. Which of M3's differences from the pre-roll caused its loss (crop mode, uncompressed writer path at
525 MB/s, untrimmed drive at 82 %, 60 s vs 2 s, build) cannot be established from the record. **Decisive**: one `be_cycle.py` window at 50 fps on
6ef0ddc (§4). With TDN off (tuning copy or `NoiseReductionMode=Off`): INSIDE by an estimated 13-16 ms, confidence MEDIUM.

**(B) 4K Clear HDR 16-bit 25 fps: MARGINAL-INSIDE, margin ≈ +4 ms (derived), confidence MEDIUM.** The serial work while recording at 30 fps
measured 36.2 ms (cycle) with BE start→done 34.6 ms; at 25 fps the same work has 40.0 ms, so the margin is ≥ 3.8 ms by medians (derived), more
with the lower DRAM load of 25 fps. Two 10-minute takes were clean (A0, A1: 15001 / 15000 frames, 0 gaps, measured) under one configuration
(WebUI closed, trimmed drive). The margin is thin enough that two other configurations lost frames at capture with the writers idle: A2 (no
per-frame writeback hint; 1491 gaps in 10 min ⇒ an effective 4.4 ms per-frame surplus, derived) and the 2026-10-31 short takes with the WebUI
open (0.6-7.9 % lost, the Log take worst). **With Log**: unverified over any long take; one 127-frame sample lost 7.9 % (WebUI open). With TDN
off: INSIDE by ≥ 4 ms even under the compute-bound reading, probably by 16-18 ms (estimated), and 30 fps becomes plausible.

The TDN state of the Pi's tuning (`/home/pi/Tuning-Files/defaults-pisp/imx585[_clearHDR].json`) is still **unverified**; every TDN-on number
below assumes the `rpi.denoise.tdn` key is present (probable: every PiSP IMX585 tuning in every tree read has it, kb q1 row 13, V/H2).

### 2.3 What the pool absorbs, and what it cannot

Extra raw buffers hide a *transient* overrun of up to (slack × period); they do nothing against a mean surplus (M3: 355 vs 358 lost with 4 vs 8
buffers, `hardware-log.md:591-594`; measured). Core's copy worker holds one raw buffer per frame for the memcpy (8.3 MB SDR ≈ 2-4 ms, 16.9 MB
HDR ≈ 5-8 ms, estimated), which is one buffer less of slack but not on the serial path (T25, `hardware-log.md:135-152`).

## 4. The decisive measurement

**Instrument**: `working/tools/be_cycle.py` on an RPI:0 window (it already splits S1/S2/S3/S4 and the cycle per frame and uses the kernel BE-done
timestamp in the log; `libcam_stages.py` lacks S2/S3). Steps (Patrik does the restarts and sudo):
1. Drop-in `libcamera-debug.conf` (exists): `LIBCAMERA_LOG_LEVELS=RPI:0,RPiStream:0` plus `LIBCAMERA_LOG_FILE=/dev/shm/rpi0.log` (be_cycle warns when
   journald drops lines, `be_cycle.py:82-84`); restart Core; let the preview settle 10 s.
2. **Mode A**: 3840x2160 SDR 12-bit, ladder off, 50 fps, uncompressed cDNG, WebUI closed, speed ramp off: record **60 s** (minimum: the SDR pool holds
   ≤ 2 frames of slack, so a steady surplus shows within seconds and a 2-4 s onset is covered; 60 s gives ~3000 cycles). Then the same at 3840x2076
   (M3's mode) and the same lossless. Then 10 min for the acceptance.
3. **Mode B**: 3840x2200 Clear HDR 16-bit 25 fps uncompressed, Log off then on, 60 s each (same conditions as A0).
4. `python3 -I ~/apertar-kb/working/tools/be_cycle.py /dev/shm/rpi0.log` per window. **Decision rule**: median cycle ≤ period and p90 ≤ period + slack
   (A: 20.0 / ~40 ms with 4 buffers; B: 40.0 / ~150 ms) ⇒ INSIDE; S2 median ≥ 17 (A) / 36 (B) ⇒ the BE is the limiter and L1/L2 apply; S2 small with a
   long cycle ⇒ software latency (S1/S3/S4) and L5b/L6 apply. Cross-check the count: DNGs written vs elapsed × fps (`dngmeasure.py`), the stats
   line (`dropped_gap_estimate`, `dropped_queue_full`, `dropped_copy_slot`, `peak_queue`) and `journalctl -u apertar-core -b | grep 'drop\['`.
5. Repeat step 2-3 with the TDN-off tuning copy (L1) after the read-only tuning grep. Prediction (probable): S2 falls roughly with bytes
   (A 29→10.6, B 57.6→20); rule-out: S2 within 15 % of the TDN-on value ⇒ not memory-bound, L3c is the fallback.

**Record alongside every window**: WebUI clients (every browser tab closed, or one open and left alone; `APERTAR_WEB_PREVIEW_RECORDING_FPS`),
`fps_speed_ramp` and `fps_phase_lock` state, trim state (journal `media: trim … ms=` time vs `record_start`; wait 60 s after a trim), pre-roll state
(`storage_preroll_last`, time since; `preroll=off` for the control arm), the tuning file in use (journal line + the `tdn` grep), first take after a
reconfigure (journal `camera configured` time vs `record_start`; take a second take too), which libcamera is loaded (`grep libcamera
/proc/$(pidof apertar-core)/maps`: installed fork vs `~/opt/libcamera-apertar`; `QBC_RAW_CPU_WORKER`, `QBC_RAW_STATS_ROW_STEP`), raw buffer count
(`buffer_*` state / `APERTAR_RAW_CAMERA_BUFFERS`), `APERTAR_RT_CAPTURE_PRIORITY`, the journal's `camera configured … format= packing=` line (COMP1
confirmation for the fork), `vcgencmd measure_clock isp`, `vcgencmd get_throttled`, drive fill and temperature.

## Appendix B. Composition of the cycle (upstream `c682979`, confirmed; fork differences marked)

Per frame, PH = libcamera's CameraManager thread (the thread Core's callback runs on), IPA = the in-process IPA proxy thread:

1. **CFE dequeue** (PH, `cfeBufferDequeue` `pisp.cpp:1705-1780`): Output0 (raw), Stats and Config buffers; log line with the SOF timestamp; new `CfeJob`;
   DelayedControls lookup; wall-clock sample. **16-bit only**: `do16BitEndianSwap` on the raw (6.1 → 9.9 ms measured, PH in L1; the fork's L2 moves it and
   the fork-only software raw stats, 5.8 → 7.1 ms at row step 1, to a worker, `hardware-log.md:219-233`). SDR COMP1: nothing but the bookkeeping (~0.1 ms, est.).
   Config buffers are re-queued at once with a new `fe_->Prepare` (`prepareCfe` `:2258-2272`).
2. **`handleState` → `tryRunPipeline`** (`:2327-2381`): gate `state_ == Idle && !requestQueue_.empty() && cfeJobComplete()`; `applyScalerCrop` (BE retile only
   on a change); `fillRequestMetadata`; `handleControlLists` (per-request controls → `params.requestControls`); `state_ = Busy`; `ipa_->prepareIsp` (async).
3. **IPA `prepareIsp`** (IPA thread, `ipa_base.cpp:416-525`): `applyControls` (incl. `NoiseReductionMode` → `handleControls`), device status, `helper_->prepare`,
   **`processStats` inline on the FE statistics** (AGC, AWB, ALSC, contrast, noise, lux… `controller_.process`; in 16-bit the fork feeds its software stats),
   `controller_.prepare` (every algorithm's `prepare`, Denoise included → `tdn.status`), `platformPrepareIsp` (`pisp.cpp:357-470`: FE lock briefly; BE global
   enables; `applyTdn`, LSC tables, CCM, gamma…; `be_->SetGlobal`), `reportMetadata` → `metadataReady` (PH merges into `requestQueue_.front()`), emit
   `prepareIspComplete`. ≈ S1 together with the two hand-offs: ≤ 1.6 ms by medians (HDR, derived); unmeasured alone.
4. **`prepareIspComplete` → `prepareBe`** (PH, `:1874-1899, 2274-2325`): log "Input re-queue to ISP"; QBUF input (the CFE buffer itself), TDN in/out ping-pong,
   stitch in/out (unless `disable_hdr`), acquire one of 2 config buffers, **`be_->Prepare`** (libpisp tiling: 10 tiles, ~16.7 kB config), QBUF config → the kernel
   forms the job and programs ~1620 MMIO words (~0.16 ms est., q2 §3) → **BE hardware runs the whole frame as one job**. `state_ = IpaComplete`.
5. **BE done** → PH dequeues Input (`beInputDequeue` `:1783-1795`, log carries the done timestamp), Output1 and Config (`beOutputDequeue` `:1797-1848`; the
   software downscale / 32-bit conversion paths are unused here) → `handleStreamBuffer` → `completeBuffer`; `checkRequestCompleted` (`pipeline_base.cpp:1499-1527`)
   → `completeRequest` → **synchronous** `Camera::requestCompleted` (`pipeline_handler.cpp:584-603`, `camera.cpp:1481-1488`) → **Core `requestComplete`**
   (`CameraController.cpp:8660-8760@6ef0ddc`): metadata reads (WB, exposure, gain), `noteFrameForPreroll`, first-frame priority set, `stepFramePhaseLock`,
   `capturePhotoFrame` (no-op), **`publishPreviewFrame`** (`:9630`: dma-buf fds dup'd once per slot, then a descriptor to the UI socket; **web downsample +
   turbojpeg hand-off on this thread when ≥ 1 MJPEG client and the rate cap allows**, `ApertarCoreApp.cpp:9366-9450`), **`recordRawFrame`** (`:8955-9079`:
   `enqueueCopy` under the queue mutex; the copy worker takes the request and requeues it after its memcpy) **or `requeueRequest`** (`:8551-8650`:
   `reuse`, merge `pendingControls_`, phase-lock/pre-roll `FrameDurationLimits` pin, `queueRequest` → `queueRequestDevice` → 2 QBUFs) → `state_ = Idle` →
   `tryRunPipeline` for the next CFE job.

Measured for the HDR configuration (A.1): S2 ≤ 13.4 idle / ≤ 34.6 recording (upper bounds); S1+S4 ≈ 1.6; Core's callback 0.23 ms idle / 0.3-0.5 ms recording
(kb usample, V/H4); web downsample 0.2-0.5 ms (README.md:293). Not measured for SDR at all.

Where the fork may differ (not readable here): the L1/L2 raw CPU passes and `cfeJobReady` gate (`pisp.cpp:1105-1112@6b0b49f`), forcing `Packing::None` for
16-bit/WDR (`compare-raw/b2-libcamera-16bit.md:152`), the RP1 pixel-rate cap from the device tree (646.7 MPix/s), tuning-helper paths. The state machine
(`Idle` gate, raw buffer back on BE-input dequeue, synchronous completion) is the same in both trees (q2 §1 cites the fork at `pisp.cpp:3112-3117,
2272-2284, 2363-2389@6b0b49f`; upstream read here).
