# F6 — Levers and the roadmap

Analyst F6, 2026-11-01. Dimension: every configuration, tuning, control, code and hardware lever across the chain
(sensor → CSI-2 → CFE → IPA/BE incl. TDN → Core callback → copy worker → Log → writers → page cache → exFAT → NVMe)
that adds margin toward drop-free (A) 4K SDR 12-bit 50 fps and (B) 4K Clear HDR 16-bit 25 fps (with and without Log), ordered into a path.

Trees: Apertar-Core `6ef0ddc` (/home/user/Apertar-Core), upstream libcamera `c682979` (/home/user/raspberrypi/libcamera), cinemate `4990afc`,
cinepi-raw `63a08d5`, the kb (hardware-log 2026-10-25 → 2026-11-01, `working/dng-chain/*`, `working/research-30fps/*`). **The Apertar libcamera fork
(`6b0b49f`) is not local**; every fork line is quoted from the kb (q1, q2, q7, R9). Nothing ran on the Pi. tomshardware.com and techpowerup.com do not
resolve from this session; their drive figures are cited from search summaries only.

Labels: **measured** (log line cited) / **derived** (arithmetic shown) / **estimated** (model named, weakest assumption named) / **unverified** / **web**.
Period budgets: **20.0 ms (A)**, **40.0 ms (B)**. "Inside the cycle" = libcamera's serial per-frame loop (CFE dequeue → IPA → BE → Core callback → requeue).

### 3.2 Notes on the load-bearing levers

**T1, the tuning copy.** Mechanism confirmed in upstream: `tdnEnable = params.contains("tdn")`; without it `Denoise::prepare` never sets
`tdn.status`, `platformPrepareIsp` never calls `applyTdn`, and the TDN bits are cleared every frame (`denoise.cpp:55-70,161-167`,
`ipa/rpi/pisp/pisp.cpp:365-370,426-428,773-809@c682979`). TDN's reference buffers use the CFE format (`pipeline/rpi/pisp/pisp.cpp:1492-1498`):
COMP1 in SDR (so the SDR TDN is already compressed, 2 × 9.19 MB), unpacked 16-bit in Clear HDR (2 × 18.73 MB). The fork `6b0b49f` has the same
blocks per V/H2 (WebFetch). Apertar's two tuning files are not in any repo; V/H2 argues "probable on, strongly" (a 134,888-byte PiSP tuning with
`rpi.hdr`; every PiSP tuning of that size class in upstream has three `tdn` blocks). Core's selection: automatic mode picks
`/home/pi/Tuning-Files/defaults-pisp/imx585.json` and the `_clearHDR` variant in Clear HDR (`DefaultTuningSelection.hpp:186-197`); a user-picked file
is used as given (`CameraController.cpp:6981-6990`), validated for the pisp target (`tuning::compatibleFile`, `:1334`), and `setTuningFile` reconfigures
the camera (`:11016-11075`). The Log/ProRes preview derivation (`makeProresIspTuning`, `src/color/ProresIspProfile.cpp:118-237`) rewrites only
`rpi.ccm`, `rpi.contrast` and `rpi.hdr.*.tonemap_enable` by byte-range edits and passes `rpi.denoise` through, so a no-tdn derivation can follow the same
pattern (Path 3a). Recipe (from the kb, tested on an IMX585 PiSP tuning):
`python3 -I -c "import json,sys;s,o=sys.argv[1:];d=json.load(open(s));[m.pop('tdn',None) for a in d['algorithms'] if 'rpi.denoise' in a for m in a['rpi.denoise'].values() if isinstance(m,dict)];json.dump(d,open(o,'w'),indent=4)" ~/Tuning-Files/defaults-pisp/imx585_clearHDR.json ~/Tuning-Files/imx585_clearHDR_notdn.json`
(and the same for `imx585.json` → `imx585_notdn.json`), then `printf '{"cmd":"set_tuning_file","path":"/home/pi/Tuning-Files/imx585_notdn.json"}\n' | socat - UNIX-CONNECT:/tmp/apertar-core.sock`.
Rule-out: if `be_cycle.py`'s S2 stays within 15 % of the TDN-on value, the BE is compute-bound or not the limiter (then C5/C6/C7 or Path 4).

**Why the SDR gain has a floor.** The idle BE figure (13.4 ms for 9.36 Mpx with re-read) bounds the BE's pixel throughput at ≥ 0.70 Gpix/s if that
time were all compute; 8.29 Mpx then needs ≈ 11.8 ms regardless of TDN. The byte model gives 2.5 ms idle for the TDN-off SDR BE, which is below that
floor, so the honest SDR estimate after T1 is "between 8 and 17 ms", inside 20 ms either way. The 60 fps pre-roll (cycle ≤ 16.7 ms with TDN probably on,
lossless, 2 s) says the TDN-on SDR cycle can already fit 60 fps in some conditions, which makes the recording-only DRAM traffic (D1, D7, K8) the
other suspect for the M3 loss; the E4 repeat decides.

**T2 versus T1.** `NoiseReductionMode` is in the IPA's control list (`ipa_base.cpp:85@c682979`) and the handler only distinguishes Off from everything
else (`ipa/rpi/pisp/pisp.cpp:557-572`). Off also drops SDN and CDN, so the preview is noisier than with T1, and the mid-stream switch leaves
`PISP_BE_BAYER_ENABLE_TDN` set (not in the per-frame clear mask) with its DMA disabled: an unverified hardware state. A knob that sets Off only while a
raw take runs is therefore the risky variant; a session-long Off is safe but then T1 does the same with better image. Verdict: build T1's automatic
derivation (Path 3a), not T2.

**K1/K7, the web preview.** `captureWebPreviewFrame` runs on libcamera's completion thread (`ApertarCoreApp.cpp:9366-9440@6ef0ddc`), gated on
`mjpegClientCount_ > 0` and now on `rawTakeActive()` × `webPreviewRecordingFps()` (`:9377`). Measured 0.2-0.5 ms/frame (V/H4), so alone it cannot
produce the 1.3-2.7 ms deficit of the short takes; it is a contributor and a cheap mitigation.

**K2/K3/K4, scheduling.** V/H15: nice −5 vs 0 under EEVDF gives tens to hundreds of µs expected and ≈ 2 ms tail per wake-up, only when all four cores are
busy (measured 59/44/48/38 % while recording ⇒ a few % of wake-ups). It cannot explain M3's 2.7 ms steady deficit; it is marginal for (B)'s single-frame
gaps. Per-thread FIFO (K2) is the right shape; whole-process FIFO (K3) is cinemate's shape and the wrong one for Core. `APERTAR_RT_CAPTURE_PRIORITY`
is set from `requestComplete` when the first frame arrives (`CameraController.cpp:8676-8705@6ef0ddc`) and falls back to nice −5 if refused.

**C1, buffers.** The CFE skips a frame when no raw buffer is queued at SOF; with N buffers and a steady deficit d per frame, the first skip comes after
≈ (N − buffers held by libcamera and Core) × period / d frames and then one skip per period/d frames (q5 §3.2 model; matches M3 and the 30 fps Clear HDR
gap pattern). Buffers move the first skip, never the rate. For a transient (first-seconds) deficit they can absorb it entirely: that is the one case
where `APERTAR_RAW_CAMERA_BUFFERS=12` could turn (B)'s short-take gaps into zero; it is a mask, not a fix.

**C5, pipelining (fork).** The gate is `state_ != Idle` in `tryRunPipeline` (`pisp.cpp:3112-3117@6b0b49f`); the kernel driver already keeps a two-slot
hardware queue. Depth 2 recovers at most the non-BE serial time (S1+S3+S4), and nothing if the BE hardware is ≥ the period. The verifier sized the
patch at 300+ lines with three traps. The IPA pixel-rate cap is not touched by pipelining and does not bind on this rig (the fork derives 646.7 Mpix/s
from the device tree; the M3 probe shows unstretched HMAX-550 lines, V/H1). Do it only if a `be_cycle.py` window shows ≥ 3 ms outside S2 with S2 below
the period, after T1.

**C7, preview off during a take.** libcamera supports a raw-only configuration (`beEnabled_ = false`, `pisp.cpp:2033,2377-2384@6b0b49f`): the BE never
runs and the raw buffer returns at once. Core would have to reconfigure at record start and stop (a mode switch of 45-110 ms plus the first frame and the
cadence gate), and the operator would lose the HDMI monitor and the web preview for the whole take unless Core renders a preview from the raw buffer on
the CPU/GPU (a new subsystem). It removes the largest stage but at a cost no cinema camera accepts; keep it as the last-resort diagnostic
(`cam -c1 -C300 -s role=raw,…` gives the BE-free ceiling without any Core change, q2 E3).

**D7, O_DIRECT.** The one writer-side lever backed by a measurement that isolates the mechanism: on 2026-10-26 with Core idle, a buffered `dd` to
`/media/RAW` cost 19 capture gaps in 3.4 GB while `dd oflag=direct` cost none (`clearhdr-design.md:120-127`). O_DIRECT straight from the camera buffer is
impossible (dma-heap mappings are `VM_IO|VM_PFNMAP`, GUP returns −EFAULT, q5), so it is copy + O_DIRECT from the pooled copy, which 6ef0ddc's direct
payload write already lines up (one `write()` from the copy). The T24 patch predates the copy worker and the direct write and must be rebased; exFAT
accepts O_DIRECT (the `dd` ran on it) but falls back to buffered silently on misalignment, so the patch's `APERTAR_CDNG_DIRECT_IO` log line must confirm
the mode per take.

`APERTAR_DNG_WRITEBACK=0` + `APERTAR_DNG_DONTNEED=off` + `APERTAR_RAW_CAMERA_BUFFERS=10` + `set_buffer_mode ram` + `APERTAR_MEDIA_TUNE=1` + swap off**;
of these only T1 acts on the serial cycle by a named mechanism of size; the others are worth ≤ 1-2 ms together or act on the queue-full class. There is no
counted cinemate take of either operator case (V/H9), and cinemate's own May 2026 table rated 4K 12-bit at 38 fps sustainable on CFE/NVMe exFAT.
