## 3. Errors found

- **E1 (arithmetic/model): L_max = N*T - R, not (N-1)T - R.** Kernel reading above. Corrected table: (A) 4 buffers **64 ms**, 8: **144 ms**, 16: **304 ms**; (B) 8 buffers **287 ms**, 16: **607 ms**. The verdict label does not move (one-off slack of ~2 periods at N=4 is still MARGINAL), but every number in §2.3's table and §3's buffer-count lever row is 20 ms (A) / 40 ms (B) too low. The report's cross-check against 217 ms used the right count and therefore contradicted its own formula.
- **E2 (wrong code reading): the FE Config queue is 2 deep, not 12.** `numCfeConfigQueue = 2` (default, overridable by `num_cfe_config_queue` in the pipeline YAML, `pisp.cpp:1381-1382`). The Config buffer for frame k is dequeued at EOF_k and re-queued only when libcamera's CameraManager thread handles that event (`cfeBufferDequeue` Config branch -> `prepareCfe`). Frame k+1 is covered by the second buffer; frame k+2's job needs the re-queue before SOF_(k+2), i.e. within **2T - R = 24 ms at (A), 47 ms at (B)** of EOF_k. The raw pool tolerates 64 / 287 ms. So the shallowest CFE queue is Config, not raw, and a single CameraManager-thread stall longer than ~24 ms at 50 fps starves the FE_CONFIG node and skips a frame with exactly the same dt = 2T signature. The report called Stats/Config "not binding (derived)" without this arithmetic. No measurement shows it firing (the 30 fps handlers were 6-13 ms), so it is a candidate mechanism for single skips under (A), not a demonstrated one. It is also a free lever the report missed (section 4).
- **E3 (miscite):** `CONFIG_DYNAMIC_DEBUG` statement is at `hardware-log.md:90`, not `:76`.
- **E4 (path):** the kernel directory in rpi-6.12.y is `drivers/media/platform/raspberrypi/rp1_cfe/` (underscore); the report's `rp1-cfe` 404s on raw.githubusercontent.com. Cosmetic, but anyone re-fetching will fail.
- No error found in: link arithmetic, sensor ceilings, RP1 cap figures, config.txt line 65, M3 exclusion of the cap, the raw-pool count (4/8 vs the answer page's 6/10), the env knob, the +33 MB cost, the PCIe share, the Log/release order, the pre-roll and probe citations.

## 4. What the report missed

1. **The Config node as a second starvation path** (E2). It does not change the stage verdict for (A) or (B) because no evidence shows it fires, but it belongs in §2.4's table and in the decisive-test plan: when the stage-1-only window shows a dt = 2T with the pipeline idle, the cause can be a late Config re-queue as well as a late raw return; `LIBCAMERA_LOG_LEVELS=RPI:0,RPiStream:0` logs the Config dequeue/queue events too. Lever: `num_cfe_config_queue: 4` (or more, up to 12 allocated) in the pipeline handler's YAML (`/usr/share/libcamera/pipeline/rpi/pisp/*.yaml`, line 18 shows the commented default `2` in upstream `pisp.cpp:1381` reads it), zero memory cost. Whether the Pi's qbc or L2 libcamera reads the same YAML key: the fork clone has the same code (`pisp.cpp:1630` default, `:2096` loop); the installed YAML is unverified.
2. **The corrected tolerance changes the lever table's numbers**, not its ranking: 4 -> 8 raw buffers buys 80 ms (64 -> 144) at 50 fps, still "zero gain against a mean deficit".
3. The 217 ms measurement is stronger evidence than the report makes of it: with the corrected count it reproduces the measured queue wait to ~1 ms, confirming that the pool was saturated and the loss at 30 fps Clear HDR was a mean deficit, which is the same argument used for M3.

## 5. Corrected verdict and margin

- **(A) 3840x2160 12-bit 50 fps, stage 1: INSIDE.** Sensor 60.0 fps measured at this size (+20 %); link 69.8 % (derived); RP1 518.4 of 646.7 Mpix/s (80 %, derived from fork code + two config.txt readings; live `clk_sys` unread); CFE DMA 23-25 % of the RP1 PCIe link (derived, web). Raw pool at 4: one-off lateness tolerance **64 ms** (about two periods beyond a 20-25 ms hold) -> MARGINAL as a jitter absorber; FE Config queue tolerance **24 ms** of CameraManager-thread stall -> the shallower of the two, unmeasured. Confidence: **probable** (the only measured delivery at this size is 2 s; 10-minute D-PHY integrity at 1782 Mbps on this board unverified; CSI-2 counters never read at 50 fps).
- **(A') 3840x2076: unverified**, as the report says.
- **(B) 3840x2200 16-bit 25 fps, Log on or off: INSIDE, measured** (two clean 10-minute takes). Pool tolerance **287 ms** (8 buffers), Config tolerance **47 ms**. Confidence: **measured** for the stage; Log does not touch the raw-buffer hold (code).
