## 3. Errors found

1. **(1) The R9-vs-pre-roll resolution is one-sided.** F2's A.4 says the byte model "over-predicts demonstrably" because the 34.6 ms recording figure is thread-contaminated. The contamination is real for the pre-L1 window (`hardware-log.md:195-199`). But the L2 window — the swap and stats on a worker, thread 34 % busy — delivered 26.3-28.2 fps, a cycle of 35.5-38.0 ms (`:225-233`), and q2 §5 derives t_HW ≈ 33.9-36.4 ms while recording from it (`q2-pipelining.md:139-143`). Scaled by bytes that is 17.1-18.3 ms of BE in SDR (+1.6 ms) = 18.7-19.9 ms, R9's bracket at its low end. F2 states this in A.1 ("unresolved") and then ranks R9 "wrong" in §1 and A.4 on the idle-scaled model. Correction: both numbers are models; neither can arbitrate; the record holds two measurements (M3 22.7 ms, pre-roll ≤ 17.5 ms) in different configurations, and that is all. The verdict label does not change; the confidence stays LOW and the sentence "the R9 figure of 19-23 ms was an over-prediction" should be withdrawn. Caveat on the L2 reading (q2 caveat 2): the thread's remaining ~12.6 ms per frame is unnamed and may still be serial; the L1-vs-L2 difference is not significant (p ≈ 0.14).
2. **(2) Pre-roll pool size.** F2 assumes the SDR default of 4 raw buffers. The unit's environment on 10-30 carried `APERTAR_RAW_CAMERA_BUFFERS=8` (`hardware-log.md:741`, "read back from the unit"), set by the `zz-ladder-buffers.conf` drop-in on 10-28 (`:591`); no entry records its removal. Probable 8 buffers ⇒ the bound is ≤ 17.5 ms, not 17.0 (slack ~5-6 frames, consistent with the HDR measurement of 3.6-6.4). Margin at 50 fps ≥ +2.5 ms (if it generalises). The fps-printing code and the "one skip prints 59.5" reading are correct (table row 6).
3. **(5) B margin.** +3.8 uses the pre-L1 cycle only. The L2 cycles (35.5-38.0 ms, same mode, same fps) give +2.0 to +5.3 ms. And the 25 fps cycle is not a constant: at 25 fps on f60e301 the lossless-encoder load pulled delivery to 19.3-22.4 fps (`hardware-log.md:64-78`: cycle 45-52 ms) and `dd` to tmpfs alone, Core idle, gave 22.77 fps (`:70`). Those are older builds (copy still on the thread, pre-L1) but they show the serial loop at 25 fps is DRAM/CPU-load sensitive, so "+4 ms, more with less DRAM load" has to be stated as "+2 to +5 ms at the A0 load (uncompressed, Log off, WebUI closed)". Nothing in the kb measures the 25 fps cycle itself (no RPI:0 window at 25 fps: `grep RPI:0 hardware-log.md` → lines 172, 180, 229 only, all 30 fps). No stage is known to scale with frame rate except the per-second DRAM and writer traffic (25/30 = 0.83 ×); AGC/AWB statistics run once per frame regardless.
4. **(6) Memory-bound evidence.** F2 names "memory-bound" as its weakest assumption and offers none. Two measured items bear on it, both in the kb: (a) the L2 result — BE time inferred 2.5 × idle with the thread free, same pixel count, only the DRAM load changed; a compute-bound BE would stay at 13.4 ms; (b) T22's `dd` to tmpfs (memory traffic, no NVMe) cost frames at 25 fps idle while direct I/O did not (`hardware-log.md:70-78`). Both support contention-sensitivity of the serial loop; neither isolates the BE from the thread. No measurement separates them (be_cycle.py S2 with TDN on vs off would). Label: memory-bound = probable, not confirmed; the AXI QoS 0 write is confirmed (`PISP_BE_AXI_REG = 0x32703200`, comment "AXI QOS=0", kernel web read), its effect unverifiable.
5. **(TDN-off B row)** internally inconsistent (table row 18); the stated −10 to −20 ms is inside the plausible envelope (−12 to −23 memory-bound, 0 compute-bound) but the shown derivation does not produce it.
6. **(3) `APERTAR_TUNING_FILE`.** F2's code reading is right: the variable read is **`LIBCAMERA_RPI_TUNING_FILE`** (the start script maps `APERTAR_TUNING_FILE` to it, `start-apertar-core.sh:16-17`), under the condition `settings_.tuningFile.empty()` after `loadPersistedCaptureSettings` (`CameraController.cpp:10077-10080`), i.e. whenever the persisted `tuning_file=` is empty (automatic selection, the default state). It is dead only when a non-empty tuning file is persisted. Two consequences F2 omits: (a) the adopted path becomes `settings_.tuningFile` and is written by `persistSettingsLocked` on the next save of any setting (`:886` writes `tuning_file=` unconditionally) — the env choice **sticks** after the variable is removed, until the UI/socket selects "automatic" (empty path) again; (b) a non-empty `settings.tuningFile` disables the automatic `_clearHDR` substitution (`:6981-6990`), so an env-selected `imx585_notdn.json` is used in Clear HDR too (the same pitfall F2 notes for `set_tuning_file`). UI side: the UI sends `set_tuning_file` only on a user action (`ApertarControlBridge.cpp:582`), mirrors Core's `tuning_file` state (`:1673-1674`) and stores it in QSettings `camera/tuningFile` (`:1080, 1135`); it does not push a saved selection at start. **The answer page must be corrected**: `working/dng-chain-answer.md:35,208`, `STATUS.md:111`, `V/VERDICTS.md` H2 say "APERTAR_TUNING_FILE is dead: Core overrides it at start". Correct text: "`APERTAR_TUNING_FILE` (→ `LIBCAMERA_RPI_TUNING_FILE`) selects the tuning when no tuning file is persisted (the default); a persisted selection wins over it; the env-selected file is used as given in SDR and Clear HDR alike and is persisted at the next settings save. `set_tuning_file` / the UI picker select at runtime with a reconfigure. Check which is in effect with `journalctl -u apertar-core -b | grep -i tuning` and `grep tuning_file` in the persisted settings file."
7. **(4) `NoiseReductionMode=Off` runtime caveat is weaker than stated.** The TDN enable bit does stay set (`pisp.cpp:365-368` clears only TDN_OUTPUT/INPUT), but the kernel's `pispbe_xlate_addrs()` clears the TDN enable bits when no TDN input buffer address is present, and `pispbe_prepare_job()` ignores the TDN nodes when their enable bits are clear (web read, rpi-6.12.y). So a runtime toggle is driver-handled, not an undefined hardware state; F2's open question 7 can be closed as "probable: clean". Set-at-start remains the simpler path.
8. **(7) 8 buffers / `disable_tdn`.** Both hold (rows 16-17). Addition: the kernel code confirms the stall mechanism (an enabled node without a buffer ⇒ `-ENODEV`, no job), as q1 row 41 inferred.
9. Minor: "10 camera commits, nothing on the completion path" (row 20); A0 and A1 ran on `a40112a`, which F2 states correctly, but the 10-31 short takes ran on pre-squash builds (V/H16), not "the current code" — F2 does not claim otherwise, but its §1 phrase "the only observation on the current code" (the pre-roll) is right only because d44b177 is the squash of those builds.

## 4. What the report missed that changes the verdict

Nothing that flips a label. Three items change the stated numbers or confidence:
- The L2 datum as the counter-model for (A): the SDR TDN-on cycle estimate is 10-14 ms (F2) **or** 19-20 ms (R9/L2 scaling); the pre-roll excludes ≥ 17.5 ms in its configuration, which favours the low model or TDN off, but the pre-roll was 1.9 s, lossless, 2160, probably WebUI open. The (A) answer stays "measure it".
- The pre-roll's probable 8-buffer pool (bound 17.5 ms).
- The 25 fps load-sensitivity measurements (T22) for (B): the margin is a property of the A0 configuration, and Log (+0.73 GB/s) or an open WebUI may consume it (the 10-31 Log sample lost 7.9 %).

## 5. Corrected verdict and margin

- **(A) 4K SDR 12-bit 50 fps: MARGINAL, bracket −2.7 ms (M3, measured-derived) to ≥ +2.5 ms (pre-roll bound ≤ 17.5 ms, measured-derived, 1.9 s, 60 fps, 2160 lossless, probably 8 buffers), confidence LOW.** The model estimates (10-14 vs 19-20 ms) disagree and cannot arbitrate. TDN off: probably inside (memory-bound reading), unmeasured; no number with confidence above LOW. Decisive test unchanged: `be_cycle.py` at 50 fps for ≥ 60 s on 6ef0ddc, 4 and 8 buffers recorded, tuning `tdn` grep first.
- **(B) 4K Clear HDR 16-bit 25 fps, Log off: MARGINAL-INSIDE, +2.0 to +5.3 ms at the A0 load (derived from the 30 fps L1/L2 cycles), 10-minute clean takes measured twice (A0, A1), confidence MEDIUM.** With Log: UNVERIFIED (one 127-frame sample, 7.9 % lost, WebUI open). TDN off: inside by a further 12-23 ms if memory-bound (probable), 0 if compute-bound; one TDN-off be_cycle window settles it.
- Corrections to carry into the answer page: the `APERTAR_TUNING_FILE` statement (§3.6); the runtime `NoiseReductionMode=Off` caveat (§3.7); the pre-roll buffer count; and "R9 over-predicted" should read "R9's and F2's SDR models bracket the budget; only a measurement decides".
