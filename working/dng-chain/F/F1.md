### 2.2 RP1 pixel-rate cap

Mechanism (code): the PiSP hardware entry sets `minPixelProcessingTime = 1.0us / pispPixelRateMpixPerS()`; the fork reads the *requested* `RP1_PLL_SYS` from `/sys/firmware/devicetree/base/axi/pcie@1000120000/rp1/clocks@18000/assigned-clock-rates`, snaps it to 1 GHz / N and returns `2 x clk - 20` Mpix/s, falling back to 380 when the node is missing or the value implausible (`src/ipa/rpi/controller/controller.cpp:59-152@6b0b49f (clone)`; identical in the installed 7e9fef0 per q6 §4.1). Upstream has a fixed `1.0us / 390` and the comment "rate of pixels going from CSI2 peripheral to ISP-FE (400Mpix/s ...) ... a 64kbit data FIFO before the bottleneck" (`src/ipa/rpi/controller/controller.cpp:64-78@c682979`). `IpaBase::setMode` stretches the minimum line length to `minPixelTime x width` when the sensor's pixel time is shorter and logs "Adjusting mode minimum line length ... because of ISP constraints" (`src/ipa/rpi/common/ipa_base.cpp:612-640@c682979`; fork `:612-628@6b0b49f (clone)`).

When exactly the CFE skips a frame (kernel `rpi-6.12.y drivers/media/platform/raspberrypi/rp1_cfe/cfe.c`, **web**, approximate lines):

- A job (CSI2 DMA addresses and, in FE mode, the FE output/stats/config addresses) is prepared only when **every enabled node** has a buffer in its `dma_queue`: `cfe_check_job_ready()` iterates the nodes and returns false with `cfe_dbg_verbose("%s: [%s] has no buffer, unable to schedule job\n", ...)` (~611-629). Verbose debug is compiled out on the Pi's kernel (`CONFIG_DYNAMIC_DEBUG` not set, `hardware-log.md:76`), so the line is never visible.
- `cfe_prepare_next_job()` sets `job_queued = true`, programs the next CSI2 buffers (`cfe_schedule_next_csi2_job`: `node->next_frm = buf; list_del(&buf->list); csi2_set_buffer(...)`) and, in FE mode, `pisp_fe_submit_job()` which writes the output DMA addresses and `FE_CONTROL_QUEUE` (~631-642; `pisp_fe.c` ~265-330). It is called from two places: when user space queues a buffer (`cfe_buffer_queue`: `if (!cfe->job_queued && cfe->job_ready && test_all_nodes(...)) cfe_prepare_next_job(cfe)`, ~480-500) and at the end of each node's SOF/EOF handling in `cfe_isr` (`if (!cfe->job_queued && cfe->job_ready) cfe_prepare_next_job(cfe)`, ~690-700).
- At frame start the queued job becomes the current one (`node->cur_frm = node->next_frm; node->next_frm = NULL; node->fs_count++; node->ts = ktime_get_ns()`; once all nodes have seen the FS, `cfe->job_queued = false`, ~677-719). If at that FS no job was queued, the hardware has no output address for that frame: the frame is not written anywhere and no buffer completes for it. The driver has no comment saying "frame dropped"; the inference is from the mechanism (no `next_frm`, nothing to complete). **Probable.** The `fs_count` still increments, so the next completed buffer carries a sequence two higher and a SOF timestamp 2T later; that is the `dt = 2 x period` gap Core counts (R7 §3.1 b).
- So the rule is: **the CFE needs one raw buffer (plus a stats and a config buffer) queued at every frame start.** Stats and Config have 12 each and are returned early, so the raw pool is the binding one (derived).

What the pool depth buys and what it cannot (derived model; uses R = readout, T = period, L = time from the frame's EOF until Core requeues its buffer, i.e. IRQ -> `cfeBufferDequeue` -> wait for `Idle` -> IPA -> BE -> `beInputDequeue` -> `requestCompleted` -> Core callback -> copy worker memcpy -> `requeueRequest`):

- A buffer is out of the pool from its SOF to its requeue, R + L. With N buffers the pool runs dry at a frame start when the oldest in-flight buffer is still out after N-1 further frame starts: **the pool survives one late return of up to L_max = (N - 1) x T - R**.

| Mode | N | L_max | Typical L when the cycle keeps up (cycle + ~2-3 ms copy) | Spare |
|---|---|---|---|---|
| (A) 50 fps, R = 16.0 ms | 4 | 3 x 20 - 16 = **44 ms** | 20-25 ms | about one frame period of jitter, once |
| (A) | 8 | **124 ms** | | ~5 periods |
| (A) | 16 (env max) | **284 ms** | | ~13 periods |
| (B) 25 fps, R = 32.6 ms | 8 | 7 x 40 - 32.6 = **247 ms** | 38-45 ms | ~5 periods; consistent with the **measured** 217 ms queue wait when the pool saturated at 30 fps (`hardware-log.md:189`: 8 x 33.3 - 32.6 = 234 ms predicted) |
| (B) | 16 | **567 ms** | | ~13 periods |

- A deeper pool therefore absorbs **transients**: a single late cycle, a scheduling stall, a slow first frame after a reconfigure, up to L_max in total lateness, and it moves the first gap of a *steady* deficit later: first gap after about (N - 3) / ((Pp - T) / T) frames, then one skip every T / (Pp - T) frames, delivered rate 1 / Pp whatever N (q5 §3.2 model, checked there against the 30 fps measurements: first gap after 27-47 frames, one every 5-9).
- It cannot buy a mean cycle longer than the period: once Pp > T the queue grows one buffer every T / (Pp - T) frames until the pool is empty, and from then on exactly one frame is skipped per T / (Pp - T) frames.
- **T34 M3 unchanged from 4 to 8 buffers** (2632 vs 2616 of ~2980, `hardware-log.md:582-595`): delivered 44.0 fps -> Pp = 22.7 ms -> one skip every 7.4 frames -> 355 per 60 s, matching 355 / 358 (derived). This proves the loss was a **steady rate deficit, not jitter and not pool size**: the 8-buffer run only moved the first gap from ~7 to ~37 frames in. It does **not** by itself locate the deficit: a sensor or link that silently loses one frame in 7.4 would be equally buffer-independent. The evidence that it is the cycle, not stage 1, is indirect: the same single-regular-gap signature was measured together with a 36.2 ms cycle at 30 fps Clear HDR (`hardware-log.md:186-196`), the 3840x2160 60 fps pre-roll delivered every frame for 2 s, and 1080p50 was clean (`:595`). For 3840x2076 specifically, no stage-1-only run exists (section 4).

Build 6ef0ddc and (B) with Log: the copy worker does `dmabufCpuSync` -> `memcpy` -> `dmabufCpuSync` -> `releaseHeldRequest(copy.request)` and only then the Log LUT or `compressClearHdrFrame` (`CameraController.cpp:4864-4892@6ef0ddc`), so the raw buffer's hold time L is identical with and without Log (confirmed from source). Log's extra DRAM traffic (R8: +33 MB/frame) can lengthen the cycle; that is the F2/F4 stage, not this one.

## 4. What would settle it on the Pi

The decisive measurement for this stage is a **stage-1-only window**: Core running, **not recording**, 60 s in each mode, with libcamera's per-frame debug on, then count the CFE frame-start timestamps.

1. Drop-in on `apertar-core.service`: `Environment=LIBCAMERA_LOG_LEVELS=RPI:0,RPiStream:0` (the `libcamera-debug.conf` used 2026-10-26), restart Core. Set the mode (3840x2160 12-bit 50 fps; then 3840x2076; then Clear HDR 16-bit 25 fps), WebUI closed, wait 10 s.
2. `journalctl -u apertar-core -o cat --since <t0> --until <t0+60s> > /tmp/f1_<mode>.log`, then `python3 -I working/tools/be_cycle.py /tmp/f1_<mode>.log` (its `cfe` event is `Stream CFE Image buffer dequeue, buffer id N, timestamp: T`; T is the kernel SOF `ktime_get_ns()`). Pass: frame count = 60 x fps +/- 1 and every consecutive T difference = period +/- 0.05 ms (3000 frames at 20.000 ms; 1500 at 40.000 ms). Any dt = 2T here, with the pipeline idle, is this stage's fault (or an idle cycle longer than the period, which `be_cycle.py` shows as `cycle`).
3. Alongside, once per boot: `sudo cat /sys/kernel/debug/clk/clk_sys/clk_rate` (expect 333333333); `journalctl -u apertar-core -b | grep -E 'pixel-rate cap|Adjusting mode minimum|IMAGE CORRUPTION'` (expect `646.667`, no Adjusting line); `grep -o 'rp1_cfe[^ ]*' /proc/cmdline`; `sudo dmesg | grep -E 'DPHY|link rate|imx585.*(VMAX|HMAX)'`.
4. Then the same 60 s **recording** in each mode with `sudo sh -c 'cat /sys/kernel/debug/rp1-cfe*/csi2_errors'` read immediately before and after (requires `rp1_cfe.track_csi2_errors=1`), and `sudo dmesg | grep -c Orphanded` before and after. If gaps appear only while recording and the counters stay 0 and no Orphanded line appears, stage 1 is cleared for that mode and the skips are the pool running dry behind the cycle (F2's stage, `be_cycle.py` S1-S4 on the same log).

Record with every run: WebUI clients (0), speed ramp state, trim state and time since trim, pre-roll state (`storage_preroll_last`), the tuning file in the journal (`tuning file`), whether it is the first take after a reconfigure, `get_throttled`, and `APERTAR_RAW_CAMERA_BUFFERS` as read back from the unit. Minimum duration 60 s idle per mode; the 10-minute question for (A) (D-PHY integrity at 1782 Mbps) needs one 10-minute idle window at 4K50 with the same count.

## 5. Open questions and claims not verified

- Live `clk_sys` on the Pi (333.33 / 200 / 166.7 MHz) and the overlay's entry 7: never read (q6 E1). The fork trusts the DT request.
- Whether `rp1_cfe.track_csi2_errors=1` survived the later reboots; CSI-2 counters at 4K 50 fps SDR and at 30 fps uncompressed Clear HDR were never read.
- 3840x2076 crop-mode timing at 50 fps with the pipeline idle: never measured; the driver branch that defines the crop modes (`cinemate-port`, DKMS) is not readable here, so VMAX_min 2148 is derived from the probe's 62.85 fps.
- One 16-bit row per 2H in Clear HDR (q6 §1.2): probable from the driver's VMAX doubling and the link arithmetic; the Sony datasheet or q6 E3 (SOF-to-dequeue minimum ~32.6 ms) would confirm.
- D-PHY integrity at 1782 Mbps over 10 minutes at 70 % utilisation on this board: no counter covers CRC/ECC; only `Orphanded` WARNs and image checks can show it.
- Which libcamera is active now: the system qbc `7e9fef0` (hardware-log 2026-10-26 22:xx entries) or the L2 `6b0b49f` drop-in loaded at 21:10 that day. For this stage the two are identical except where the 16-bit swap runs (L1 on the pipeline thread holds the raw buffer 6-10 ms longer before the job is complete).
- The journal line `PiSP pixel-rate cap = 646.667 Mpix/s` has been described but never captured verbatim in the kb.
- `dng-chain-answer.md` §2.2 states "CFE pools of 6 and 10 with libcamera's two internal buffers"; the code says 4 and 8 (section 2.3). The conclusion there (buffer-independent loss) is unchanged.
