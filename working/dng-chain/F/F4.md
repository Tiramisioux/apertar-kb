What the queue holds is not the file: the raw copy, i.e. 8.29 MB COMP1 per 4K SDR frame (7.97 MB at 2076 rows) and 16.59 MB per Clear HDR frame (Log is applied in place, so still 16.59 MB) (R8 §4, confirmed from `CameraController.cpp` copy path). exFAT metadata per frame file, **derived** from the 6.12 driver (`exfat_raw.h` DENTRY_SIZE 32; name entries of 15 UTF-16 chars; V/H14 §1 #7):
- Directory: Core's default frame name `cDNG_26-10-28_C0001_000000123.dng` is 33 chars (`frameFilename`, `CameraController.cpp:4968-4975@6ef0ddc`) → 1 file + 1 stream + 3 name entries = **5 dentries = 160 B**; the directory grows one 128 KiB cluster per 819 files (4,096 dentries per cluster).
- Allocation bitmap: one bit per cluster → 95–127 bits per file; the bitmap (≈ 0.94 MB) is pinned in RAM at mount (R6 a21).
- FAT: with four concurrent writers every frame file becomes a FAT chain at its second cluster (V/H14 C1, `fatent.c` `if (new_clu != hint_clu && flags == ALLOC_NO_FAT_CHAIN)` → `exfat_chain_cont_cluster`, re-read on rpi-6.12.y this session), so 95–127 x 4 B = 380–508 B of FAT entries per file.
- Total metadata bytes ≈ 0.6–0.7 KB per frame = **< 0.01 % of the data**: metadata **bandwidth** is not a budget item. Its **I/O operations** are: dirty FAT blocks ≈ bytes/s ÷ 16 MiB (one 512-B FAT block covers 128 clusters) → **37 blocks/s at 622 MB/s, 25/s at 415**; the same number of **cold synchronous 512-B FAT reads** per second on the allocating writer thread (V/H14 C2; `exfat_ent_set` → `sb_bread`); 50 (A) or 25 (B) directory-sector writes per second from the 1 s fsync; 1–2 bitmap blocks per second. All written out by `sync_blockdev` inside each fsync (R6 a8).

Does 622 MB/s for 10 minutes (373 GB) fit? **Arithmetic says barely; no measurement says yes.**
- Against the link + controller as measured in cache: 733 − 622 = **+111 MB/s (15 %)**; 759 − 622 = +137 (18 %).
- Against the only buffered measurement: 556 − 622 = **−66 MB/s**. That `dd` was one thread with the kernel's single flusher behind it; Core's four writers each start their own writeback (`posix_fadvise(DONTNEED)` and `sync_file_range` run writeback in the caller, R6 e2, H3), so Core's path should land between 556 and 733 — **unverified**.
- Against the NAND after the pSLC (from ≈ 90 s into the take to the end): ≈ 800 MB/s post-cache is above the link, so the link stays the wall **if** that snippet figure applies to this unit; a post-cache rate below 622 would make (A) fail from minute 2 onward with a full queue (drop[queue-full]).
- Volume: 373 GB per take is 40 % of the 917 GiB volume; 2.5 takes walk the allocation cursor around the whole volume once (the 0.9 TB mark); Core's trim at mount and after deletes (incl. deletes made outside Core, `04bac89@6ef0ddc`) is what keeps the wrap harmless (HL:701-733).

**Directory create cost vs. the frame period (the arithmetic asked for).** The create scan is one pass over N x 5 dentries, each dentry a buffer-cache hit (`exfat_get_dentry` → `sb_bread` → per-CPU bh LRU hit for 15 of 16 entries, slow path every 16th, type check, `brelse`). Per-dentry cost **c ≈ 80–250 ns** on a Cortex-A76 at 2.4 GHz (**estimated**, V/H14 §4.2; R6 C-a4 says 100–200 ns; **nobody has measured it**; this constant is the weakest assumption of this whole section).

| (A) 10 min 50 fps | 30,000 | 150,000 | **12–38 ms** | 6–19 ms |

Which budget does it fall under? Not the four writers' 4 x 20 ms = 80 ms aggregate: the scan runs under **`s_lock`, a single mutex that every writer's `exfat_get_block` also needs once per 512-B block** (F1, F6). So the budget is the **serialised** one: per frame period, `s_lock` must carry one create scan + 24,300 block mappings + (every 20th frame) one synchronous dentry write of the fsync thread, in **20.0 ms** at 50 fps / **40.0 ms** at 25 fps.

## 4. What would settle it on the Pi

The storage question for (A) can be settled **without the camera** (the capture side may block 50 fps regardless): Core stopped, drive trimmed (`sudo fstrim -v /media/RAW`), drive cooled to ≤ 40 °C, WebUI closed, nothing else running.

**Step 1 — the drive's sustained curve on this link (10 min).** `sudo fio --name=w --filename=/media/RAW/fio.bin --rw=write --bs=1M --direct=1 --iodepth=32 --numjobs=1 --size=400G --write_bw_log=/home/pi/fio_w --log_avg_msec=1000` (Core's own `run_media_speed_test` is the same fio with `--size=1024M`, `ApertarCoreApp.cpp:10349-10358@6ef0ddc`: a 1 GiB in-cache burst, useless here; pass a large `testMiB` or run fio by hand). Record every second: the fio bandwidth log (the pSLC knee, expected at 50–70 GB ≈ 90 s, and the plateau after it), `/sys/class/nvme/nvme0/hwmon*/temp1_input` (or `nvme smart-log /dev/nvme0 | grep -i temp`), `/sys/block/nvme0n1/stat` deltas (write sectors, write ticks, in_flight, flush_ios/flush_ticks), `lspci -vv -s 0000:01:00.0 | grep LnkSta` before and after (8 GT/s x1 throughout), `dmesg -w` for nvme/pcie lines. **Pass for (A): plateau ≥ 700 MB/s for the whole 600 s with no thermal dip.** Minimum duration 10 min: the knee is at ~1.5 min, the thermal plateau at 5–10 min.

**Step 2 — the real file pattern (10 min).** The kb's harness `/home/pi/ab-tests/variant2.py` (4 writer threads, one folder, 12-deep queue, per-file timing; HL:704-706) at **50 files/s x 12,443,140 B**, 600 s, trimmed drive, logging per-file open/write/close latency vs file index, queue depth, `iostat -x 1 nvme0n1` (w/s, wMB/s, `r/s` = cold FAT reads ≈ 37/s expected, `w_await`, `aqu-sz`), drive temperature. **Pass: 50 files/s held for 600 s, queue never above 6/12, per-file latency at file 30,000 no worse than at file 1,000 by more than 10 ms.** The slope of open latency vs index ÷ 5 gives the per-dentry constant c (V/H14 §6.4); a 10-minute Python loop creating 30,000 empty files `cDNG_26-11-01_C0001_%09d.dng` gives c alone.

**Step 3 — the counted Core take (if the capture side permits 50 fps).** `takes.sh 1 600` at 3840x2160 12-bit uncompressed 50 fps, trimmed drive, WebUI closed, speed ramp off, pre-roll state recorded; read `ApertarCore recording stats:` (`peak_queue=`, `dropped_queue_full=`, `write_failures=`, `dropped_copy_slot=`; in RAM mode `queue_bytes_peak=`/`queue_budget=`, `CameraController.cpp:4310-4324@6ef0ddc`), `ApertarCore capture stats: dropped_gap_estimate=`, the stop-time `synced to the medium in N ms`, frames written vs WAV seconds x fps. **Core logs no per-file write-time histogram for uncompressed cDNG** (only the lossless path has `max_wall_ms`), so per-file latency comes from step 2 or from `strace -T -f -e trace=openat,close -p <core pid>` on the writer threads / `bpftrace` on `exfat_find_dir_entry`. Repeat once in RAM mode and once with `APERTAR_DNG_DONTNEED=sync`.

Record alongside, for every step: `blockdev --getss /dev/nvme0n1p2` and `dump.exfat /dev/nvme0n1p2 | grep -iE "sector|cluster"` (the 512-B sector assumption behind F3), `sudo nvme id-ctrl /dev/nvme0 | grep -E "^mn|^fr|vwc|hmpre|hmmin"` (E27T identity, volatile write cache → whether fsync sends FLUSH), `cat /sys/block/nvme0n1/queue/write_cache`, `findmnt /media/RAW`, `media_trim_last_unix` from `/api/state`, drive temperature at start and peak, WebUI clients (`ss -tnp | grep 8000`), `fps_speed_ramp`, `storage_preroll_last`, the tuning file in use, whether it is the first take after a reconfigure, `swapon --show`, `grep -E "Dirty|Writeback" /proc/meminfo` at 1 Hz.

## 5. Open questions and claims I could not verify

1. The MP600 Mini (E27T, FW ERFM11.1) post-pSLC write rate **on this x1 link**: the ≈ 800 MB/s figure is a search snippet of a review on a Gen 3 x4 host; the 1 TB E27T's cache size is not in any reachable source (49 GB for the 2 TB sibling). Step 1 settles it.
2. Whether Core's buffered 4-writer exFAT path reaches the direct-I/O 733 MB/s or stays near the buffered `dd`'s 556: never measured above 525 MB/s. Step 2/3.
3. The per-dentry cost c (80–250 ns estimated) and therefore whether the create scan overruns the 20 ms period before minute 10 at 50 fps. V/H14 §6.4 loop.
4. The exFAT sector size of the volume (512 vs 4096 changes every `s_lock`/FAT count 8x). `blockdev --getss`.
5. Whether the drive advertises a volatile write cache (vwc) — decides whether the 1 s fsync sends 50 FLUSH/s — and what a FLUSH costs on it. `nvme id-ctrl`, `/sys/block/nvme0n1/stat` flush fields.
6. Drive temperature and throttling behaviour behind the CFexpress hat at 622 MB/s for 10 min (only 415 MB/s runs exist: 54 °C after 10 min cold, 60–72 °C back-to-back).
7. Whether the PCIe link holds 8 GT/s and the controller stays up for 10 min at 85 % utilisation (two Gen 3 controller drops on 2026-10-26; `errors=remount-ro` would end the take at the first I/O error).
8. The 4 GB board's memory headroom with `buffer=ram` (1.4 GiB) plus the camera's CMA buffers during a long take.
9. The speed-ramp setting during A0–A2 (probably ON during A2, V/H16): the A0/A1 "clean" readings stand (frames written = fps x s), but every future reading must record it.
10. Whether anything lists the live clip folder during a take (touch UI clip list): a 150,000-dentry `readdir` slices `s_lock`.
11. **A kb claim that does not hold on this kernel:** `dng-chain-answer.md` §5.2 says exFAT direct I/O "silently falls back to buffered" unless the file is extended first (`i_size_aligned`). The rpi-6.12.y `fs/exfat/inode.c` fetched this session has no `i_size_aligned` anywhere and `exfat_direct_IO` ends in `return ret` with no fallback branch; the write branch only updates `valid_size`. The alignment constraints stand; the preallocation requirement does not (it remains useful for contiguity).
12. The web hosts for drive reviews (tomshardware.com, techpowerup.com, computerbase.de, tweaktown.com, pcworld.com, igorslab.de, guru3d.com, phison.com) are blocked in this session; every drive figure above marked **web (snippet)** should be re-read from the page when a session can reach them.
