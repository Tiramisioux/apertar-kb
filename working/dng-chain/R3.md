## 3. One DNG on disk — confirmed (CE)

Open flags (uncompressed): `O_WRONLY | O_CREAT | O_TRUNC [| O_CLOEXEC]`, mode 0644 (CE:1749-1754). No `O_DIRECT`, no `O_SYNC`, no
`fallocate`, no `fdatasync`/`fsync` anywhere in `src/cdng` (grep: the only fadvise lines are CE:1759 SEQUENTIAL and CE:1780 DONTNEED;
`O_DIRECT`/`fallocate` have no hits in `src/`). The kb patch `0001-cdng-direct-I-O-*.patch` (T24) was never applied: MP:144 says so and
the branch has no `APERTAR_CDNG_DIRECT_IO`.

Layout (IFD **last**): 8-byte TIFF header pointing at `ifdOffset = align4(8 + payload)`; strip at offset 8; 0-3 pad bytes; main IFD +
Exif IFD in one buffer (CE:1387-1392, 1771-1778). No header rewrite for uncompressed (the payload size is known before the header is
written). Lossless: 8-byte zero placeholder first, strips, then `pwrite` of the real header at offset 0 (CE:1277, 1764). MLV patches 4
bytes at close (kb a4 §1c; unchanged on this branch per `git log -- src/mlv`? not re-read: unconfirmed, low relevance).

Chunking (CE:1869-1873): `chunk = max(rowBytes, min(4 MiB, max(256 KiB, rowBytes × 64)))`. For every 4K row size in use the inner
term `rowBytes × 64` lies between 256 KiB and 4 MiB, so the chunk is always **64 rows** and the number of payload writes depends only on
the row count: `ceil(2160/64) = 34` (`ceil(2200/64) = 35` for a 2200-row crop).

## 4. Writeback initiations per frame and the kernel-side cost — probable (kernel sources not re-read)

Order on the writer thread per DNG: data writes → `posix_fadvise(fd,0,0,DONTNEED)` (CE:1780) → `close` (CE:1781) → `open(path)` +
`sync_file_range(fd,0,0,SYNC_FILE_RANGE_WRITE)` + `close` (CC:4504-4510).

| Call | What 6.12 does (probable) | Writeback initiated? |
| --- | --- | --- |
| `fadvise(DONTNEED)` on the just-written, still-open file | `__filemap_fdatawrite_range(WB_SYNC_NONE)` over the whole file: every dirty page (4,050 at 16-bit, 3,038 at Log 12) is tagged writeback and submitted as bios from the writer thread; then `lru_add_drain()` (local), `mapping_try_invalidate` — fails for every page now under writeback — then **`lru_add_drain_all()`** (queues one work item on every CPU that has LRU pagevecs pending and waits for all) and a second `invalidate_mapping_pages` that fails the same way. The pages stay in the page cache as clean pages once the I/O completes and are reclaimed later by the LRU, so DONTNEED frees nothing promptly here. | **Yes: the whole file, once.** |
| `close` | exFAT has no flush/writeback on release (`exfat_file_release` only trims the on-disk-size bookkeeping) | No |
| `sync_file_range(WRITE)` | `__filemap_fdatawrite_range(WB_SYNC_NONE)` again; with no dirty-tagged pages left it is a tag-scan no-op | **No new pages; redundant after DONTNEED** |
| sync thread `fsync(file)` (default on) | `exfat_file_fsync` = `__generic_file_fsync` (waits for that file's data writeback to complete, writes its directory entry set) + `sync_blockdev(sb->s_bdev)` (all dirty metadata buffers: bitmap, FAT, directories) + `blkdev_issue_flush` (**an NVMe FLUSH**) | metadata + device flush per file |
| sync thread `fsync(dir)` | same path on the directory inode | one more flush per second |

Counts: **25 full-file writeback bursts per second at 25 fps, 50 at 50 fps**, each 16.6 MB (12.4 MB Log 12; ≈ 7.5 MB lossless),
submitted every 40 ms (20 ms) from one of the 2-4 writer threads; the same number of `lru_add_drain_all` calls → **100 (200) per-CPU
work items per second on a 4-core Pi**, each a kworker wake on every CPU including the one running libcamera's thread; writers run
these concurrently (`lru_add_drain_all` serialises callers on its own mutex, so a second writer waits for the first's drain). With
the sync thread on (A0 default): **26 device FLUSHes per second at 25 fps, 51 at 50 fps** (probable). Peak dirty memory measured
3-11 MB (HL:745, 763): the per-frame DONTNEED keeps the dirty cushion empty, so `vm.dirty_*` knobs barely matter for Core (section 9).

cinepi-raw's removed DONTNEED (b71ec67, 2026-03-06) sat **before** its single `write()`, on an empty file
(`/home/user/tiramisioux/cinepi-raw/cinepi/dng_encoder.cpp:989-995@b71ec67^`: SEQUENTIAL, NOREUSE, DONTNEED at 989-991, `write` at 995):
it never wrote anything back — **confirmed**, so the orchestrator's note holds. cinepi-raw today initiates no writeback itself: the
kernel flusher does it when `dirty_background_bytes` (256 MiB tuned, cinemate) is reached, in bursts.

Consequence for the kb's A2 reading (HL:757-776, PP:40): A2 removed only `sync_file_range` and kept DONTNEED. If 6.12 behaves as above,
A2 removed a redundant call and the 10 % capture loss cannot be "the writeback hint"; the kb itself says "one run" and "the mechanism
inside the kernel is not measured". The 2026-10-31 short takes lost 2-10 frames at capture with the hint on (HL:778-792). **Status of
the kb claim "the per-frame writeback hint keeps the CFE from stalling": unconfirmed** (one run; contradicts the code reading).

## 7. exFAT specifics — confirmed layout, probable kernel costs

- Clip layout: **one directory per clip, every frame in it**: `folderPathString_ + "/" + frameName`, `frameFilename` =
  `<clip>_<9 digits>.dng` (CC:4678-4689, 4898-4905). Default clip name `cDNG_26-10-28_C0025` (19 chars) → file names of 33 chars.
- exFAT entry set per file (probable, exFAT spec): file dentry + stream dentry + `ceil(33/15) = 3` name dentries = 5 × 32 B = **160 B**.
  10-min take at 25 fps = 15,000 files → **2.34 MiB directory** (19 clusters of 128 KiB); at 50 fps 30,000 files → 4.7 MiB.
- Lookup cost (probable, fs/exfat has no directory index): `open(O_CREAT)` of a new name scans the directory to prove absence
  (`exfat_find_dir_entry`, name-hash compare per entry set): O(N) per create → Σ 160·N over a take ≈ **18 GB of cached directory bytes
  scanned per 10-minute take**, ≈ 1.5 ms per lookup at the end. The kb's synthetic folder-layout test found sub-folders of 500-2500
  files "did not matter" (PP:39), so this is not the measured bottleneck; it does scale with take length.
- Allocation (probable): 16.6 MB / 128 KiB = **127 cluster allocations per frame** (97 at Log 12), bitmap bit sets in memory; FAT chain
  entries (`exfat_ent_set`) only when the clusters are not contiguous — the stall stacks showed `exfat_alloc_cluster > exfat_ent_set >
  __bread_gfp`, i.e. FAT-chained files on a fragmented free space (brief digest). Fragmentation after many takes/deletes is
  **unconfirmed**: `sudo filefrag -v <dng>` on a late clip would settle it.
- The sync thread's per-file `fsync` writes each file's 32-byte entry set in its 512-byte sector + bitmap + FAT sectors = small random
  metadata writes between the 16.6 MB bursts, plus a device flush per file (section 4).
- Mount options across the three mounters (all exFAT):

## 8. Stop-time drain and syncfs — confirmed

`stop()` (CC:4224-4388): stop the copy worker first (frames waiting for a copy are lost, their requests go back, CC:4845-4870);
`stopping_ = true`; writers **drain the whole queue** (every queued frame is written; 12 frames ≈ 0.5 s, or the whole ram budget: the
measured safety-stop flush took ≈ 3 s); join with a bounded wait on a dead medium (`APERTAR_DEAD_MEDIUM_STOP_MS` 2000, CC:4252); the
sync thread exits with the writers; the stats line (CC:4296-4316). Then `CameraSession::stopRecording` calls

## 9. Trim worker and the media-tune helper — confirmed

`vm.dirty_*` part is moot for cDNG; it would matter for MLV/H.264/audio only.

## 10. Storage pre-roll from the writer's side — confirmed

A real take through the full write chain at `prerollMaximumFps` (sensor probe max; 60 fps in 4K SDR 12-bit measured, HL:842-855) for
`preroll_seconds` (default 2), `FrameDurationLimits` pinned per request, waits ≤ 1 s for the period, no safety stop
(`setPrerollTake`, CC:4455/7402-7414, 11425-11500), then the clip folder is deleted (`remove_all`, CC:11537-11545). Triggers: Core start,
card insert, format, manual (`StoragePreroll.hpp`). Effects on the next take that follow from the code: (a) the raw pool is warm
(≤ 6-7 buffers already allocated) only if no reconfigure happens in between; (b) exFAT metadata and the dentry cache are warm;
(c) **the deleted 0.7 GB (measured, 115 frames) is below the 1 GiB delete-trim threshold, so no trim follows and the next take's
first ≈ 0.7 GB are written onto freed-but-untrimmed LBAs** (the SSD must erase first; probable, SSD mechanics); (d) 0.7 GB of clean
page cache remains. Its effect on drops was never measured (PP:215, 229-257).
