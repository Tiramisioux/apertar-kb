## 3. Quantitative plausibility of the HMB's effect on this workload

| Quantity | Value | Source / arithmetic |
|---|---|---|
| exFAT FAT size | 917 GiB / 128 KiB = 7,512,064 clusters × 4 B = 28.7 MiB | HL:703 geometry |
| Full L2P table for a 1 TB drive at 4 KiB granularity | ≈ 931 MiB | 1e12 / 4096 × 4 B |
| LBA span mapped by a 64 MiB HMB | ≈ 69 GB (≈ 7 % of the drive) | 64 MiB / 4 B × 4 KiB |
| Time for a 415 MB/s take to stream through 64 GB of fresh LBAs | ≈ 154 s | 16.6 MB × 25 fps |
| Per-read penalty of an L2P miss on a DRAM-less drive | one extra NAND page read, ≈ 50-100 µs ("read latency is doubled", AnandTech snippet) | — |
| Upper bound of HMB-attributable time per maximally chained frame | 127 synchronous FAT reads × ≈ 0.1 ms ≈ 10 ms (and the kernel buffer cache serves repeated FAT sectors without touching the drive) | S1:107 count; pci/exfat mechanism |

Reading: a 64 MiB HMB maps about 7 % of the drive. Unless the controller pins hot mapping pages (unknown, vendor secret), a streaming write of 415 MB/s cycles the mapped span every ~2.5 min, so the HMB's hit rate for the FAT region during a take is uncertain. Even with 100 % misses the penalty is milliseconds per frame, second-order against the 40 ms (25 fps) or 20 ms (50 fps) budget and three orders below the measured stalls. HMB is a drive-side nicety for the fragmented-FAT regime, not a candidate cause of the residual drops. It is NVMe-only; it has no bearing on the USB SSDs.

## 4. Corrections to H13 / R6 / S1 / S3 / kb

1. **rpi-6.18.y's new default of 32 MiB does not enable HMB on this drive**: hmmin = 64 MiB > 32 → same `min > max` exit (pci.c:2074). The operator will have to set `nvme.max_host_mem_size_mb=64` (or more) explicitly even after a kernel upgrade. H13 should say so; S3's E7b "(or with 16)" and R6 b7's "=32" measure nothing on this unit.
2. **R6 b1**: with max = 0 this drive exits at the `min > max` warning, not at the "failed to allocate" branch (that branch is for hmmin = 0 drives). The kb line is proof of the former.
3. **kb README item 5 "remove it on a test boot"**: not possible; the token is in the DT `/chosen/bootargs`, not in cmdline.txt. Override by appending `nvme.max_host_mem_size_mb=64` to `/boot/firmware/cmdline.txt` (last occurrence wins, kernel/params.c). Run-time enabling via `/sys/class/nvme/nvme0/hmb` is also blocked by the same limit; `max_host_mem_size_mb` is 0444.
4. **"needs CMA headroom"** → "pair with a larger CMA (`dtoverlay=vc4-kms-v3d,cma-256`) so the 2 × 32 MiB HMB chunks taken from CMA at early probe do not starve the display/camera allocations (#6504); the HMB itself would probably still be allocated from buddy pages if CMA were full". On 6.12 the chunks are 32 MiB because the kernel runs 16 KiB pages (MAX_ORDER 11), not the 16 MiB R6 implied.
5. **"the drive asks for 64 MiB"** → "the drive's minimum (HMMIN) is 64 MiB; its preferred size (HMPRE) is unknown, ≥ 64 MiB" — `nvme id-ctrl` settles both.
6. **Drive identity** stays probable: the ERFM ↔ E27T link is from review spec tables (TechPowerUp 2 TB: ERFM11.1 + E27T; Elite: ERFM11.0/11.2 + E27T; original E21T Mini: ELFMB0.6/0.7), none of which could be opened directly in this session.
7. **For the synthesis**: both rigs (Apertar 6.12.75, cinemate 6.12.93) ran with HMB disabled; HMB explains no difference between the stacks and none of the measured drops.
8. Minor: issue #6504's reporter said the stutter persisted "without ... NVMe" in one visible comment; the HMB→CMA attribution is the maintainers' (4263812, 9ec9445), with 151 comments unread here. Word it as "the maintainers attributed the CMA exhaustion in #6504 to the NVMe HMB".

## 5. Better test (replaces S1-14 / E7b)

1. Identify first, no reboot: `sudo nvme id-ctrl /dev/nvme0 | grep -E '^mn|^fr|hmpre|hmmin|hmminds|hmmaxd'`; expect `fr ERFM11.1`, `hmmin 16384` (64 MiB), read `hmpre`. `cat /sys/class/nvme/nvme0/hmb` (expect 0). `grep -i 'host memory' /var/log/kern.log* | head` to date-stamp the warning.
2. Baseline with HMB off, read-only on the raw device so the L2P cache cannot hide in a 1 GiB file: `sudo fio --name=rr --filename=/dev/nvme0n1 --rw=randread --bs=4k --iodepth=1 --direct=1 --norandommap --randrepeat=0 --time_based --runtime=60` → record p50/p99 latency. Repeat once while the synthetic writer (variant2.py, 25 files/s) streams, to measure the take-like condition.
3. Test boot: append `nvme.max_host_mem_size_mb=64` to `/boot/firmware/cmdline.txt` (keep the DT token; last wins) and set `dtoverlay=vc4-kms-v3d,cma-256` in config.txt; reboot; `dmesg | grep -i 'host memory'` must read `allocated 64 MiB host memory buffer`; `cat /sys/class/nvme/nvme0/hmb` = 1; `grep Cma /proc/meminfo` before and after; check the camera and display still start (CMA users).
4. Repeat step 2. Expected if H13's mechanism holds: QD1 random-read p50 falls by roughly a third to a half; sequential write rate unchanged.
5. Take-level: one wrap test (S1-10: run the writer past one volume pass, then `iostat -x 1 nvme0n1` during a 4-minute take; `r/s` and `r_await` are the FAT reads) with HMB on versus off. Decision rule: adopt the setting only if `r_await` or worst-file time falls in the fragmented regime and no controller reset or CMA failure appears across the session; otherwise leave the Pi default and close finding 9 as "no effect".
6. Note for the kb: after any kernel upgrade re-check `/proc/cmdline` — 6.18 will show `=32` from the DT, which still disables HMB on this drive unless the cmdline override is present.
