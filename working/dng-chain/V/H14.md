# V/H14 — exFAT metadata costs that grow with a take and with volume age

Verifier: H14. Date 2026-11-01. Sources read in full (not excerpts): Linux **v6.12** tag `adc21867` at `/home/user/torvalds/linux`
(`fs/exfat/{fatent,balloc,dir,namei,inode,super,misc,file,cache}.c`, `exfat_fs.h`, `exfat_raw.h`, `fs/buffer.c`, `fs/namei.c`);
Apertar-Core `92d0970`; cinepi-raw `63a08d5`; kb `lessons/hardware-log.md` (HL) and `working/drop-frames/README.md` (PP), working tree
2026-11-01; exfatprogs `master` (`mkfs/mkfs.c`, `lib/libexfat.c`, via WebFetch). Refs: `file:line@commit`. Labels: **confirmed** (read in
source / measured in a log), **probable** (inferred, reason given), **unconfirmed** (test named).

## 0. Verdict

**Plausible as a cost model, refuted as stated.** H14 bundles three claims. Two mechanisms are real and confirmed in v6.12 (the allocation
cursor sweeps the volume once and resets at mount; a create of a new name is an O(N) scan of every used-or-deleted dentry under `s_lock`). The
load-bearing causal link is wrong: **FAT chains are not a post-wrap phenomenon on this workload.** With two or more files being extended at the
same time (Core: 4 writer threads; the kb's synthetic test: 4 writer threads; cinepi-raw: `disk_workers` default 8) the exFAT allocator hands
alternate clusters to the concurrent files, and `exfat_alloc_cluster` converts every such file to `ALLOC_FAT_CHAIN` at its **second cluster**
(`fatent.c:358-366`). So the 2026-10-30 stack `exfat_alloc_cluster > exfat_ent_set > __bread_gfp` is the **normal** path of every multi-writer
frame, trimmed or not, wrapped or not; it does not show fragmented free space, and the "FAT chain after the cursor wraps" inference in R2 §2.3,
R6 C-a2, S1 §3.3 and S1-10 is unsupported. The "synchronous FAT/directory reads" claim also needs rewording: directory reads in a take are
buffer-cache hits (the directory was just written); the FAT read is cold once per 512-byte FAT block = once per 16 MiB of allocation (about one
per 16-bit frame); and `exfat_write_inode > __wait_on_buffer` is the sync thread's synchronous directory **write** (fsync), not a read. The
numbers hold with corrections: 5 dentries per frame file for Core's default name (not 4-5), 75k dentries / 2.4 MB / 19 clusters after 15,000
files, and 100-200 ns per dentry is a fair cache-hit estimate (I put it at 80-250 ns) that nobody has measured. The O(N) create cost is real,
identical in both stacks (cinepi-raw's names are longer: 6 dentries per file), untested above 6,000 files per folder in the kb, invisible in A0/A1
at 25 fps, and only becomes a candidate limiter for 10-minute takes at 50 fps if the per-dentry cost is near the upper end of the estimate.

Conclusions (labelled):

- **C1 (confirmed by code, probable in practice)**: with N ≥ 2 files being extended concurrently in the same region, cluster grants interleave
  (A gets X, B gets X+1, A's next hint X+1 is taken → A gets X+2 and converts; B likewise). Core's uncompressed cDNG path runs **4** writer threads
  on 4 different files (R3 §1: `CameraController.cpp:4116-4122@92d0970`, `MediaProfile.hpp:148-162`), each `write()` of 480 KiB
  (`CdngEncoder.cpp:1881`) allocating 3-4 clusters block by block with `s_lock` released between blocks. The kb's `variant2.py` used 4 writer threads
  (HL:705). cinepi-raw runs `disk_workers` = 8 by default (`raw_options.hpp:60@63a08d5`; cinemate passes 2 per R1/S1). All three produce FAT-chained
  frame files from the second cluster on, on a fresh volume, before any wrap. One `filefrag -v` on any two frames of a clean trimmed take settles it.
- **C2 (confirmed)**: per FAT-chained 16-bit frame (127 clusters) the driver does 254 `exfat_ent_set` = 254 `sb_bread` + 254 `mark_buffer_dirty`;
  the `sb_bread`s hit the cache except when a new 512-B FAT block is entered: **≈ 1 cold synchronous 512-B read per frame** (127/128), on the
  writer thread, while holding `bitmap_lock` and `s_lock`. On a healthy NVMe that is ~0.1-0.2 ms × 25/s ≈ 0.3 % of wall time. On a device whose
  queue is stalled (the untrimmed-drive regime) every such read waits behind the stall and, through `s_lock`, stops every other writer's block
  mapping. That is the 2026-10-30 picture, without any wrap.
- **C3 (confirmed)**: the "wrap at ~917 GiB" is real and is relevant to the **drive-side** mechanism the kb already names: the allocator never
  reuses a freed cluster until it has passed every never-used cluster once, so the first writes onto deleted-but-untrimmed LBAs come exactly at one
  volume pass (HL:724-726 "909 to 981 GB, close to the volume size"). The code supports the kb's inference; it does not add an exFAT-side cost at
  the wrap beyond C2, which is already paid every take.
- **C4 (probable, unmeasured)**: FAT-chained files also pay a CPU cost in `exfat_map_cluster` → `exfat_cache_lookup` on every one of the
  ≈ 32,400 `exfat_get_block` calls per 16-bit frame (512-B blocks): ~100-300 ns each → 3-10 ms CPU per frame per writer under `s_lock`. Constant per
  frame (does not grow with the take). `perf top` on `exfat_cache_lookup`/`exfat_get_block` would show it.
- **C5 (correction to R3 §6 / S1 §5.2 last row)**: a writer does **not** wait on a buffer lock held by `sync_blockdev` in `exfat_alloc_cluster` or
  `exfat_set_bitmap`: `mark_buffer_dirty` does not take the buffer lock and `__bread_gfp` returns an uptodate buffer without locking it. The only
  waits in the allocation path are cold reads (C2).

Conclusions:

- **C6 (confirmed)**: H14's "scans every used and deleted entry under the superblock lock" holds. The "rewind" detail is moot (never taken here);
  the scan is one pass from 0. The hint added in 2021 (R6 a25) helps readdir/lookup of *existing* names, not creates of new names.
- **C7 (confirmed)**: there is no second O(N) pass for the empty slot (the `hint_femp` tail hint, `dir.c:974-981`), so the per-create cost is one
  dentry walk, not two.
- **C8 (confirmed)**: `s_lock` is held for the whole walk (`namei.c:701-756`), and every other writer needs `s_lock` once per 512-B block
  (`inode.c:278`), so a long create pauses the data path of all writers for its duration. `bitmap_lock` is not involved in the lookup.

| Dentries per cluster | 4,096 | `super.c:528-529` |
| Directory after 15,000 / 25,000 / 30,000 Core files | 75k / 125k / 150k dentries = 2.4 / 4.0 / 4.8 MB = 19 / 31 / 37 clusters | arithmetic |
| Directory after 15,000 / 30,000 cinepi-raw files | 90k / 180k dentries = 2.9 / 5.8 MB | §1 #7 |

### 4.2 Per-dentry cost of the miss scan (hot buffer cache), estimate — **probable**, unmeasured

Per entry (`dir.c:1040-1065` loop body on a `TYPE_FILE`/`TYPE_STREAM`/`TYPE_EXTEND` entry that does not match):
`exfat_find_location` (shifts, no FAT walk because `clu` is already the current cluster) → every 128th entry `exfat_dir_readahead` →
`sb_find_get_block` (LRU hit) → `sb_bread` → `bdev_getblk` → `__find_get_block` → `lookup_bh_lru` (irq-off, compare up to 16, `get_bh`) →
`touch_buffer` → `exfat_get_entry_type` → one or two compares → `brelse`. 16 consecutive entries share one 512-B buffer head, so 15 of 16 are
per-CPU LRU hits (`fs/buffer.c:1359-1390`); every 16th entry goes to `__find_get_block_slow` (xarray lookup + `i_private_lock` + walk ≤ 8 bhs,
`fs/buffer.c:189-243`) and `bh_lru_install`. On a Cortex-A76 at 2.4 GHz: LRU-hit path ≈ 60-150 ns, slow path ≈ 400-900 ns amortised +25-55 ns →
**≈ 80-250 ns per dentry**. R6's 100-200 ns is inside this; neither is measured.

| Take | Dentries at the end | Per-create at the end | `s_lock` occupancy by creates at the end (fps × per-create) |
|---|---|---|---|
| 10 min 4K25 (A0/A1) | 75k | 6-19 ms | 15-47 % — measured outcome: no effect (queue ≤ 2/12) |
| 10 min 4K50 12-bit | 150k | 12-38 ms | 60-190 % → **cannot be sustained in the last minutes if the cost is at the upper end**; breakeven (per-create ≈ 10-15 ms ≈ the writers' slack) at ≈ 60-120k dentries = 12-24k files = 4-8 min |
| 60 s 4K50 | 15k | 1.2-3.8 ms | 6-19 % — not a factor in the operator's 50 fps case as tested so far |

So H14 is quantitatively plausible **only** for long (> 4-8 min) 50 fps takes, which have not been recorded (the 50 fps case fails earlier, upstream
of storage, per H1). It is not a candidate for the operator's two reported cases (4K25 16-bit drops persist even in short takes; 4K50 drops appear
within seconds).

### 4.3 Mechanism sanity checks

- Is the O(N) real in 6.12? Yes (§2.2). Is there any index/hash to avoid it? No; the only hash is the 16-bit `name_hash` compared per stream
  entry (`dir.c:1088-1092`), which saves the UTF-16 compare, not the walk.
- Is the FAT read synchronous? Yes, once per cold 512-B FAT block (`__bread_slow`). Is it "when cold" often? Once per 16 MiB of allocation on a
  512-B-sector volume — essentially once per frame — so the right phrasing is "one cold FAT read per frame", not "when cold" as a rare event.
- Does the directory read block? Not in steady state (hot). It would after a page-cache eviction of the directory's bdev pages (idle camera, memory
  pressure) — the first create of a take after a long idle could page in up to 19-37 clusters with `exfat_dir_readahead` (128 KiB windows,
  `dir.c:638-670`), i.e. a few ms. Minor.
- HMB (S1-14) relevance: the cold FAT reads are 512-B random reads, which is what an HMB speeds on a DRAM-less drive — but at ~25-37/s and
  ~0.1-0.2 ms each the win is < 1 % of wall time on a healthy drive. Not a lever.
- 1 MiB clusters (S1-11): 8× fewer `exfat_alloc_cluster`/`exfat_ent_set` calls and 8× fewer cold FAT reads per frame (one per 128 MiB); does not
  change the directory cost; C1 still chains every file. Modest.
- Fewer writers: with `APERTAR_CDNG_UNCOMPRESSED_WORKERS=1` files stay `NO_FAT_CHAIN` (no FAT writes, no cold FAT reads, arithmetic mapping) at the
  price of serialising the 16.6 MB copies. That is the direct test of C1/C2 and a candidate improvement if the one writer keeps up (A0 ran at
  415 MB/s with the queue at 2/12; a single writer's `write()` throughput on this drive is unmeasured).

## 6. Better tests (cheapest first)

1. **Sector size and FAT geometry (1 min)**: `cat /sys/block/nvme0n1/queue/logical_block_size`; `sudo dump.exfat /dev/nvme0n1p1 | grep -i
   -E "sector|cluster"` (or `blockdev --getss`). Settles the 512 B assumption behind the FAT-read rate and the 32,400 `s_lock` takes per frame.
2. **Chains are the norm (2 min)**: after a trimmed take, `sudo filefrag -v /media/RAW/<clip>/<any two consecutive frames>.dng` → expect > 1
   extent each and interleaved physical offsets. Then one short take with `APERTAR_CDNG_UNCOMPRESSED_WORKERS=1` → expect 1 extent. This refutes
   or confirms C1 directly and separates it from volume age.
3. **Cold FAT reads (during any take)**: `iostat -x 1 /dev/nvme0n1` → `r/s` on a pure-write workload. Prediction: ≈ 25 at 4K25 16-bit,
   ≈ 37 at 4K50 12-bit with 4 writers (≈ 3-5 if the volume has 4-KiB sectors); ≈ 0 with one writer. (`bitmap` never reads.)
4. **Per-dentry cost (10 min, no camera)**: a Python loop creating 30,000 empty files `cDNG_26-11-01_C0001_%09d.dng` in one directory on
   `/media/RAW`, timing each `os.open(O_CREAT|O_WRONLY)`; plot latency vs index. Expect a straight line; slope / 5 = ns per dentry. Compare a run with
   16-char names (4 dentries). This replaces the 80-250 ns estimate with a number and tells whether a 10-min 50 fps take can reach the breakeven.
   (The kb's `variant2.py` harness already has the timing code.)
5. **The claim itself (long 50 fps take)**: a 10-min 4K50 12-bit synthetic run (`variant2.py` at 50 files/s, 12.45 MB) on a trimmed drive, logging
   per-file open latency and queue depth vs file index; then the same with a new sub-folder every 2,000 files. If the single-folder run degrades
   after ~15-20k files and the sub-folder run does not, S1-16 is confirmed for long takes; if neither degrades, close it. Doing this outside Core
   avoids the capture-side limits of the real 50 fps case (H1).
6. **Live instrumentation on the camera (if `bpftrace` is installable)**:
   `bpftrace -e 'kprobe:exfat_find_dir_entry { @s[tid]=nsecs } kretprobe:exfat_find_dir_entry /@s[tid]/ { @us=hist((nsecs-@s[tid])/1000); delete(@s[tid]) }'`
   during the last minute of a 10-min take; or `perf top -p <core pid>` for `exfat_find_dir_entry`, `lookup_bh_lru`, `exfat_cache_lookup`.
