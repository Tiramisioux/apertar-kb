# V/H7 — A 'discard' mount is not a substitute for fstrim on exFAT

Verdict: **confirmed** (confidence 0.9). Every load-bearing code claim holds in both v6.12 and the Pi's rpi-6.12.y line; no measurement in the kb contradicts it; the mechanism is real and the count (≈1.9 M synchronous discards for a 15 000-frame 16-bit clip) is arithmetic from the source. Two corrections: the hazard is wider than stated (the deleter also holds the superblock lock `s_lock`, so a concurrent take's *writes* and file creates block, not only its allocations), and the proposed `mount -o remount,discard` test cannot enable discard on a live exFAT mount (remount parses options into a throw-away context), so it would measure nothing. The wall time of a discard-mount delete stays unconfirmed (no latency figure anywhere); the envelope is 1.5 to 30 minutes.

### 1b. Can the block layer merge the per-cluster discards? **No.**

| Step | Why not | Ref |
|---|---|---|
| Each `blkdev_issue_discard` opens its **own** plug and **waits** before returning | `block/blk-lib.c:92-100@v6.12`. The plug list is per call; `blk_attempt_plug_merge` (`block/blk-merge.c:1153-1178@v6.12`) only looks at `current->plug`, which is empty when the next cluster's call starts | confirmed |
| By the time exfat issues cluster *n+1*, cluster *n*'s request has already completed | `submit_bio_wait` → `blk_wait_io` (`block/bio.c:1455`). The scheduler merge path (`blk_mq_sched_bio_merge`, `blk-mq.c:2841`) can only merge into requests still queued; there are none | confirmed |
| `__exfat_free_cluster` does not coalesce the run itself | `fatent.c:177-195`: it knows `dir..dir+size-1` is contiguous (NoFatChain) yet clears and discards one cluster per iteration. No upstream change does otherwise through rpi-6.12.y (diff above); the only exfat change in this loop is the error break | confirmed |
| NVMe side: one single-bio request = one Dataset Management command with one range | `drivers/nvme/host/core.c:816-884@v6.12` `nvme_setup_discard`: `segments = blk_rq_nr_discard_segments(req)`, one `range[n]` per bio, `cmnd->dsm.nr = segments - 1`. Multi-range (up to `NVME_DSM_MAX_RANGES` = 256, `core.c:1854-1857`) needs merged bios, which never happens here | confirmed |

So: **1,905,000 NVMe DSM commands, strictly serialized, each a full submit → interrupt → wake round trip, inside the deleting thread.**

### 1c. Locks held while the discards run — wider than H7 says

| Lock | Held by the deleter during the 127 discards of one file | Who else needs it (a concurrent take) | Ref |
|---|---|---|---|
| `sbi->bitmap_lock` | yes (`exfat_free_cluster` :231) | `exfat_alloc_cluster` for every new cluster of every frame (one call per cluster on a sequential write: `inode.c:140-141,200` `num_to_be_allocated = clu_offset - num_clusters + 1`) and `exfat_trim_fs` | `fatent.c:231@v6.12` |
| **`sbi->s_lock`** (superblock lock) | **yes** — `exfat_evict_inode` takes it around `__exfat_truncate` (`inode.c:682-684`), which is where the frees happen | **every** `exfat_get_block` (`inode.c:278-380`: the whole block-mapping path of a buffered write holds `s_lock`), `exfat_create` (`namei.c:553-581`), `exfat_lookup` (`:701`), `exfat_unlink` (`:779`), `exfat_write_inode` (`inode.c:108-110`, used by fsync), `readdir` (`dir.c:256`) | `inode.c:682@v6.12` |

Consequence (confirmed mechanism, unmeasured magnitude): on a `discard` mount, deleting a clip while another process records on the same volume stalls the writers' `write()` calls (not just their allocations) for the duration of each file's 127 synchronous discards, released and immediately re-taken for the next file. H7/R4 say "a concurrent take's `exfat_alloc_cluster` blocks"; the truth is stronger: the take's `write()` blocks in `exfat_get_block`.

### 1e. `remount,discard` cannot turn discard on (new finding; breaks the proposed test)

| Step | Ref |
|---|---|
| A remount builds a new `fs_context` and calls the filesystem's `init_fs_context` | `fs/fs_context.c:306-318@v6.12` (`FS_CONTEXT_FOR_RECONFIGURE` → `init_fs_context(fc)`) |
| exfat's `init_fs_context` allocates a **fresh** `exfat_sb_info` and stores it in `fc->s_fs_info` | `fs/exfat/super.c:778-792@v6.12` |
| `exfat_parse_param` writes `opts->discard = 1` into **that fresh** `sbi->options`, not the live superblock's | `super.c:291-294, 330-332@v6.12` |
| `exfat_reconfigure` only sets `SB_NODIRATIME` and calls `sync_filesystem`; it never copies options into the mounted `sbi` | `super.c:762-769@v6.12`; identical in `rpi-6.12.y` `:775-782` (the 2025-11 "fix remount failure in different process environments", `df3ca0411`, only copies uid/gid/masks *from* the live mount *into* the fresh context so validation passes) |
| the fresh `sbi` is freed by `exfat_free` | `super.c:754-760@v6.12` |
| there is no `nodiscard` option at all | `super.c:272-279@v6.12` (`fsparam_flag("discard", Opt_discard)` only) → `remount,nodiscard` fails as an unknown option |

So R4 §6b / S1-12's test (`sudo mount -o remount,discard /media/RAW; time rm -rf ...`) would run with discard still off and "prove" the discard mount is cheap. The test needs a real `umount` + `mount -t exfat -o ...,discard`, and `grep /media/RAW /proc/mounts` must show `discard` (`exfat_show_options`, `super.c:160-161`).

## 3. Mechanism and domain

### 3a. The discard-mount delete (15 000 × 16-bit frames, 128 KiB clusters)

| Quantity | Value | Basis |
|---|---|---|
| Discard commands | 1,905,000 (127 per file), each 128 KiB = 256 LBAs of 512 B | §1a-8 |
| Bytes deallocated | 248.9 GB | 15 000 × 16,590,340 B |
| Issue pattern | strictly serial: submit, sleep in `blk_wait_io`, wake, next | §1b |
| Per-command round trip | **unconfirmed**; floor is the blk-mq submit + MSI + softirq + wake path (tens of µs on a Cortex-A76 at 2.4 GHz) plus the FTL's map update | no figure in any log |
| Wall time envelope | 20 µs → 38 s; 50 µs → 1.6 min; 100 µs → 3.2 min; 200 µs → 6.3 min; 500 µs → 15.9 min; 1 ms → 31.8 min | arithmetic |
| Where the time is spent | inside the deleting thread (touch-UI thread, Core's HTTP handler, or `rm`), holding `s_lock` + `bitmap_lock` for each file's 127 commands | §1c |
| Same delete without `discard` | bitmap bits cleared in memory, `exfat_update_bh(bh, sync=false)` = `mark_buffer_dirty` only (`misc.c:164-171`; `IS_DIRSYNC` is false on a `noatime`-only mount), 1–2 dirtied bitmap buffers per file, dentry set marked deleted → milliseconds per file at most, no device round trip | `fatent.c:186-192`, `misc.c:164-171@v6.12` |

R4's "38 s at 20 µs" lower bound is optimistic for a synchronous round trip through an interrupt; 1.5 to 6 minutes is the plausible band, 30 minutes the pessimistic one. Either way it is two to four orders of magnitude above the helper's 0.47 s.

### 3b. The measured FITRIM (0.467 s for 927.2 GB) is consistent with the code

| Quantity | Value | Basis |
|---|---|---|
| Free clusters walked | 7,074,282 | 927,240,290,304 / 131,072 |
| Loop cost | ≤ 66 ns per `exfat_find_free_bitmap` step (whole 467 ms / 7.07 M) — `ffz` on 64-bit words, `balloc.c:196-220` | arithmetic |
| Discard bios per free run | `bio_discard_limit` caps a bio at `round_down(UINT_MAX, 512)` = 4,294,966,784 B ≈ 4.000 GiB (`block/blk-lib.c:13-36@v6.12`); 927.2 GB in one run → ≥ 216 bios, chained and submitted asynchronously, **one** `submit_bio_wait` at the end (`blk-lib.c:63-72, 85-100`) | code |
| Can those 4 GiB bios merge into multi-range DSMs? | No: `bio_attempt_discard_merge` (`blk-merge.c:1081-1104`) requires `blk_rq_sectors(req) + bio_sectors(bio) <= blk_rq_get_max_sectors`, and for discards that is `min(max_discard_sectors, UINT_MAX >> 9)` = 4 GiB (`block/blk.h:185-192@v6.12`). So ≈ 216–230 single-range DSM commands of ≈ 4 GiB each (more if the free space is fragmented into runs < 4 GiB; those *can* merge up to 256 ranges per command) | code |
| Device-side rate | ≈ 2.2 ms per 4 GiB DSM if serial; the device may process them in parallel | arithmetic |
| Lock held | `bitmap_lock` for the whole 0.467 s (`balloc.c:274-329`); **not** `s_lock` — a concurrent writer's `exfat_get_block` would proceed until it needs a new cluster | code; Core runs it only when idle (`mediaTrimMayRun`) |

So FITRIM does the same deallocation work as a 15 000-file discard-mount delete in a few hundred device commands instead of 1.9 million, and for the whole free space (including deletes made on a Mac or by the touch UI).

### 3c. Granularity note

`exfat_ioctl_fitrim` raises `minlen` to `bdev_discard_granularity` (`file.c:463-464`), which NVMe sets to the logical block size (`core.c:1852`), so every free run of ≥ 1 cluster is trimmed. Nothing in the kb records the NVMe's `discard_max_bytes` / `discard_granularity` / `dmrsl` (if the controller reports `dmrsl`, 4 GiB bios would be split further by `bio_split_discard`, `blk-merge.c:133-167`; it does not change the FITRIM/discard-mount ratio).

## 4. Corrections to H7 as worded

1. "inside `__exfat_free_cluster`" → "inside `exfat_clear_bitmap` (`balloc.c:162-173`), which `__exfat_free_cluster` calls once per cluster (`fatent.c:192`, `:213`)". Minor.
2. Add the superblock lock: the frees run under **`s_lock` and `bitmap_lock`** (`inode.c:682-684`, `fatent.c:231`), so a concurrent take's `write()` (`exfat_get_block`, `inode.c:278-380`) and file creates (`exfat_create`, `namei.c:553`) block, not only its cluster allocations. Strengthens the hypothesis.
3. "927 GB in 0.47 s measured" → the figure is the **free space** trimmed at mount (863.6 GiB of a 917.4 GiB volume), not the volume size; the same mount's `fstrim -v` by hand reported 917.4 GiB when the volume was emptier. Immaterial to the conclusion.
4. The number "~1.9 million" is exact at 1,905,000 for 16,590,340-byte files; a Log-12 clip gives 1,425,000; with cinemate's 1 MiB clusters it would be 240,000 — still 240 000 serialized commands.
5. R4 §6a / S1 §: `record_start` waits **5 s** for a running trim (`waitForMediaTrim(command.name, 5000)`, `ApertarCoreApp.cpp:11820`, and `:10823` for the pre-roll), not 2 s.
6. R4 §6b / S1-12 test: `mount -o remount,discard` does **not** enable discard on exFAT (§1e); `remount,nodiscard` is not an option. Replace with umount/mount.
7. "wall time unmeasured: 38 s at 20 µs" → the floor is unrealistic for a synchronous interrupt round trip; state "minutes (1.5–6 min at 50–200 µs per command), up to ~30 min at 1 ms".

## 5. Better test (settles the wall time and the concurrent-take hazard in one session, idle Pi)

Prerequisite: a volume state with one 15 000-frame clip to delete and the mount options under control (stop apertar-ui's automounter or let it mount, then remount by hand):

```
# A. baseline: delete without discard, then trim
cat /sys/block/nvme0n1/queue/discard_max_bytes /sys/block/nvme0n1/queue/discard_granularity   # record once
grep /media/RAW /proc/mounts                        # must NOT show discard
iostat -dx 1 nvme0n1 > /tmp/iostat-A.txt &          # columns d/s, dMB/s, d_await show discards and their latency
time rm -rf /media/RAW/<clip-15000>                 # expect seconds
time sudo fstrim -v /media/RAW                      # expect < 1 s (Core logs the same as media_trim_ms)
kill %1

# B. discard mount: umount + mount (remount cannot set it), same clip re-recorded first
sudo umount /media/RAW
sudo mount -t exfat -o rw,noatime,uid=1000,gid=1000,fmask=0002,dmask=0002,discard /dev/nvme0n1p1 /media/RAW
grep /media/RAW /proc/mounts                        # must show ",discard"
iostat -dx 1 nvme0n1 > /tmp/iostat-B.txt &
time rm -rf /media/RAW/<clip-15000>                 # the number H7 lacks; iostat d/s = commands per second, d_await = per-command latency
kill %1
# while rm runs, once: cat /proc/$(pgrep -x rm)/stack   -> expect blk_wait_io / submit_bio_wait / blkdev_issue_discard / exfat_clear_bitmap

# C. hazard: discard mount, record a 4K25 16-bit take, delete a 1000-frame clip from the touch UI during it
#    read drop[queue-full] / peak_queue in Core's journal, and the writers' stacks:
for t in /proc/$(pgrep -x apertar-core)/task/*; do echo $t; cat $t/stack; done | grep -B1 -A3 "exfat_get_block\|mutex_lock"
```
Pass criterion for H7: B's `rm` takes ≥ 100× A's `rm` + `fstrim`, `d/s` ≈ 1/d_await (serial), and C shows writer tasks parked in `exfat_get_block → mutex_lock` while `rm`/the UI thread sits in `blk_wait_io`.

## 7. Observations vs conclusions

Observations: §1 (source text), §2 (log lines). Conclusions: the discard mount is functionally a trim-at-delete but costs 1.9 M serialized device commands per 10-minute clip in the deleting thread under both exFAT locks; FITRIM does the same in ≈ 200–300 commands in under half a second; Core's idle FITRIM is the right primitive on this kernel; its remaining hole is deletes Core does not see (touch UI, Mac), covered only at the next mount.
