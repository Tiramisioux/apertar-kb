# V/H5 — verification of "the copy worker allocates a fresh 16.6 MB zero-filled vector while holding DngRecordingQueue::mutex_, which libcamera's thread takes every frame"

Verifier: read-only. All Apertar-Core refs are `src/camera/CameraController.cpp` (CC) at 92d0970 unless another file is named. Kernel/glibc refs are URLs. Bench figures come from this x86 container and are labelled as such.

## 0. Verdict in one paragraph

Every code fact in H5 holds (allocation under `mutex_`, pool 6, pool cleared on (re)configure, excess freed by writers, `hasCapacityForFrame` on libcamera's thread takes the same mutex). The load-bearing mechanism claim — the per-miss cost (1-8 ms) lands "inside the serial cycle" — does not hold in the normal frame cadence: the copy worker starts `acquireRawBuffer` for frame n within ~0.1 ms of frame n's completion callback and is out of the lock within ≤ ~10 ms, while the next callback arrives 40 ms (25 fps) or 20 ms (50 fps) later. libcamera's thread can only find the mutex held by an allocation when the copy worker is already lagging by ≥ T − W (≥ ~30 ms at 25 fps, ≥ ~15 ms at 50 fps), i.e. in a copy backlog that the pool miss does not itself create and that no logged take ever showed (`drop[copy-slot]` never printed; at 50 fps SDR the held-request cap is 2, so a one-frame lag would have been logged). The measurements agree: A0 was a cold first take after a Core restart (no pre-roll existed yet) and lost nothing; the 2026-10-31 short-take gaps start at frame ~50-100 in every take, long after the pool is warm; the 4K50 SDR gaps are a steady 12 %, not the sporadic pattern misses would give. Verdict: **refuted as a cause and as a "serial cycle" cost**; survives as a cheap hygiene improvement for the copy worker (and writer-side frees) with an expected effect on drops of about zero. Several numbers in the reports also need correcting (16 KB pages → ~1,013 faults, not ~4,050; faults recur on most misses, they do not stop after the first free; the stale "exFAT gets 2 writers" and "on libcamera's completion thread" comments in the source).

## 2. When does a pool miss happen? (the condition in H5 is imprecise)

Model from the code (one copy worker, 4 writers, pool cap P = 6):
- Circulating vectors C = (copy worker holds one: 0/1) + `queue_.size()` + busy writers (≤ 4). Alive vectors N = pool + C.
- `acquireRawBuffer`: pool > 0 → hit (pool − 1); pool = 0 → **miss**, N + 1 (CC:4635-4636).
- `recycleRawBuffer`: pool < P → pool + 1; pool ≥ P → **free** on the writer thread, N − 1 (CC:5145).

Consequences:
1. N tracks the running maximum of C. After a (re)configure (N = 0) every new high of C is a miss: frame 0, then each frame where C exceeds every earlier value. With writers at ~10-30 ms per 16.6 MB frame and a 40 ms period, C sits at 1-3, so the first take misses on ~2-4 frames, not "the first 6": the pool only reaches 6 after a burst that lifted C to ≥ 6 and fell back.
2. A free (trim) happens only when a recycle finds pool = 6, i.e. N ≥ 6 + C. After it N = 6 + C_low. New misses then need C > 6 + C_low: a swing of more than 6 vectors between a quiet moment and a burst. "Queue depth > pool" is not the condition; with 4 writers busy whenever the queue is non-empty, queue depth q means C ≥ q + 4 (+1 while the copy worker holds one), so **peak_queue 2 ⇒ C_max ≈ 6-7 ⇒ at most a handful of misses per take** (the ~5-7 cold ones plus a thrash miss whenever C swings by > 6).
3. Each thrash cycle also costs a 16.6 MB free on a writer thread (munmap or heap delete, ~0.5-1.5 ms, plus TLB-shootdown IPIs to the cores running Core's other threads — µs each).

So the kb's STATUS.md item 18 ("misses recur whenever the queue holds more than ~6") and S1's "queue > ≈ 2 with 4 writers busy" both overstate the frequency; the right statement is "a miss on every new high of circulation since the last trim".

## 3. Does libcamera's thread actually wait for the allocation? (the load-bearing claim)

Per-frame timeline, normal cadence, T = 40 ms (25 fps) or 20 ms (50 fps):

| t | libcamera's CameraManager thread | copy worker (one thread) | `mutex_` |
| --- | --- | --- | --- |
| t_n | `requestComplete` → `recordRawFrame` → `hasCapacityForFrame` (lock, µs) → `enqueueCopy` (`copyMutex_`) → returns; libcamera goes on with its own per-frame work (swap, stats, IPA, back end) | wakes from `copyCv_` (idle core: ~0.05-0.2 ms; loaded box: a few ms) | free |
| t_n + ~0.1 ms | — | `acquireRawBuffer`: hit → µs; **miss → W ms allocation under `mutex_`** | **held for W** |
| t_n + W … + W + 6 ms | — | sync, memcpy 16.6 MB (~6 ms per 351a3ee; "sync ~4 + copy ~4" kb b3:35-36), sync end, `releaseHeldRequest` → `requeueRequest` | free |
| … + 8 ms (Log) | — | `applyCdngLogFrame`: 8.3 M table lookups, est. 7-9 ms (kb b3 row 9g estimates the same loop shape at 7-9 ms) | free |
| … + µs | — | `enqueue` (lock, µs) → idle | held µs |
| t_n + T | `hasCapacityForFrame` for frame n+1 | idle since t_n + ~15-25 ms | free |

- The lock is contended by the allocation only if `acquireRawBuffer(n)` is still running at t_n + T, i.e. it began later than t_n + T − W. In cadence it begins at t_n + ~0.1 ms. **Exposure requires the copy worker to be lagging by ≥ T − W: ≥ ~30-35 ms at 25 fps, ≥ ~15-17 ms at 50 fps.** The copy worker's own per-frame work is ~6 ms (16-bit, no Log), ~14-16 ms (16-bit + Log), ~3-4 ms (8.3 MB SDR), so it is idle for more than half of every period; a lag of that size needs a backlog in `copyQueue_` (the worker descheduled for tens of ms, or work exceeding T). A pool miss adds W to the copy worker's own time but does not create that backlog.
- A lag ≥ one period shows up as held requests: in SDR 12-bit the cap is 2 (CC:8229 with 4 buffers), so a one-frame lag at 50 fps would have printed `drop[copy-slot]`; none is in any logged take (T34 M3 lines list queue-full 0, capture-gap only; T25 safety pass "no `drop[copy-slot]`"; A0/A1 "no `drop[...]` line of any kind"). In Clear HDR the cap is 6, so lags below 6 frames are invisible there, but the stats line prints `dropped_copy_slot` only when > 0 (S1-20 notes this).
- Preemption while holding the lock (CFS slice 3-4 ms on a 4-core box with 6-8 runnable threads) can stretch the hold by a few ms. It cannot stretch it to T.
- Even in the backlog + miss coincidence, the completion thread loses ≤ W (3-10 ms) once. A capture gap needs the CFE to find no buffer at SOF; with 8 raw buffers at 25 fps one ~10 ms delay does not get there. At 50 fps, where H1 puts the serial cycle at ≈ T already, one W would cost one frame — sporadically, not every 8th frame.

Conclusion for lens 1: H5's wording "inside the serial cycle" is false for the cadence Core actually runs; the cost is on the copy worker. The completion thread is exposed only as a second-order effect (probability ≈ W/T per lagging frame that also misses the pool) in a regime never observed.

## 4. How long does a 16.6 MB `std::vector<uint8_t>(size)` take? (lens 3)

What the constructor does: `operator new(size)` → `malloc`, then value-initialisation = `std::fill_n` = `memset` of all 16.6 MB (libstdc++; GCC does not turn new + memset into calloc). On fresh pages the first touch happens inside the memset, so one pass pays both the kernel's page clear and the user memset.

glibc path (glibc 2.36 on Pi OS Bookworm = Debian 12 — probable, packages.debian.org not reachable from here; the logic below is unchanged since 2.26):
- Requests ≥ `mp_.mmap_threshold` (default `DEFAULT_MMAP_THRESHOLD_MIN` = 128 KB) go to `mmap` in `sysmalloc`: `if (av == NULL || ((unsigned long)(nb) >= (unsigned long)(mp_.mmap_threshold) && (mp_.n_mmaps < mp_.n_mmaps_max)))` (malloc.c@glibc-2.36, sysmalloc) → fresh zero pages → first-touch faults.
- Freeing an mmapped chunk raises the threshold: `if (!mp_.no_dyn_threshold && chunksize_nomask(p) > mp_.mmap_threshold && chunksize_nomask(p) <= DEFAULT_MMAP_THRESHOLD_MAX) { mp_.mmap_threshold = chunksize(p); mp_.trim_threshold = 2 * mp_.mmap_threshold; } munmap_chunk(p);` (malloc.c@glibc-2.36, `__libc_free`); `DEFAULT_MMAP_THRESHOLD_MAX` = 4 × 1024 × 1024 × sizeof(long) = 32 MiB on 64-bit, so a 16.6 MB chunk qualifies. Later same-size requests are served from the arena heap.
- The copy worker is not the main thread → non-main arena with mmapped heaps of `HEAP_MAX_SIZE = 2 * DEFAULT_MMAP_THRESHOLD_MAX` = 64 MiB (arena.c@glibc-2.36). Three 16.6 MB chunks fit one heap. `heap_trim` returns without trimming while `top_size < mp_.trim_threshold` (33 MB after the adjustment), but a heap whose chunks are all freed is deleted, and the next allocation maps and faults a new one.

Bench on this container (x86 Xeon VM, 4 KB pages, glibc 2.39, `-O2`), file `../bench/pooldyn.cpp`: thread A constructs `std::vector<uint8_t>(16588800)`, hands it to thread B, which frees the oldest once `live` vectors are held (Core's allocate-on-copy-worker / free-on-writer pattern):

| circulation `live` | allocations that page-faulted (of 16) | faulting ctor | non-faulting ctor |
| --- | --- | --- | --- |
| 1 | 0-3, then none | 8-11 ms (4,050 faults) | 1.7-2.0 ms (0 faults) |
| 3 | 0-7, then none | 8-9 ms | 1.8-2.1 ms |
| 6 | 0-13, then none | 8-11 ms | 2.0 ms |
| 8 | all 16 | 8-15 ms | — |

Also (`../bench/vecalloc.cpp`, main thread): first two ctors 10.9-11.3 ms with 4,050 faults, then 1.2-1.9 ms with 0 faults; free of a faulted chunk 1.6 ms. So with 6-8 vectors in circulation (Core's regime at peak_queue 2 with 4 writers) **faults recur on most misses**: R7 §7's "later allocations come from the heap" is right about the heap but wrong about the faults.

Pi 5 numbers:
- Kernel page size: `CONFIG_ARM64_16K_PAGES=y` in `arch/arm64/configs/bcm2712_defconfig` (rpi-6.12.y, fetched; no `CONFIG_ARM64_4K_PAGES`, no `TRANSPARENT_HUGEPAGE` key) — the kb already noted this (`working/research-30fps/q5-copy.md:77`, "UNCONFIRMED on the Pi: `getconf PAGESIZE`"). 16,588,800 B = **1,013 pages of 16 KB**, not "~4,050" (S2 §2.1, R7, S1 wrote ~4,050 / ~4,100; that is the 4 KB `kernel8.img` figure). Unconfirmed on the rig until `getconf PAGESIZE` is read.
- Memory: LPDDR4X-4267; tinymembench on a CM5 reports memset ≈ 12.6 GB/s and memcpy ≈ 6.0 GB/s (https://github.com/geerlingguy/sbc-reviews/issues/58; https://forum.clockworkpi.com/t/bookworm-6-12-y-for-the-uconsole-and-devterm/15847?page=9).
- Estimate per **faulting** miss, 16 KB pages: kernel clear of 16.6 MB (~1.3 ms) + user memset of 16.6 MB (~1.3 ms) + 1,013 fault entries (~1-2 µs each, 1-2 ms) ≈ **3.5-5 ms**; with a 4 KB kernel ≈ 7-11 ms (4,050 entries). Per **non-faulting** miss (memset only): **1.5-2 ms**. SDR 8.3 MB copies: half. The munmap/heap delete on the writer: ~0.5-1.5 ms. M.md's "1-8 ms" is therefore a fair range (the 8 needs 4 KB pages); S1/S2's "2-8 / 3-8 ms" likewise. Label: probable (x86 bench + published Pi bandwidth; not measured on the Pi).

## 6. Corrections to M.md H5 and to the reports it cites

1. Reword the title/claim: "the copy worker holds `mutex_` across a 16.6 MB allocation on a pool miss; libcamera's thread would wait only if its next callback arrived during that window, which the cadence does not allow unless the copy worker is already ≥ T − W behind". Drop "inside the serial cycle".
2. Miss condition: not "first ~6 frames after a reconfigure" and not "queue depth > pool"; it is "every new high of circulating copies since the last trim" (§2). At peak_queue 2 that is a handful of misses per take.
3. Page faults: ~1,013 (16 KB pages, default Pi 5 kernel), not ~4,050. Faults recur on most misses in Core's allocate-here/free-there pattern (bench §4); they do not stop after the first free.
4. Cost: 3.5-5 ms per faulting miss, 1.5-2 ms per non-faulting miss on a Pi 5 (probable), on the copy worker; plus 0.5-1.5 ms per excess free on a writer. "1-8 ms" is acceptable as a range.
5. Line refs: `acquireRawBuffer` CC:4623-4646 (alloc 4636), `hasCapacityForFrame` CC:4570-4607, `clearRawPool` CC:4649-4655 (call CC:8191), `recycleRawBuffer` CC:5132-5153, `preferredRawPoolSize` CC:5232-5235 (R3's 5242-5245 is wrong), copy worker CC:4776-4833, held cap CC:8224-8229 and CC:1363-1371.
6. Two stale comments in Core mislead readers: CC:4384-4385 ("page in 16.6 MB each on libcamera's completion thread" — the copy worker does it since 351a3ee) and CC:4117-4118 ("exFAT/NTFS get 2" writers — `MediaProfile.hpp:135` gives exFAT 4 since 0358fcf).
7. Classification: not a cause of either operator case; an **improvement of low priority** (S2-I3's fix is still right: allocate outside `mutex_`, pre-fill the pool to workers + queue + 1 in `startAtFolder`, no value-initialisation; expected effect on drops ≈ 0, benefit = removing 2-5 ms jitter events from the copy worker and 16.6 MB frees from the writers; cost ≈ +100-200 MB resident). The pre-roll's "warms the raw pool" side effect (R3 §250, R7 §169, S1-10) is real but worthless by the same argument.

## 7. Is the proposed test able to settle it? A better test

- Proposed in R7 L3 / S2-3: "compare the first take after a mode change with the second" (kb step 0b COLD / WARM / SECOND). Weak: it is confounded (fstrim, exFAT metadata, drive state, WebUI) and the cold-pool effect is predicted to be nil anyway; a null result would not distinguish "no effect" from "effect masked".
- Better, direct, cheap (one build): in `hasCapacityForFrame` time the lock acquisition (`steady_clock` before and after the `unique_lock` constructor), keep the maximum and the count of waits > 1 ms; in `acquireRawBuffer` count misses and time the allocation; in `recycleRawBuffer` count frees; print `pool_miss= pool_miss_max_ms= pool_free= cap_lock_wait_max_ms= cap_lock_waits_1ms=` in the `recording stats` line. Run: a cold first take after a restart and a second take, 4K25 16-bit with Log, WebUI open, then 4K50 SDR 12-bit. H5 is dead as a cause if `cap_lock_wait_max_ms` stays < 1 while `pool_miss` > 0; it is alive only if waits of several ms line up with `drop[capture-gap]` timestamps.
- Without a build: `perf trace -e syscalls:sys_enter_mmap,syscalls:sys_enter_munmap -p $(pidof apertar-core)` during a take gives the miss/free timeline (each miss is one 16.6 MB mmap or heap growth) to set against the gap timestamps in the journal; `perf stat -e minor-faults -p <pid>` gives the fault count per take (expect ≈ 1,013 per faulting miss on the 16 KB kernel). `getconf PAGESIZE` on the Pi settles the page size.
- The copy backlog question (the only regime in which H5 can bite): print `dropped_copy_slot` always and add `held_max=` (max of `heldRequests_`) to the stats line; `held_max ≥ 2` for a whole take would show the copy worker lagging.
