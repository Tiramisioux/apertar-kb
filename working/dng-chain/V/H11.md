# V/H11 — Core's per-file fsync on exFAT: whole-device metadata flush + FLUSH per file; A1 showed it removable

Hypothesis under test (M.md:87-90): `syncLoop` (CameraController.cpp ~4525-4549) fsyncs every file written in the last
second then the folder; `exfat_file_fsync` = `__generic_file_fsync` + `sync_blockdev` + `blkdev_issue_flush`, so each
fsync is a whole-device metadata flush plus an NVMe FLUSH (26/s at 25 fps, 51/s at 50 fps); A0 (on) and A1 (off) both clean
for 10 min at 25 fps; the fsync exists for pull-safety (C0010 0-byte files).

Verdict: **plausible** (code path confirmed in both kernel trees; FLUSH reaching the drive is conditional on an unread
device bit; the cost is estimated, never measured; two wording corrections and one wrong downstream proposal).

Refs use `CC` = `/home/user/Apertar-Core/src/camera/CameraController.cpp@92d0970`, `HL` = `/home/user/apertar-kb/lessons/hardware-log.md`,
kernel = `https://raw.githubusercontent.com/torvalds/linux/v6.12/<path>` unless `rpi-6.12.y` is named. Kernel files were read
through WebFetch (raw.githubusercontent.com refuses curl from this session), so kernel refs carry function names, not line numbers.

### 2.2 Does the FLUSH reach the drive? (the "volatile write cache off" question)

Answer to the lens-3 question: yes — an NVMe FLUSH with the volatile write cache "off" *as the kernel sees it* (VWC bit absent, or
`write_cache` written to "write through") is a no-op at the block layer: the request completes in `blk_insert_flush` case 0
and no command is issued (K12-K13). With the feature on, the flush enters the flush state machine (`default:` →
`blk_flush_complete_seq`) and becomes one NVMe Flush command per `blkdev_issue_flush` (probable: `nvme_setup_flush` not re-read).
Consumer NVMe controllers normally report VWC present (probable, general knowledge; not verified for this part), so the
expected state is "write back" and 26 Flush commands/s at 25 fps. It must be read on the Pi, not assumed (test T1).

### 2.3 What one tick costs (estimate, nothing measured)

| Step per tick (25 fps, cDNG) | Count | Size / wait | Basis |
|---|---|---|---|
| `file_write_and_wait_range` on the newest file(s) | 1-2 of 25 still in flight | up to one 17 MB DNG at ~500 MB/s ≈ 35 ms wait (sync thread only) | C3/C9 start writeback at write time; K3 |
| Synchronous dentry write under `s_lock` | 25 + 1 (dir) | one 512 B..4 KiB buffer each; NVMe ≈ 0.1-0.3 ms; USB-UAS ≈ 1-3 ms | K6-K7; latencies are typical values, unconfirmed on this rig |
| `sync_blockdev` | 26 calls | first call: ~1 bitmap block (25 × 133 clusters = 3325 bits), ~1 directory block (25 × 3 × 32 B), 0 FAT blocks for contiguous files; the other 25 calls: only what the writers dirtied in the last few ms (0-2 blocks) | K9; 128 KB clusters, 17 MB files (HL:703-706) |
| `blkdev_issue_flush` | 26 (+1 audio) | 0 ms if `write_cache` = write through; otherwise one NVMe Flush each, latency unknown on this drive (the drive must commit ~17 MB of data arriving every 40 ms) | K10-K14 |

Writer coupling: ≈ 26 × (0.1-0.3) ms ≈ 3-8 ms of `s_lock` hold per second on NVMe (≈ 0.5 %); the flushes do not block
other data writes in the block layer (flush machinery is per-hctx and separate), they load the device. At 50 fps everything
doubles. None of this reaches the capture side (libcamera / CFE) by any path in the code; H11 is a writer-margin cost, not a
capture-gap mechanism.

## 4. Corrections to H11 (wording, numbers, refs)

1. **"plus an NVMe FLUSH per file"** → "plus a pre-flush request per file, which becomes an NVMe Flush command only if the
   controller advertises a volatile write cache (`cat /sys/block/nvme0n1/queue/write_cache` = `write back`; `nvme id-ctrl
   /dev/nvme0 | grep vwc` bit 0); otherwise `blk_insert_flush` completes it without touching the device (K12). Unread on this
   drive; probable for a consumer NVMe."
2. **"whole-device metadata flush"** → "a write-and-wait of every dirty metadata buffer of the device (bitmap, FAT, directory
   sectors). Scope is the whole device, volume is small: the first fsync of each tick carries a second's worth (≈ 2-3 × 4 KiB
   blocks for contiguous files), the following 25 carry what the writers dirtied in the last few ms."
3. **Add the real writer coupling**: `exfat_write_inode` holds `sbi->s_lock` across a *synchronous* directory-entry write
   (`write_dirty_buffer(REQ_SYNC)` + `wait_on_buffer`, K6-K7) and every writer's `exfat_get_block` takes `s_lock` (K8):
   one device round-trip stall for all four writers per fsync, 26/s. This, not the FLUSH, is the mechanism that touches the
   writers; `exfat_write_inode > __wait_on_buffer` in the 2026-10-30 stacks is this path.
4. **Count**: 26/s and 51/s hold for cDNG (uncompressed and lossless). Add +1/s for `audio_capture.raw` when audio records
   (AudioRecordingSession.cpp:779-786). Lossy DNG: 0 per-file fsyncs (CC:4958-4981). MLV: 1 file/s. The 25 fsyncs run as one
   burst per tick; "26/s" is an average, the shape is a 1 Hz burst.
5. **"__generic_file_fsync ... writes its directory entry set"**: correct only via `sync_inode_metadata` → `exfat_write_inode`,
   and only because `exfat_write_end` marked the inode dirty (K4-K5). `__generic_file_fsync` itself issues no flush.
6. **"A1 showed it removable"**: A0 and A1 are one 10-minute run each at 25 fps on a freshly trimmed NVMe, both with zero
   drops; A1 shows "no measured benefit of the fsync for drops", not "a measured cost". The only deltas are peak_queue 2→1
   and peak dirty 11→3 MB.
7. **Downstream proposal S1-5 ("`APERTAR_MEDIA_SYNC_MS` 5000 → 5× fewer flushes") is wrong**: `syncLoop` fsyncs *every* file
   written since the last tick (C5), so a 5 s interval still issues 125 file fsyncs (125 dentry writes + 125 sync_blockdev
   + 125 flushes) every 5 s — the same average, in a 5× bigger burst, with 5 s of pull exposure. Only the folder fsync count
   drops (1/5 s). To cut flushes the design has to change (fewer fsync *calls*, not a longer interval) — see T6.
8. Refs in M.md: `CC ~4525-4549` is exact (4525-4549); `start` is 4153-4166 not "~4163" alone; add `CC:4958-4981` (call
   site) and `CC:4512-4523` (reason). R4 §5 / R6 a8's `fs/exfat/file.c@v6.12:exfat_file_fsync` holds in rpi-6.12.y too.

## 6. Verdict

- Code: every code claim in H11 holds in Apertar-Core 92d0970 and in fs/exfat (v6.12 and rpi-6.12.y). The hypothesis omits the
  `s_lock`-held synchronous dentry write (the only path to the writers) and states the FLUSH as unconditional when it depends
  on an unread device bit.
- Evidence: consistent with every measurement; nothing shows a cost (A0 = A1 at 25 fps, one run each); nothing exists at 50
  fps or on USB; the "26 FLUSHes/s" has never been counted.
- Mechanism: real and bounded; on a healthy NVMe the estimated writer coupling is ≈ 0.5 % of a second plus an unknown Flush
  load; it cannot produce capture gaps by any path in the code.
