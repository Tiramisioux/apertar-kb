## 0. Verdict in one paragraph

**Plausible as a configuration comparison, but the title's load-bearing word "uninstalled" is contradicted by the kb itself and must go.** Everything
about cinemate checks out in source: `run()` prefixes `chrt -f 70`, `ionice -c2 -n0`, `taskset -c 1-3` (`CM:275-290`), the unit carries `LimitRTPRIO=80`
(`cinemate-autostart.service:27`), the installer writes `@audio - rtprio 80` and the CPU-3 isolation tokens on 4-core boards (`cinemate-install.sh:1236-1253,
1652-1668`), and cinepi-raw's `--disk-nice -5` fails every take (handbook `open-threads.md:340-356`). Core's side also checks out in source: no SCHED_FIFO,
no affinity, no ionice anywhere (grep over `src/ scripts/ config/ README.md CMakeLists.txt`), one `setpriority(-5)` on the callback thread (`CC:8591-8601`),
and no installer step for `config/apertar-core-capture-priority.conf` in Core, Apertar-UI or any script (grep; the sibling sudoers/tmpfiles files carry
install comments, this one does not). **But the kb's architecture docs record the drop-in as installed on the live Pi**: `architecture/build.md:96`
"**Confirmed** installed (Pi, 2026-10-25: `systemctl cat apertar-core` shows `LimitNICE=-5`)", `architecture/core.md:29`, and `architecture/overview.md:5`
states that all unit contents in those docs come from `systemctl cat` on the live Pi that day. R7, S2, S3 and M.md never looked there. So the honest status is:
*nothing in the repos installs the drop-in, the Pi has it anyway (kb record of a live check, no raw output quoted), and the nice -5 is therefore probably in
effect; the journal line `capture scheduling: thread=… nice=-5` is still unquoted.* Two smaller corrections: the cinepi-raw failure is **EACCES** ("Permission
denied"), not EPERM; and the nice requests are moot under SCHED_FIFO anyway. On the mechanism: ~20 nice-0 threads cannot impose much on a nice -5 thread on
this kernel — EEVDF picks by virtual deadline (nice -5 weight 3121 vs 1024, 3.05x shorter), RUN_TO_PARITY bounds the wait to one slice of 2.25 ms on 4 CPUs,
and the wait only happens when all four cores are busy (measured 59/44/48/38 % → a few % of wake-ups). Expected added latency per serial wake-up is tens of µs,
tail ~2 ms: it cannot explain the steady 30 fps deficit (~5 ms/frame) and is only a marginal candidate for the WebUI-open single-frame gaps at 25 fps.
Whole-process SCHED_FIFO is **not the right shape for Core**: equal-priority FIFO threads never preempt each other, so a FIFO-70 capture thread waking while
three FIFO-70 writers/MJPEG threads hold cores 1-3 waits until one blocks (unbounded by the scheduler, vs 2.25 ms under CFS), and Core's own nice split
(callback -5, lossy workers +5, playback +10) collapses to one level. RT throttling (950 ms/s per CPU, no sharing) keeps a spinning thread from locking the
box but would starve that CPU's kworkers/ksoftirqd to 5 %; neither engine has a spin loop (grep), so the risk is latent, not present. The better design is
FIFO on the two libcamera threads only (CameraManager + IPA proxy), writers left SCHED_OTHER — exactly H15's "fallback" clause, which should become the
primary test.

### 3.2 How much run-queue delay can ~20 nice-0 threads impose on a nice −5 thread on 4 cores?

Facts (v6.12, EEVDF):
- Weights: nice −5 = 3121, nice 0 = 1024 → ratio 3.05 (`core.c sched_prio_to_weight`, "10 % per nice level", WebFetch).
- Slice: `sysctl_sched_base_slice = 750000 ns × (1 + ilog2(ncpus))` = 0.75 × 3 = **2.25 ms** on 4 CPUs (`fair.c`, `get_update_sysctl_factor`).
  Virtual deadline = `vruntime + calc_delta_fair(slice, se)` = slice × 1024/weight: a nice −5 task's request is 0.74 ms virtual against 2.25 ms for nice 0,
  so at a pick it beats any similarly placed nice-0 task (`fair.c update_deadline`, `calc_delta_fair`).
- Wake-up preemption: `check_preempt_wakeup_fair` → `pick_eevdf(cfs_rq) == pse` → `resched_curr`; `RUN_TO_PARITY` (default true) protects the running
  task until its 0-lag point or slice end; `PLACE_LAG` (true) preserves the sleeper's lag; `WAKEUP_PREEMPTION` true (`features.h`, `fair.c`, WebFetch).
  Worst-case wait when the target CPU is busy ≈ one remaining slice ≤ **2.25 ms**; `CONFIG_PREEMPT=y` makes in-kernel copies (a writer's 17 MB
  `copy_from_user`) preemptible, so the bound holds outside spinlocked sections.
- A waking task first looks for an idle CPU (`select_task_rq_fair` → idle sibling search); only when **all four** cores are busy does it wait at all.
- Measured load while recording 30 fps: cores 59/44/48/38 % busy (`hardware-log.md:164`). If independent, P(all busy) ≈ 0.59 × 0.44 × 0.48 × 0.38 ≈ **4.7 %**.
  With the WebUI open (MJPEG + HTTP threads) say 10-20 %.

Estimate: per scheduler wake-up on the serial path, expected delay ≈ P(all busy) × ~1 ms ≈ **50-200 µs**, p99 ≈ **2 ms** (one protected slice), and the
**count** of competing nice-0 threads barely matters: EEVDF picks by virtual deadline, not queue position, and the −5 weight wins the pick; the nice −5
buys at most the difference between "picked next" and "picked after one or two nice-0 slices" (~2-4 ms) in the rare all-busy case. The serial path has
~3-4 wake-ups per frame (IPA prepare/return, BE-done → CameraManager, completion → copy worker), so ~0.2-0.8 ms expected per frame, tail a few ms.
Against the measured ~38 ms cycle at 30 fps this is noise (the deficit is ~5 ms/frame, every frame). At 25 fps (40 ms period) a 2-3 ms tail could tip a
cycle that already sits near 38 ms, but only a *sustained* overrun drains 8-10 buffers — which is what the WebUI-open pattern looks like, and that is a
load/DRAM story more than a wake-up story. **Judgement: the mechanism is real but quantitatively small; nice −5 vs nice 0 on this kernel is worth a few
hundred µs per frame in expectation.** The kb's own number (S1+S3+S4 ~1.6 ms idle, ~5 ms under load, S2 §3) is a *work* figure measured on the thread, not a
run-queue delay; run-queue delay has never been measured on either rig (`/proc/<pid>/task/<tid>/schedstat` field 2, or `perf sched latency`).

Conclusion on shape: the safe and effective form is **per-thread**: `pthread_setschedparam(SCHED_FIFO, 70)` on the CameraManager thread (from
`requestComplete`, replacing the `setpriority(-5)`) and on the IPA proxy thread (needs a libcamera hook or `chrt -f -p 70 <tid>` on the two tids after start),
writers and WebUI left SCHED_OTHER, `LimitRTPRIO=80` on the unit. That is H15's "fallback" clause; it should be the primary test. Whole-process `chrt` as in
kb patch 0005 is acceptable as a *quick A/B* because the throttle keeps the box alive, but a null or negative result would not refute per-thread RT.
