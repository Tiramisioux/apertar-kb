# V/H6 — Touch-UI clip deletes bypass Core; no trim follows; the ~0.9 TB stall can return in a touch-UI-driven session

Verdict: **confirmed** (confidence 0.88). Every load-bearing code claim holds at the named commits; the fstrim `--listed-in` dispute settles for R4 from the util-linux v2.38.1 source; the stall past ~0.9 TB without a trim is measured (71 runs). What is not established: that any operator session has actually run that way, the rig's `/etc/fstab`, and that Debian's shipped `fstrim.service` is byte-identical to upstream's `.in` (both are probable).

Commits: Apertar-Core `92d0970` (APP = `src/ApertarCoreApp.cpp`, CC = `src/camera/CameraController.cpp`); Apertar-UI `e061be8`; util-linux `v2.38.1` = `54a4d5c` (2022-08-04), sparse clone at `dl/ul/ul/sys-utils/`; pi-gen `master` (raw.githubusercontent.com via WebFetch).

### 1c. "The pre-roll's usual 0.7 GB delete is below the threshold" — mode-dependent (correction)

`prerollMaximumFps` = sensor maximum for the running mode with only the IMX585 Clear-HDR-16-bit back-end cap (25) kept (`CC:3332-3342`); `preroll_seconds` default 2 (`APP:4721-4724`). |---|---|---|---|---|

{
	char *list = xstrdup(tabs);

		struct stat st;

**Settlement: R4 is right, R6 c1 is wrong.** `--listed-in /etc/fstab:/proc/self/mountinfo` is a fallback chain, not a union: on any system whose `/etc/fstab` parses to at least one entry (every Raspberry Pi OS image), `/proc/self/mountinfo` is never read, and the weekly service trims only the fstab filesystems (`/boot/firmware`, `/`). R6's citing `master` instead of v2.38.1 does not explain the disagreement: the `master` man page carries the same sentence, so the semantics hold for bookworm (2.38.1) and trixie (2.41) alike. Consequences: (i) `fstrim.timer` is no backstop for `/media/RAW`, as H6 says; (ii) R6 c5 ("the timer can overlap a shoot and block exFAT allocations while it walks 917 GiB") is wrong for the same reason — the timer never touches the exFAT volume; (iii) R2's lead that cinemate's rig stayed clean through the timer (S3-20) is dead unless that rig listed RAW in fstab.

Quantitative plausibility of "a touch-UI-driven session": at 4K25 16-bit (415 MB/s) the volume wraps after ≈ 984 GB / 0.415 GB/s ≈ 40 min of recording; at 4K50 12-bit uncompressed (620 MB/s) after ≈ 26 min. Note the mitigations that close the hole in practice: any reboot, Core restart or card re-insert (trim at mount), any WebUI delete ≥ 1 GiB, a pre-roll in an uncompressed SDR mode (§1c), a manual `sudo fstrim`.

## 3. Mechanism and domain

- Drive side: FITRIM (`exfat_trim_fs`) tells the SSD which LBAs are free; without it the FTL keeps the deleted clips' LBAs as valid data, and overwriting them after the allocation cursor wraps costs erase/GC with the host waiting — the stalls were seen as writers parked in exFAT metadata calls with nothing in flight on the device (hardware-log:719-722). The effect is measured (two independent onsets, two arms); the per-LBA explanation is inference, as the log says. H6 does not depend on the explanation, only on the measured onset ≈ 0.9 TB and the cure.
- Filesystem side: exFAT frees clusters in the bitmap on delete; `statvfs` sees the jump at once, which is why `trimMediaAfterDelete`'s before/after comparison works for Core's own deletes (`APP:11015-11018`). A delete by another process changes the same bitmap, but nobody in Core reads it for that purpose.
- util-linux side: settled from source in §1d.

3. Reword "the pre-roll's usual 0.7 GB delete is below the threshold" → "below the threshold in lossless modes (0.69 GB measured) and in 16-bit Clear HDR (≈ 0.83 GB at the 25 fps cap); above it (≈ 1.25-1.49 GB) in uncompressed 10/12-bit SDR at 60 fps and whenever `preroll_seconds` ≥ 3, where the pre-roll does trim".
4. fstrim sentence: cite `fstrim.c:423-442` (loop, `if (rc >= 0) break;`) and `:288-291` (−1 only for an empty table); state that a fstab with even one unusable entry already stops the chain; add that the stock Raspberry Pi OS fstab has three entries (pi-gen `stage1/01-sys-tweaks/files/fstab`) and that the automounter uses `mount(2)` (`CfeAutomounter.cpp:627`), so `/media/RAW` is in mountinfo only. ## 5. Better test

The R4 L1 protocol (10-min takes, touch-UI deletes, no manual trims, past one volume pass, control arm with WebUI deletes) does settle it but costs ≈ 50 min of recording per arm and has two confounders. Sharper, in two parts:

- **Part 1 (2 min, settles the code hole on the rig):** with Core idle, read `get_state` → `media_trim_last_unix`, `media_trim_last_result`. Delete a clip ≥ 1 GiB from the touch UI (Clip Browser → Remove Selected). Re-read `get_state` and `journalctl -u apertar-core -n 50 | grep 'media: trim'`. Expected: `media_trim_last_unix` unchanged, no `reason=delete` line. Then delete a clip ≥ 1 GiB from the WebUI: expected `reason=delete result=trimmed` within a few seconds. This proves the asymmetry directly.
- **Part 2 (the stall return, ≈ 45 min, optional because hardware-log:701-733 already shows it):** start from a Core restart (trim at mount, confirm the journal line), set 4K25 16-bit Clear HDR uncompressed or any lossless mode (so the pre-roll stays < 1 GiB, §1c), record 10-min takes and delete each from the touch UI; after the 4th-5th take expect `queue-full` bursts and seconds-long file times, `media_trim_last_unix` still at the restart time. Control: same with WebUI deletes (one trim per delete), expected clean. Record `free_mb` from the media event before each take to know where the cursor is.
- Rig-state reads that bound the fstrim side (once, read-only): `cat /etc/fstab; systemctl is-enabled fstrim.timer; systemctl cat fstrim.service; fstrim --version; journalctl -u fstrim.service`. Expected: fstab with `proc`, `/boot/firmware`, `/`; ExecStart with `--listed-in /etc/fstab:/proc/self/mountinfo`; no `/media/RAW` line in any fstrim journal entry.
