Verdict: **plausible** (confidence 0.6). The code claims hold in every tree read. Two corrections are load-bearing: (1) "cinemate runs without TDN" is
established only for an install made by `cinemate-install.sh` from `main`; the operator's *colour* cinemate rig ran the fork's full tuning (tdn x3) at its

cannot select the tuning copy (Core overrides it on every start); only `set_tuning_file` / `settings.tuningFile` can. The Apertar side moves from
"probable on" to "probable on, strongly": the Pi's `imx585_clearHDR.json` is a 134,888-byte file equal to `imx585.json` minus `rpi.hdr`, and no PiSP
tuning of that class in any tree lacks `tdn` (the only tdn-less PiSP tuning anywhere is upstream's 4,944-byte `uncalibrated.json`, from which cinemate's
stub is derived). "Largest removable term" rests on an unmeasured assumption (BE time scales with bytes); the arithmetic is right, the mechanism is
plausible, the BE hardware time has never been read.

## 3. Lens 3 — mechanism and arithmetic

### 3.1 Byte arithmetic (R9 §5, q1 method) re-done

Inputs: re-read factor 1.1085 from the q1 tiler simulation for 3840x2200 (10 tiles 408/432 px, 2192 rows; `q1-backend.md:107-116`); output 1280x720
YUV420 = 1,382,400 B; TDN read and write each counted at the re-read size (q1 labels the write PROBABLE, lower bound without overlap).

| Case | raw px | B/px | raw read | TDN r+w | out | total | H2/R9 says |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Clear HDR 16-bit 3840x2200, TDN on | 8,448,000 | 2 | 18.73 | 37.46 | 1.38 | **57.57** | 57.6 ✓ |
| same, TDN off | | | 18.73 | 0 | 1.38 | **20.11** | 20.0 (q1 case B simulation 19.953; 0.8 % apart, not material) |
| SDR 12-bit 3840x2160 COMP1, TDN on | 8,294,400 | 1 | 9.19 | 18.39 | 1.38 | **28.96** | 29.0 ✓ |
| same, TDN off | | | 9.19 | 0 | 1.38 | **10.57** | 10.6 ✓ |

| cinemate SDR `12:U` SBGGR16 container, no TDN / TDN | 8,294,400 | 2 | 18.39 | 0 / 36.77 | 1.38 | 19.77 / 56.54 | 19.8 / 56.5 ✓ |

Caveats the hypothesis should carry: (a) the 1.1085 factor is simulated for 2200 rows and 16-bit; for COMP1 the tiler aligns compressed tiles to
8-px blocks, and the overlap may differ by a few per cent (probable, unverified); (b) TDN write with overlap is PROBABLE — lower bounds are 53.8 MB (HDR)
and 27.2 MB (SDR); (c) TDN at COMP1 means the BE also runs the TDN compress/decompress blocks (`:2096-2105`), which is compute, not bytes.
The arithmetic is sound; the format premise (TDN = CFE format) is confirmed in upstream and in the Apertar fork.

### 3.2 "TDN is the largest removable term of the serial cycle"

- Bytes: TDN is 65 % of BE traffic in Clear HDR (37.5 of 57.6 MB) and 63 % in SDR COMP1 (18.4 of 29.0). Among things that can be removed without a
  build, nothing else in the BE comes close; the other candidates (SW stats 5.8→7.1 ms, swap 6.1→9.9 ms, `HL:185-188`) were already cut by L1/L2 without
  shrinking the cycle (`HL:219-232`).
- The step from bytes to time assumes the BE is DRAM-bound while recording. Supporting: 13.4 → 34.6 ms for the same job when the writers run; L2 showed
  the thread is not the limit. Against: the 34.6 ms is a thread-seen upper bound, 78 % of completions were delayed behind stats/swap work (`HL:191-194`),
  and the BE's own completion timestamp (`ktime_get_ns()` on the ISP Input buffer, kb `research-30fps-answer.md` item 4, `be_cycle.py`) has never been
  read. Idle rate 9.36 Mpx / 13.4 ms = 0.70 Gpx/s says compute is not the wall at 50 fps; a hardware BE that is not memory-bound would gain little from
  TDN off. So: **plausible, not established**. H2's own rule-out (S2 within 15 % with TDN off → not memory-bound) is the right one.
- Side effects of a tdn-less copy: SDN/CDN switch to `*_no_tdn` values (`denoise.cpp:62-70`) → preview a little noisier; DNGs untouched (the BE only
  reads the raw). The kb's warning not to use `disable_tdn` in the pipeline config stands (`q1-backend.md:332`).

### 3.3 Domain plausibility

TDN as a full-frame reference read + write per frame is how PiSP's temporal denoise works (ping-pong buffers, `pisp.cpp:2283-2287`; kernel job formation
`pisp_be.c`, kb q1 row 30). Compressed TDN exists in hardware (`PISP_BE_BAYER_ENABLE_TDN_COMPRESS/DECOMPRESS`). The kernel BE format table accepts
COMP1 on any node. Nothing in the mechanism is doubtful.
