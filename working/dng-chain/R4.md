### 4d. What the cluster size means per frame on this rig

Mechanism (6.12 exfat, confirmed from source; the per-cluster count is **probable**): Core writes a frame with plain buffered `write()` of the whole payload (`writeAll`, CdngEncoder.cpp:463-480; open flags `O_WRONLY|O_CREAT|O_TRUNC` :1749-1754, **no `O_DIRECT`** at 92d0970; `posix_fadvise SEQUENTIAL` :1759, `DONTNEED` after :1780). The kernel maps block by block through `exfat_get_block` → `exfat_map_cluster(inode, iblock >> sect_per_clus_bits, ...)`; when the cluster index is past the on-disk size it allocates `num_to_be_allocated = clu_offset - num_clusters + 1` clusters — for a sequential write that is one cluster per new cluster (fs/exfat/inode.c). Each `exfat_alloc_cluster` takes `bitmap_lock`, searches from `clu_srch_ptr`, sets one bitmap bit per cluster (`exfat_set_bitmap`, dirty buffer, written later), and only if the new cluster is **not contiguous** with the previous one converts the file to a FAT chain (`exfat_chain_cont_cluster` writes one FAT entry per existing cluster, then `exfat_ent_set` twice per further cluster; fs/exfat/fatent.c). The directory entry (size, first cluster) is written by inode writeback or fsync, not per `write()` (`exfat_map_cluster` only `mark_inode_dirty`s via `exfat_get_block`/`exfat_write_end`; `exfat_write_inode` syncs only for `WB_SYNC_ALL`; fs/exfat/inode.c) — orchestrator fact **holds**.

| Frame | Bytes | clusters @128 KiB | clusters @1 MiB | alloc calls/s @128 KiB | @1 MiB |
|---|---|---|---|---|---|
| 4K 16-bit Clear HDR uncompressed, 25 fps | ≈16.6 MB (hardware-log.md:820) | 127 | 16 | 3 175 | 400 |
| 4K 16-bit with Log 16→12 | 12 451 344 (hardware-log.md:820) | 95 | 12 | 2 375 | 300 |
| 4K SDR 12-bit uncompressed, 50 fps | ≈12.44 MB (3840·2160·12/8 + header) | 95 | 12 | 4 750 | 600 |
| Volume | 917 GiB free | 7.5 M clusters, bitmap ≈0.94 MB, FAT ≈30 MB (FAT only touched by chained files) | 0.94 M clusters, bitmap ≈0.12 MB | | |

What the count buys: each allocation is a mutex + bitmap search + one dirty bit; for a contiguous file it never touches the FAT. The expensive case in the 2026-10-30 stack dumps is `exfat_alloc_cluster > exfat_ent_set > __bread_gfp` (hardware-log.md:721-723): a **non-contiguous** allocation that converts the file to a FAT chain and reads cold FAT sectors from a stalled device. That path is reached when the free space is fragmented — after the allocator has walked the volume once (`clu_srch_ptr` wraps) and new frames land in deleted holes. 1 MiB clusters cut the number of allocation calls 8×, cut the bitmap/FAT sectors touched 8×, and make fragmentation coarser; they cost up to 1 MiB of slack per file (≈6 % at 16.6 MB) and macOS compatibility per cinemate 91f3ba0 (**unconfirmed**: a 1 MB-cluster card has never been mounted on Patrik's Mac in any log). Both exFAT and the drive's performance after one pass remain a trim/fragmentation question, not a cluster-size one (hardware-log.md:701-733: trim alone restored 0 drops at 128 KB clusters).

### 6b. Cost model, 15 000 frames × 127 clusters (16.6 MB uncompressed 16-bit; ≈249 GB)

| | `discard` mount | Core helper (`fstrim` after the delete) |
|---|---|---|
| Discard commands | 1 905 000 × 128 KiB, **synchronous**, issued one by one inside each `unlink`'s cluster free, **under `bitmap_lock`** (section 5) | one FITRIM: contiguous free runs merged; the block layer splits a run into bios of ≈4 GiB (`round_down(UINT_MAX, granularity)`), i.e. tens of bios for 249 GB; the NVMe driver may split further by its DSM limits |
| Wall time | **unconfirmed**: NVMe Dataset Management latency per command is not in any log; at 20 µs → 38 s, at 200 µs → 6 min, at 1 ms → 32 min, all spent inside the deleting process (touch UI thread or Core's web handler) | measured 0.47 s for 927 GB of free space (whole-volume, at mount); a 249 GB hole: probable < 0.5 s |
| Lock held | `bitmap_lock` for the duration of each file's discards → a concurrent take's `exfat_alloc_cluster` blocks; Core refuses its own deletes while recording (:8655-8661) but the touch UI has **no recording guard** (cliplistmodel.cpp:382-440) | `bitmap_lock` for 0.47 s, only when idle (`mediaTrimMayRun`) |
| Discards during writing | none (discard only on free) | none |
| Covers deletes done elsewhere (Mac, touch UI) | yes, at delete time, if the card is mounted with `discard` on the Pi; a Mac delete is not discarded until... never (macOS does not trim exFAT) | yes, at the next mount (`reason=mount`) |
| Mount-side ownership | needs a change in the automounter (Apertar-UI) and in `mount-raw.sh` and in the four other mount paths | none |

Verdict (probable): a `discard` mount would keep the drive trimmed without the helper, but on exFAT 6.12 it turns a 15 000-frame delete into ~1.9 million serialized DSM commands and can stall a running take if anything deletes during it; the helper does the same work in one FITRIM when idle. The kb's deferral note (working/drop-frames/README.md:119-120, "online discard on exFAT may slow big deletes") holds. Test that settles the wall time: `sudo mount -o remount,discard /media/RAW; time rm -rf /media/RAW/<15000-frame clip>` versus `sudo mount -o remount,nodiscard ...; time rm -rf ...; time sudo fstrim -v /media/RAW`, idle, same card state.

## 10. Observations (measured or read) kept apart from conclusions

Observations:
1. Live mount 2026-10-26/30: exFAT, `rw,noatime,uid=1000,gid=1000,fmask=0002,dmask=0002,...`, 128 KB clusters, no discard (hardware-log.md:54, :703-704).
2. After a card pull the automounter remounted (its log lines) within 2-8 s (hardware-log.md:364-368).
3. Core trimmed 927 GB in 467 ms at mount on 2026-10-31 (hardware-log.md:817-818).
4. Stall stacks were in `exfat_alloc_cluster > exfat_ent_set > __bread_gfp` and `exfat_write_inode > __wait_on_buffer` (hardware-log.md:721-723).
5. Source: five Apertar mount paths with three different option sets; one of them (automounter) is the one in use; three lack `noatime`.
6. Source: touch-UI deletes bypass Core.
7. Source: 6.12 exfat `discard` = one synchronous discard per freed cluster under `bitmap_lock`; FITRIM = one discard per free run under the same lock.

Conclusions:
- The boot/insert mounter on the rig is the CFE automounter (probable; `mount-raw.sh` unknown); `noatime` is on (confirmed).
- Mount options are not a plausible cause of the residual drops: the live options equal the best set Apertar has; cinemate's exFAT string differs only in `dmask/fmask` (cosmetic) and `rw` (default).
- The exFAT-specific cost per frame is the cluster-allocation count (127 at 128 KB), the per-file dir entry, the bitmap write-back and, after one volume pass, FAT-chain writes on fragmented free space; cluster size is the only format-level knob and it trades macOS compatibility.
- A `discard` mount is the wrong tool on this kernel; Core's idle FITRIM is right, but it has a hole (touch-UI deletes).
