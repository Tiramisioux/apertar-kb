Notes:
- The `usb_ssd` cushion was halved in d7a8d2b with the stated reason "a USB SSD's write speed falls off a cliff once its SLC cache is exhausted (~90 s into a 4K take)" (:127-139 comment, :337-340 log hint). The 90 s figure is a comment, not a measurement in any log (unconfirmed).
- `default_ps_max_latency_us` is written to `/sys/module/nvme_core/parameters/...` **at mount time** (:309-316). The parameter is consumed when the NVMe controller is probed (APST table configured at init), so writing it after enumeration affects only the next probe (e.g. the CFE latch unbind/bind) — **probable**; cinemate's own fallback message says to put it in cmdline.txt (:316). The operator's Apertar rig already has `nvme_core.default_ps_max_latency_us=0` as a boot argument (kb working/drop-frames/README.md:236).
- Apertar's equivalent helper `scripts/apertar-media-tune` (Apertar-Core 92d0970) copies this table (pi-nvme 1 GiB/256 MiB/none/512/2/APST 0; usb-uas 512/256; usb-storage 256/128; sd-card 256/128/mq-deadline/128/1) but is **opt-in** (`APERTAR_MEDIA_TUNE=1`, ApertarCoreApp.cpp:10953-10962; reason: "16-bit 4K25 ran clean without it (2026-10-27)").

### 1.4 fsck policy (confirmed)

| When | What | Ref |
| --- | --- | --- |
| Mount fails | `_auto_repair`: ext4 `e2fsck -f -p`; ntfs `ntfsfix`; **exfat `fsck.exfat -a`**; then one retry of the mount | storage-automount.py:384-398, :483-497 |
| After every mount, then every 24 h, never while `is_recording=1` | ssd_monitor: `sudo nice -n 19 ionice -c3 fsck -n <dev>` (read-only), result to Redis `FSCK_STATUS`; NTFS skipped | ssd_monitor.py:827-870 |

Hazard for the operator's rig: `fsck -n` of a 932 GB exFAT volume reads the whole bitmap/FAT/directory tree right after mount, i.e. in the first seconds after insertion — competes with a take started immediately (probable; test: `journalctl -u cinemate-autostart | grep "fsck result"` timestamps vs the first take).

### 1.5 Unmount / yank / RAW arbitration (confirmed)

- `_unmount`: non-blocking `umount -l` via `Popen`, mountpoint cleanup deferred to startup purge, sysctl restore (:513-539).
- NVMe watchdog: `/sys/block/<root>/device/state == dead` → lazy unmount + promote standby (:813-833). Sanity watchdog: `statvfs` every 3 s; EIO/ENOENT/ENODEV/ENOTCONN/ESTALE → lazy unmount + promote (:835-867).
- RAW arbitration: first `LABEL=RAW` → `/media/RAW`, others `/media/RAW1..n` standbys; promotion by `mount --move` (FUSE falls back to remount) (:620-760).
- Eject-intent flag `/run/cinemate-storage/eject/<dev>` written by cinemate before its own umount so the automounter does not re-grab (:47-70; ssd_monitor.py:49-72, :942-948).
- cinemate `unmount_drive`: `sync` then `sudo umount`, lazy fallback (ssd_monitor.py:942-968). `erase_drive`: `sync`, `fuser -km`, parallel `rm -rf`, `sync` (:1009-1078). **No trim after erase** (Apertar trims after ≥1 GiB freed: kb drop-frames README "Trim" row).

### 1.6 What runs at mount (sequence, confirmed)

1. udev `add`/`change` on a partition → `blkid` LABEL/TYPE with retries (:212-236) → `_add_raw` → `_promote_to_active` → `_mount` → mount → chown → block tuning + (RAW only) sysctls + APST (:365-379).
2. ssd_monitor polls `/media/RAW` (`os.path.ismount`, 1 s) → `_handle_mount`: device type, fstype (`findmnt`/`blkid`), mount options, recorder profile → Redis (`storage_type`, `storage_filesystem`, `storage_mount_options`, `storage_recorder_profile`, `is_mounted`, `space_left`) → NTFS advisory → `mount_event.emit` → fsck scheduled (ssd_monitor.py:345-389).
3. `mount_event` → `CinePiController._handle_storage_mount_event` (cinepi_controller.py:2135-2210): if the recorder profile changed, **restart cinepi-raw** (deferred while recording/pre-rolling, :2128-2133). Worker topology and `--buffer-count` are launch-time arguments.
4. `mount_event` → `StoragePreroll._handle_mount_event` → pre-roll after 3 s (storage_preroll.py:173-183).

## 2. Format and the exFAT allocator

### 2.1 cinemate's format path (confirmed, ssd_monitor.py:1080-1262)

| Step | Detail | Ref |
| --- | --- | --- |
| Refusals | not mounted; `is_writing_buf`/`is_buffering`=1 | :1082-1094 |
| Default fs | `exfat` (was ext4 until 86c38f6 2026-05-31; b473055 2026-06-02 aligned the controller default) | :1096 |
| Unmount | eject flag → `sync` → `sudo umount` → lazy → `fuser -km` + `blockdev --flushbufs` → lazy | :1117-1167 |
| Repartition | if the partition is < 90 % of the disk: `parted mklabel gpt`, `mkpart RAW 0% 100%`, `set 1 msftdata on`, `partprobe` | :1177-1228 |
| mkfs | ext4: `mkfs.ext4 -F -L RAW`; **exfat: `mkfs.exfat -L RAW <dev>` (no `-c`)**; ntfs: `mkfs.ntfs -Q -F -L RAW` | :1230-1245 |
| After | `sync; udevadm settle; blkid -g`; remount via `mount_drive` | :1256-1262, :615-634 |

Comment at :1233-1236 (verbatim): "Do not pass -c (cluster size): the default chosen by mkfs.exfat (~256 KB for large drives) is compatible with macOS and Windows. Forcing 1 MB clusters was tried for write-latency but breaks the macOS exFAT driver on most versions."

### 2.2 exfatprogs default cluster size (confirmed, web)

`lib/libexfat.c` `exfat_set_default_cluster_size`: `< 7 MB → 512 B`; `≤ 256 MB → 4 KB`; `≤ 32 GB → 32 KB`; **else `128 * KB`**. `manpages/mkfs.exfat.8` table: ">32 GiB | 128 KiB". So the "~256 KB" in 91f3ba0 and in the code comment is **wrong**; a 932 GB drive formatted by cinemate gets **128 KiB clusters** — the same as the operator's Apertar drive (kb hardware-log.md:703 "932 GB exFAT with 128 KB clusters"). Cluster size is therefore **not** a difference between the two rigs unless the operator formatted elsewhere.

### 2.3 What the Linux exfat driver (v6.12) does per cluster (confirmed from source excerpts)

| Step | Code | Ref (Linux v6.12) |
| --- | --- | --- |
| Buffered write maps a block | `exfat_get_block` → `exfat_map_cluster(inode, iblock >> sbi->sect_per_clus_bits, ..., create)` | fs/exfat/inode.c |
| Clusters to allocate | `if (clu_offset >= num_clusters) num_to_be_allocated = clu_offset - num_clusters + 1;` → **1 cluster per crossing** for a sequential write | inode.c `exfat_map_cluster` |
| Allocation | `exfat_alloc_cluster(inode, num_to_be_allocated, &new_clu, inode_needs_sync(inode))` | inode.c |
| Loop | `while ((new_clu = exfat_find_free_bitmap(sb, hint_clu)) != EXFAT_EOF_CLUSTER)`; `exfat_find_free_bitmap` scans the bitmap word by word with `ffz` | fatent.c, balloc.c |
| Contiguity | `if (new_clu != hint_clu)` → `exfat_chain_cont_cluster(...)`, `p_chain->flags = ALLOC_FAT_CHAIN` (converts the whole file's run to FAT entries, one `__exfat_ent_set` per cluster) | fatent.c |
| Bitmap | `exfat_set_bitmap(inode, new_clu, sync_bmap)` → `set_bit_le` + `exfat_update_bh(bh, sync)` = `mark_buffer_dirty` (+ `sync_dirty_buffer` only if the inode is sync) | balloc.c, misc.c |
| FAT | **only if `ALLOC_FAT_CHAIN`**: `exfat_ent_set(sb, new_clu, EXFAT_EOF_CLUSTER)` and `exfat_ent_set(sb, last_clu, new_clu)`; each `exfat_ent_set` does `sb_bread(sb, sec)` (synchronous read of the FAT sector if not cached) then `exfat_update_bh(bh, SB_SYNCHRONOUS)` and `exfat_mirror_bh` | fatent.c |
| Search pointer | `sbi->clu_srch_ptr = hint_clu` (allocation continues from the last position; after one pass it wraps into freed space) | fatent.c |
| Discard | `__exfat_free_cluster`/`exfat_clear_bitmap`: `sb_issue_discard` **only if `sbi->options.discard`** | fatent.c, balloc.c |

Consequences (probable, reasoned from the above):
1. A 16.9 MB linear frame (16,896,680 B) is **129 cluster allocations at 128 KiB** vs **17 at 1 MiB**; a 12.45 MB Log-12 frame is 95 vs 12. Each allocation: a bitmap scan from the search pointer, a bitmap bit, and — when the run is not contiguous — two FAT-entry writes preceded by an uncached FAT-sector read.
2. The kb's stall stack `exfat_alloc_cluster > exfat_ent_set > __bread_gfp` (kb hardware-log.md:721-722) can only occur on the `ALLOC_FAT_CHAIN` path, so at that point the file being written was **not contiguous**: the allocator was handing out non-adjacent free clusters (free space fragmented by deleted takes, and `clu_srch_ptr` wrapped). Each such frame then costs up to ~129 FAT-entry updates, each preceded by a synchronous FAT-sector read when uncached, on a drive that is already slow to answer → seconds-long stalls. 1 MiB clusters would cut that by 8×; **ext4 (extents, delayed allocation) avoids per-cluster metadata entirely**, which matches cinemate's field observation "ext4 drops less" (a61a589).
3. `dirsync`/`sync` are not set by either stack, so bitmap/FAT writes are buffered and leave with the flusher (`dirty_writeback_centisecs`), not per allocation. The reads (`sb_bread`) are the synchronous part.

Test to settle: on the Pi, `sudo filefrag -v /media/RAW/<take>/<frame>.dng` (extent count > 1 ⇒ FAT-chained) on frames from a stalled take vs a clean one; `cat /sys/kernel/debug/tracing/...` is overkill — `perf trace -e 'exfat:*'` is not available; the filefrag check is enough.

### 2.4 History of the cluster-size decision (confirmed, commit messages)

| Commit | Date | What | Why stated |

| Mechanism | Effect on this stack | Status |
| --- | --- | --- |
| `chrt -f 70` on the whole process | Every cinepi-raw thread (capture, encode, disk, preview, stats) inherits SCHED_FIFO 70. | `--encode-nice -10 --disk-nice -5` | `setpriority(PRIO_PROCESS, 0, nice)` in `configureThreadContext` (cinepi-raw dng_encoder.cpp:432-440) **fails with EPERM** on every take (handbook open-threads.md:340-356 "DNG disk workers cannot set their nice level — deferred 2026-09-22"); and under SCHED_FIFO nice is irrelevant anyway | confirmed (log quoted in handbook); probable for the SCHED_FIFO remark |
| `ionice -c2 -n0` | Best-effort class 0. "Support for io priorities is io scheduler dependent and currently supported by bfq and mq-deadline" (Linux Documentation/block/ioprio.rst). The automounter sets the recording drive's scheduler to **`none`** → **no-op** on the recording drive | confirmed (doc + storage-automount.py:115,124,135,146) |
| `taskset -c 1-3` + `--encode-affinity 1-2 --disk-affinity 2` | Encode threads pinned round-robin onto 1-2, disk threads onto 2 (`cpus_to_pin.push_back(safe_affinity[index % size])`, dng_encoder.cpp:398-412); core 3 stripped from any request (:379-394). ### 3.4 cinepi-raw write path, as far as it bears on the leads (confirmed, cinepi-raw 63a08d5)

- RAM pool: `RAM_FRACTION = 0.90` of `MemAvailable` at encoder configure (dng_encoder.cpp:1063-1086); encode worker **blocks** on `ram_cv_.wait(... ram_buffers_ < max_ram_buffers_)` (:2170-2175); allocation failure drops the frame (:2184-2193).
