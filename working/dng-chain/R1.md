### Does the nice attempt fail?

**Confirmed** for disk workers: handbook `open-threads.md:340-356` ("DNG disk workers cannot set their nice level — deferred 2026-09-22": every take logs `dng-dsk-N: failed to set nice level -5: Permission denied`; the service runs as `pi` and lowering nice needs `RLIMIT_NICE` or `CAP_SYS_NICE`). **Probable** for encode workers (−10): same syscall, same user, same `configureThreadContext` (`dng_encoder.cpp:432`); the handbook names only `dng-dsk-N`. ## 3. Hand-off from the libcamera buffer

Path, in order (all **confirmed**):

1. `requestComplete` (completion thread): `CompletedRequestPtr payload(r, [this](cr){ queueRequest(cr); })` — the shared_ptr **deleter is the requeue** (`core/rpicam_app.cpp:1238@63a08d5`). `post_processor_.Process(payload)` (`:1255`) spawns the detached stage thread; outputThread later posts the Msg to the main queue (`core/post_processor.cpp:136, 165`).
2. Main loop: `CinePIRecorder::EncodeBuffer` (`cinepi/cinepi_recorder.hpp:49-106`): `BufferWriteSync w` (START|RW ioctl at ctor, END|RW at dtor — both on the **main thread**, before the worker reads; `core/buffer_sync.cpp:16-47`); gets the mmap span (`:69`); "Frame Drop!!!!!" LOG(1) if |fps_measured − fps_setting| > 1 (`:92-96`); `encode_buffer_queue_.push(completed_request)` ("creates a new reference", `:101-104`); `EncodeBuffer2(..., (void*)mem[0].data(), ...)` passes the **pointer** (`:105`).
3. `EncodeBuffer2` (`dng_encoder.cpp:455-483`): builds `EncodeItem{mem, size, info, lomem, losize, loinfo, metadata (copied ControlList), timestamp_us, index_++, folder, 0, clip_ceiling_gen_}` under `encode_mutex_`, pushes to `encode_queue_` (unbounded `std::queue`, `dng_encoder.hpp:535`), `frames_in_flight_++`. **No pixel copy on the main thread or the completion thread.**
4. Encode worker: pops FIFO (`:2025-2034`), TC bookkeeping (`:2039-2138`), RAM permit (`:2172-2176`), pooled buffer (`:2178-2196`), optional ≤2 s wait for the take's WhiteLevel (`:2212-2234`, only when this frame is not the take's first), `dng_save(num, mem_buf, encode_item.mem, ...)` (`:2239-2250`) — **the camera buffer is the source operand on the encode worker**.
5. After `dng_save` returns: DiskItem pushed (`:2280-2295`), then `input_done_callback_(nullptr)` (`:2304`) → `encodeBufferDone` pops the **front** of `encode_buffer_queue_` ("just assuming everything is done in order", `cinepi_recorder.hpp:158-174`) → last reference dropped → `queueRequest` → `DMA_BUF_SYNC END|READ` per buffer, `request->addBuffer`, `camera_->queueRequest` (`rpicam_app.cpp:975-1028`).

Answers:

| Question | Answer | Status |
|---|---|---|
| Is the camera buffer held while encoding? | **Yes.** Held from `EncodeBuffer` until the encode worker finishes `dng_save` for that frame (plus the Msg holder until the end of the loop iteration `cinepi_raw.cpp:465`, plus the DRM preview holder for the lores half). **Not** held during the disk write. | confirmed |
| How many requests in flight? | `--buffer-count` → stream 0 `bufferCount` (`rpicam_app.cpp:630-632`), raw copies it (`:657`); one Request per stream-0 buffer (`:1189-1202`). Cinemate exfat/ntfs: **10**; ext4/default: 8; bare cinepi-raw: 6. | confirmed |
| Who holds how many? | Up to `buffer_count` requests can sit in `encode_queue_` + mid-encode. Nothing in cinepi-raw caps that; the only cap is libcamera running out of buffers. | confirmed |
| When is a request requeued? | When the last `CompletedRequestPtr` drops: for a recorded frame, after `dng_save` (encode worker). Idle frames: at the end of the main-loop iteration / preview done. | confirmed |
| DMA sync | START\|READ on completion (`:1225`), START\|RW + END\|RW in `EncodeBuffer` on the main thread, END\|READ on requeue (`:1008`). `BufferReadSync` does no ioctl (`buffer_sync.cpp:54-72`). | confirmed |
| Buffer memory | app-allocated from `/dev/dma_heap/vidbuf_cached` (cached system heap on Pi 5), `core/dma_heaps.cpp:22-28`; mmap PROT_READ\|WRITE MAP_SHARED `rpicam_app.cpp:1159`. | confirmed |

Hazard (**probable**, source-only): with 4 encode workers finishing out of order, `encodeBufferDone`'s front-pop returns the wrong frame's buffer to libcamera while another worker may still be reading it. Holder count is right, identity may be wrong. Tearing risk, not a drop mechanism; window bounded by the queued-request depth (≤ buffer_count−1 frame periods).

## 4. Copies per frame

| Path (`dng_save`, `dng_encoder.cpp:1116-2008@63a08d5`) | Passes over the pixel data on the encode worker | Then |
|---|---|---|
| 16-bit unpacked (Clear HDR 16-bit, `write12bit_`/`write10bit_` false, no log) | **1**: per-row `write_pod(buf, raw + y*stride, rowBytes)` = memcpy into the pooled buffer (`:1425-1433`; `ifd_builder.hpp:173-181`) | 1 `write()` (kernel copy into page cache) |
| 12-in-16 SDR → packed 12 (`write12bit_`) | 1 pack pass `pack_row_16_to_12bit` into a thread_local row scratch, then `write_pod` of the packed row (`:1313-1323`) → 2 row-sized passes, 1 frame-sized output | 1 `write()` |
| PiSP COMP1 → packed 12 | `unpack_pisp_comp1_row_to_packed12` (decode 8 px per 8-byte block via 1024-entry dequant LUTs, pack) into row scratch + `write_pod` (`:1266-1276`; `dng_pack.hpp:316-454`) | 1 `write()` |
| COMP1 → packed 10 (`write10bit_`) | `unpack_pisp_comp1_row_to_packed10` (rounds, `dng_pack.hpp:456-489`) (`:1278-1296`) | 1 `write()` |
| COMP1 → 16 verbatim | `unpack_pisp_comp1_row_to_16` + `write_pod` (`:1297-1309`) | 1 `write()` |
| **CineMate Log** (`log_lut_` non-null) | per row: (a) normalise to right-justified uint16 (`unpack_pisp_comp1_row_to_16` / `unpack_csi2_raw12` / `right_justify_row` by `log_src_shift_`=4 for 12-in-16, or in place for 16-bit), (b) `log_lut_->encode_row` (one table lookup per sample, in place, `log_lut.hpp:297-301`), (c) `pack_row_12bit`/`pack_row_10bit`, (d) `write_pod` (`:1210-1263`) → up to 4 row passes | 1 `write()` |
| Thumbnail (modes 1-3) | lores YUV420 → Y or RGB rows into `thumbRow`, mode 3 through libjpeg (`:1795-1979`) | same `write()` |

First frame of each take additionally samples every 3rd row for the ClearHDR clamp detector inside the same loops (`kRowStride = 3`, `:1167`; `ceiling_det.add_row`).

So: **one user-space pass per frame on the 16-bit path (a memcpy), one frame-sized output buffer, one kernel copy.** All work is on the encode worker, none on the completion or main thread.

## 7. How a dropped frame is detected and counted

| Counter | Meaning | Where incremented | Reset | Published |
|---|---|---|---|---|
| `dropped_frames_` ("droppedFrames") | **capture gap**: sensor-timestamp delta between consecutive *encoded* frames rounds to ≥2 frame periods → `+= raw_elapsed − 1` | `dng_encoder.cpp:2126-2135` (encode worker, under `encode_mutex_`, FIFO order, from `encode_item.timestamp_us` = libcamera `SensorTimestamp`) | per take `resetFrameCount()` `dng_encoder.hpp:141` | `cinepi_controller.cpp:642` |
| `write_failures_` ("writeFailures") | open failure, short write, or close error | `:2365, :2376, :2382` | per take `hpp:142` | `:643` |
| `frames_in_flight_` ("framesInFlight") | capture → written gauge: `++` in `EncodeBuffer2` (`:480`), `--` after disk close (`:2389`), alloc fail (`:2188`), dng_save throw (`:2263`) | — | **not** reset (cross-take, `hpp:144-151`) | `:646` |
| `buffer_hwm_` ("bufferSizeMax") | peak `disk_buffer_` depth since last publish | `noteBufferDepth` at `:2294` | each publish | `:645` |
| `bufferSize` | instantaneous `disk_buffer_.size()` | `hpp:194-196` | — | `:644` |
| "Frame Drop!!!!!" | LOG(1) when measured fps deviates >1 from `FrameDuration` | `cinepi_recorder.hpp:92-96` | — | stdout only |
| "RAM pool exhausted — recording stopped" | pool permits at cap−2 → take ended | `cinepi_raw.cpp:442-452` | — | warn log; redis `is_recording` flips |

Conclusions (**confirmed** from the above):
- A "drop" in cinepi-raw's stats is **only a capture gap**. There is no counter for "disk too slow"; slowness becomes `bufferSize` growth, then blocked encode workers, then a camera starve (which *does* then show as `droppedFrames`), then the pool-exhausted stop.
- Pool exhaustion is not counted as a drop; it ends the take.
- A `posix_memalign` failure or a `dng_save` throw drops the frame **with no counter** (only `frames_in_flight_` is balanced) (`:2186-2196`, `:2252-2276`).
- A frame libcamera never delivered while *not* recording is not counted anywhere.
- Cinemate consumes `droppedFrames` as "Tier 1 – unbiased hw counter" (`cinemate/src/module/redis_listener.py:1003-1026@4990afc`), `writeFailures` (`:873-880`), `framesInFlight` → `is_writing_buf` (`:950-984`).

## 8. COMP1 decode and 10/12-bit packing — which thread, cost

- Thread: all in `dng_save` on the **encode worker** (`dng-enc-N`). Nothing is decoded on the main or completion thread. Confirmed (`dng_encoder.cpp:1264-1309`).
- Decision: `resolve_dng_output_depth(container, sensor_bits, trusted, packed, compressed)` (`cinepi/dng_output_depth.hpp:70-128@63a08d5`): container 16 + trusted + sensor 12 → pack12; sensor 10 and not CSI2-packed → pack10; sensor 16 → verbatim 16. COMP1 keeps pack12 (branch at `:1264`).
- COMP1 decoder (`cinepi/dng_pack.hpp:316-454`): one 8-byte block → 8 px; two 32-bit sub-blocks; 4 dequant LUTs of 1024 × uint16 (8 KiB total, built once at static init); per block ~20 integer ops + 8 LUT loads + offset add; then `pack_row_16_to_12bit` on the 8 decoded samples. "Decoder logic adapted from Apertar-Core's MIT-licensed CdngEncoder" (`dng_pack.hpp:313-314`) — so the arithmetic is the same as Apertar's.
- Cost: not measured in the handbook for COMP1 specifically. Measured for the whole `dng_save` at 4K 16-bit log: thumbnail +4.0 ms = +18 % → `dng_save` ≈ 22 ms/frame with JPEG thumb, ≈ 18 ms without, on one encode worker (`cinepi_controller.cpp:35-39`; handbook 2026-09-13). **Probable** that a 4K COMP1 → packed12 frame costs less than the log path and more than the 16-bit memcpy. **Unconfirmed**: run a take at `log_level debug` and read "Time taken for the encode: {} ms" (`:2300-2301`).
- Note on 4K 50 fps 12-bit SDR under Cinemate: Cinemate launches with packing `P` for most sensors → libcamera PiSP turns it into COMP1 (`dng_output_depth.hpp` comment; commit `96f7a2a`), so the 50 fps path is **COMP1 decode + pack12 on 4 encode workers sharing CPUs 1-2**, output 12,441,600 B/frame = **622 MB/s** to disk plus thumbnail. Whether the imx585 4K 12-bit mode is launched as `P` (COMP1) or `U` (unpacked) is decided in cinemate's `sensor_detect`/`cinepi_multi` and was **not checked here**.

## 9. The log encode — which thread

- Resolved once per take in `setup_encoder()` (`dng_encoder.cpp:744-908`): source depth from `sensor_mode_bit_depth_` (snapshot, not `bf.bits`), target from `--log-encode` (10 or 12); refuses (records linear, warns "CineMate Log off for this mode") when no spec, depth mismatch, or black-level mismatch > one footroom code. 12-bit ClearHDR (CCMP-companded) is only valid composed with the decompand to target 10 (`get_ccmp_composed_log_lut`, `:782-795`).
- Applied per row on the **encode worker** in `dng_save` (`:1210-1263`); one lookup per sample into a 65536-entry (16-bit source) or 4096-entry (12-bit/composed) `forward_` table (`log_lut.hpp:227, 261, 287, 297-301`). The LUT is process-wide, read without a lock.
- Cost: "On a log-encoded take the LUT pass dominates dng_save() so completely that the thumbnail's whole cost is a small fraction of it" (`cinepi_controller.cpp:40-41`) — qualitative, confirmed as a code comment, not a number.
- Output: 16→12 log file is 12,441,600 B at 4K (same as packed 12 SDR), 16→10 is 10,368,000 B (handbook `04b7332` message: "16.81 → 10.51 MB (−37.5 %)").

## 10. Record start / stop; when disk is slower than capture

Record start (`cinepi_raw.cpp:413-430@63a08d5`): `create_clip_folder`, `sound.record_start()`, `resetFrameCount()` (per-take counters, new `clip_ceiling_gen_`), `reset_encoder()` (forces `setup_encoder` on the next frame: re-reads MemAvailable, re-snapshots thumbnail/log). **Nothing is dropped and nothing is flushed**: the previous take's `encode_queue_`/`disk_buffer_` keep draining to their own folder (comment `:414-421`; `b76e3e7`). The interlock is on Cinemate's side: `start_recording` refuses while `_buffered_frames_flushing()` (`is_writing_buf`/`is_buffering` redis keys) — `cinemate/src/module/cinepi_controller.py:2208-2215, 2330-2339@4990afc`; the same gate holds back a mode-change relaunch (SIGTERM) (`:2385-2390`).

Record stop (`cinepi_raw.cpp:431-434`): `folderOpen = false; sound.record_stop();` — **no drain, no flush, no fsync, no wait.** The encoder keeps working; `framesInFlight` falls to 0 when the last disk worker closes its file. Cinemate shows green `is_writing_buf` while `framesInFlight > 0 && !is_recording` (`redis_listener.py:963-984, 1439`). Drain time = backlog × per-file write time, unbounded. Data reach the medium on the kernel's writeback schedule (`vm.dirty_*`, set by Cinemate at mount per the kb digest — not re-checked here).

When the disk is slower than capture (chain, **confirmed** from the code; order of events):

1. `disk_buffer_` grows; RAM permits are consumed (17 MiB each at 4K 16-bit). `bufferSize`/`bufferSizeMax` rise. Nothing else happens until ≈0.9 × MemAvailable is used (≈173 frames ≈ 6.9 s at 25 fps on 4 GB).
2. Cinemate's `_recording_worker` polls `buffer / buffer_size` at 4 Hz and auto-stops at **90 %** fill (`BUFFER_LIMIT_PERCENT = 90`, `cinepi_controller.py:355, 4064-4096`), or at 80 % system RAM.
3. If the stop has not landed yet: encode workers block on `ram_cv_.wait` holding camera buffers; `encode_queue_` grows; libcamera runs out of its 10 buffers after ≤10 frames; the CFE starves; frames stop arriving → `droppedFrames` counts the gap when frames resume.
4. Main loop: `buffer_full()` (cap−2) → `setRecording(false)` "RAM pool exhausted".

Hardware evidence for this chain: 2026-08-27/28, 16-bit soaks on NTFS (`fuseblk`) at ~355 MB/s "stalled after ~15-22 s: the RAM pool (173 frames ≈ 2941 MB) fills and frames stop arriving — cleanly, no corruption" (`hardware-log.md:963-967`). **Confirmed** (measured). There is **no** equivalent long-take measurement on exFAT in the handbook (grep for exFAT soak: none).

## 14. Leads (for the synthesizer)

Each lead: mechanism, evidence, how to test.

### Candidate causes of the residual Apertar drops (where cinepi-raw differs)

L1. **Back-pressure location** (cause / improvement). cinepi-raw never drops a frame at the writer: encode workers **block** on a RAM permit sized at 0.9 × MemAvailable (≈173 frames on 4 GB), so a disk stall of several seconds is absorbed in RAM and the only frame loss is a camera starve after the pool is gone. Apertar's 12-frame queue (`drop[queue-full]`) gives ≈0.5 s. Evidence: `dng_encoder.cpp:1079-1082, 2172-2176`; `hardware-log.md:963-967` (NTFS soak absorbed 15-22 s). The kb's drop-frames README says a `buffer=ram` mode now exists in Core (0.6 × MemAvailable − 512 MiB) — **not verified by me in Apertar-Core source**; the synthesizer should check it is on in the failing takes. Test: compare `drop[queue-full]` and `peak_queue` with `buffer=ram` vs `frames` on the same exFAT drive.

L2. **Camera buffer held during encode, not during write; no copy on the completion thread** (cause, probable). cinepi-raw's completion thread does ~nothing (2 ioctls, a struct copy, a pthread_create); the full-frame read happens on 4 encode workers on CPUs 1-2, and the buffer returns to libcamera right after that. Apertar (per kb digest) copies on the completion thread and counts `drop[copy-slot]` when the copy worker holds `buffers−2` requests. Writeback bursts (kernel flusher, exFAT cluster allocation stacks seen 2026-10-30) stall whichever thread touches the page cache or faults memory; in cinepi-raw that is never the completion thread. Test: `perf sched` / `trace-cmd` on the completion thread during a 4K25 take with and without `APERTAR_DNG_WRITEBACK`.

L3. **Camera buffer count**: cinepi-raw runs 10 raw buffers on exFAT (8 on ext4; 6 bare) → 400 ms of CFE cushion at 25 fps, 200 ms at 50 fps. Apertar: 4 SDR / 8 ClearHDR (+2 only for FAT/NTFS, 0 for exFAT per kb). At 4K50 12-bit SDR Apertar has 80 ms of cushion. Evidence: `storage_profiles.py:82, 93`; `rpicam_app.cpp:630-632, 657`; kb drop-frames README line 178. Test: `APERTAR_RAW_CAMERA_BUFFERS=10` at 4K50 12-bit, count `capture-gap`.

L4. **No sync of any kind during the take** in cinepi-raw (no `sync_file_range`, no 1 s fsync, no DONTNEED since `b71ec67` 2026-03-06). Apertar's A2 run (no per-frame `sync_file_range`) lost 10 % at capture, so simply removing the hint is **not** the answer in Apertar's chain — the difference must be elsewhere (L1-L3), or in the kernel knobs Cinemate sets at mount (not re-checked here). Evidence: `dng_encoder.cpp:2351-2379`, `b71ec67` diff. Test: Apertar A2 configuration **plus** cinemate's `vm.dirty_*`/`nr_requests` values on the same drive; if A2 then runs clean, the writeback knobs are the lever, not the per-frame hint.

L5. **One `write()` per frame of the whole DNG** from a 4 KiB-aligned buffer (4 syscalls/frame) vs Apertar's ~40 syscalls/frame (kb drop-frames README line 181). On exFAT each write extends the file by whole 128 KB clusters; many small writes mean many `exfat_get_block → exfat_alloc_cluster` entries per frame. **Unconfirmed** that this matters: `strace -c -f` both processes for one minute and compare syscall counts and time in `write`.

L6. **Four encode workers for the pack/decode work**, pinned off CPU 0 and CPU 3; whole process `taskset -c 1-3` so libcamera and the main loop also stay off the IRQ core. Apertar's worker placement is unknown to me. Test: `ps -L -o pid,tid,psr,comm` during a take on both.

### Things cinepi-raw does worse (so the comparison is fair)

F1. It **did** drop frames at 4K 16-bit ClearHDR in Sept 2026 (208 drop events 2026-09-15; "102 drops in 20 minutes" earlier) — cause: the ccmpPreview post-process stage re-rendering the lores frame (35 ms/frame at 12-bit, 22 ms at 16-bit on a detached thread). Fixed for 16-bit by `ea53b2c`; 12-bit still renders twice ("survives on a thinner margin than is comfortable", `hardware-log.md:3200-3203`). So "cinemate never dropped" is **not** true for 4K 16-bit before 2026-09-15, and a 12-bit ClearHDR take still carries a 35 ms/frame stage.

F2. **No measurement exists of a long exFAT take at 4K25 16-bit in cinepi-raw.** The only soak is NTFS (stalled). The 2026-09-13 benchmark (zero drops, disk queue ≤2) was 4K 16-bit ClearHDR Log 12 — i.e. a 12.4 MB/frame output, not 16.6 MB — duration not stated in the code comment. **Unconfirmed**: the operator's belief for 4K25 16-bit linear on exFAT needs a cinepi-raw 10-minute take with `droppedFrames`, `bufferSizeMax` and the "RAM pool" line recorded.

F3. cinepi-raw cannot see a slow disk until the pool is gone: no deadline, no per-frame timing at info level (encode/disk ms are `debug`, and Cinemate never sets `log_level`), and a `posix_memalign` failure or a `dng_save` throw drops a frame with **no counter**.

F4. Record stop does not flush or fsync; a pulled drive loses up to the kernel's `dirty_expire` worth of frames and the exFAT directory entries (0-byte files) — Apertar's folder/file fsync tick exists exactly for that (C0010).

F5. Per-frame costs cinepi-raw carries that Apertar may not: a synchronous Redis pipeline on the capture thread per frame; a formatted "DNG written:" line to a pipe per frame that Python regex-scans; a detached pthread per frame; a JPEG thumbnail (+4 ms) per frame; the WhiteLevel 2 s wait design on non-first frames (normally microseconds once frame 0 publishes).

F6. `encodeBufferDone` returns the FIFO-front buffer regardless of which worker finished (probable tearing hazard with 4 workers).

F7. Nice values do not apply (EPERM); the whole process may run SCHED_FIFO 70 instead (probable), which puts disk workers above every other process on the box.

### Assessments

A1. **Pre-roll** (cinemate `storage_preroll.py`, a 2 s take at max fps, deleted): on the cinepi-raw side its code-grounded effects are (a) `setup_encoder` runs and the pooled buffers it allocates stay in `buffer_pool_` for the real take if `buffer_size` is unchanged (same mode and bits; a different fps does not change `buffer_size`) — so the first ~N 17 MiB buffers are pre-faulted (`acquirePooledBuffer` `:2407-2432`); (b) exFAT allocation bitmap / FAT pages for the folder get cached. Neither is measured; the kb says the effect on the next take's drops was never measured. **Unconfirmed**: A/B with pre-roll on/off, 10 takes each, count first-second drops.

A2. "Did the latest Apertar changes make recording better" — outside R1's scope (no Apertar logs read here).
