### a.3 Conclusions for the exFAT side (labelled)

| # | Conclusion | Status | Why / how to test |
|---|---|---|---|
| C-a1 | On a plain mount nothing in the exFAT allocation path waits for a metadata **write**; the only blocking I/O in `exfat_alloc_cluster`/`exfat_write_inode` is a **synchronous read** of a FAT block or directory sector that is not in the buffer cache (a4, a5, a7). The kb's stack dumps (`exfat_ent_set > __bread_gfp`, `exfat_write_inode > __wait_on_buffer`) are exactly these reads waiting on a stalled device. | confirmed (mechanism); the stall itself is the drive's | `iostat -x 1 nvme0n1` during a take: any `r/s > 0` on a pure-write workload is a metadata miss; `blktrace`/`biosnoop` shows the 4 KiB reads. |
| C-a2 | `exfat_ent_set` is only reached when a file is a FAT chain (a10, a13). A FAT chain appears when the next free cluster is not the next cluster of the file, i.e. **after `clu_srch_ptr` has wrapped once around the volume and allocations land in holes left by deleted files**, or when another file was created concurrently (directory growth, pre-roll take, sidecar files). The kb's "after about 0.9 TB written" coincides with one pass of a 917 GiB volume → the FAT reads (and the trim starvation) both start at the wrap. Cannot separate the two from the kb data. | probable | Fill a trimmed volume once (wrap), then `fstrim` and record again: if drops/stalls persist with reads in `iostat`, fragmentation is the driver; `filefrag -v <dng>` (extents > 1 = FAT chain; exFAT reports via FIEMAP) on files written after the wrap. |
| C-a3 | After a remount the cursor restarts at cluster 2 (a12): the first takes after boot fill the **oldest holes at the front of the volume** even if the tail is free → fragmentation right after boot on a volume that has had deletes. | confirmed (code) + probable (effect) | Compare `filefrag` of the first take after boot on a volume with deleted takes vs a freshly formatted one. |
| C-a4 | Directory lookup cost grows linearly with the number of entries ever created in the directory (a17, a18, a16): each frame-file create = 1 miss scan of all used+deleted dentries, one `sb_bread/brelse` pair per 32 B, under `s_lock` which every `exfat_get_block` (data write mapping) also needs. Estimate ≈100–200 ns per entry → 60k entries ≈ 6–12 ms, 120k ≈ 12–24 ms per create, holding `s_lock`. At 50 fps (20 ms budget) a 30 000-file take approaches 100 % of the frame period in the last minutes. **O(N²) per take.** | probable (estimate; code confirmed) | `perf record -g` on Apertar in the last minutes of a long take → share of `exfat_find_dir_entry`/`__find_get_block`; or `strace -T -e openat` → open latency vs frame index; or ftrace `function_graph` on `exfat_lookup`. Mitigation A/B: new subdirectory every 1000 frames, or per-take directory already in use + split. |
| C-a5 | Never use the `discard` mount option with frame-per-file exFAT (a15, a.2): deleting one 10-min take = ~2 M synchronous discard commands. FITRIM coalesces free runs (a23). Core's current choice (fstrim at mount / after deletes) is right, **but `exfat_trim_fs` holds `bitmap_lock` for the whole walk → no cluster can be allocated or freed while it runs** → a trim must never overlap a take (a23). | confirmed | Measure `fstrim -v /media/RAW` duration on the 917 GiB volume; ensure Core blocks record-start until it returns. |
| C-a6 | Apertar's 1 s fsync is a whole-device metadata flush + NVMe FLUSH each second (a8). On a DRAM-less drive a FLUSH forces the controller to commit its SRAM write buffer; cost unknown on this drive. A0 vs A1 in the kb showed no visible difference in 10-min takes, so this is a cost without a demonstrated benefit for drop rate. | confirmed (mechanism) / unconfirmed (cost) | `nvme smart-log` + `biosnoop` to time FLUSH; A/B A0 vs A1 on a near-full, wrapped volume. |
| C-a7 | If anything on the camera calls `sync()`/`syncfs()` during a take, each call costs 2 FUA+PREFLUSH boot-sector writes via VOLUME_DIRTY toggling (a9) plus `sync_blockdev`. | confirmed (mechanism) / unconfirmed (whether Apertar does) | `grep -rn "syncfs\|sync()" Apertar-Core/src`; `strace -f -e sync,syncfs`. |
| C-a8 | `errors=remount-ro` (default) turns the whole volume read-only on the first fs error, e.g. an I/O error during an NVMe controller reset → every later frame write fails until remount. `errors=continue` would keep writing after the device returns. | confirmed (default) / probable (effect) | Inject: `echo 1 > /sys/block/nvme0n1/device/reset_controller` during a test take; observe `mount | grep RAW` for `ro`. |
| C-a9 | 1 MiB clusters: 8× fewer allocation calls, 8× fewer FAT entries for chained files, holes 8× coarser (a 16.9 MB file needs 17 contiguous MiB instead of 132 × 128 KiB), at the price of ~7.5 GB slack per 10-min take (a.2). Since Apertar files are all the same size, holes from deleted takes are exact-fit at either cluster size; the pre-roll take (different length) and sidecars create odd holes. | probable | Format two cards (128 KiB vs 1 MiB), run the wrap test of C-a2, compare `filefrag` extent counts and `iostat` reads. |

| e9 | Why per-file `sync_file_range(WRITE)` + small `dirty_bytes` keeps the system responsive: it bounds the dirty set (e6 pauses never trigger), keeps `Writeback` short-lived (e8 waits short), and spreads device queue usage evenly instead of 30-s bursts from the periodic flusher (e6 defaults). The kb's A2 result (no per-frame `sync_file_range` → 10 % capture-gap drops, queue never full) is consistent with the flusher's 5-s cadence producing multi-hundred-MB write bursts that starve the copy/requeue path, not with queue-full. | probable | A/B `vm.dirty_bytes=67108864 vm.dirty_background_bytes=16777216` with and without per-frame `sync_file_range`; watch `grep -E "Dirty|Writeback" /proc/meminfo` at 10 Hz during a take. |

**Lead for Apertar (from e3/e4):** the DONTNEED call should be issued for a file **only after its writeback completed** (e.g. `sync_file_range(fd, 0, 0, WAIT_BEFORE|WRITE|WAIT_AFTER)` on file N-2 from the writer thread, then `posix_fadvise(DONTNEED)`), or on file N-k when the earlier WRITE is known to have finished. As coded today (if DONTNEED follows WRITE immediately) every frame pays a global `lru_add_drain_all` (e4) and frees nothing. How to test: `perf trace -e syscalls:sys_enter_fadvise64 --duration` or `bpftrace` on `lru_add_drain_all` call count/latency during a take; count should drop to ~0 after the change; also `/proc/meminfo` `Cached` should stop growing.
