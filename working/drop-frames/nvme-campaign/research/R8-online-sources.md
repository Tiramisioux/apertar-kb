Labels are never upgraded: a vendor spec sheet number is **web** even when it is "official".

Snippet-sourced numbers are marked **web (snippet)**; numbers from pages fetched in full are marked **web (fetched)**.

**Derived / probable for 512 GB post-cache write.** The 2 TB drive has 4× the NAND dies of the 512 GB drive (E18 + 512 Gb B47R dies: 8 dies at 512 GB vs 32 at 2 TB — die count itself is **probable**, from the NAND density, not from a teardown). TLC program bandwidth scales roughly with die count, so a 512 GB post-cache write of roughly **0.4–0.8 GB/s** is **probable**; that is at or *below* the Pi's Gen 3 x1 link rate (§3.1). Rated 3,900 MB/s write already signals the smaller die count. If a take exceeds the dynamic pSLC window (~176 GB on an empty drive; smaller as the drive fills, because the cache is ~1/3 of *free* TLC — the "dynamic" behaviour is **web (snippet)** from Tom's), write throughput could fall below link rate. The recorder's sustained bitrate must be compared against ~0.4 GB/s, not against 3.9 GB/s. Treat this as the main open measurement for the KC3000.

**Derived endurance arithmetic.** 400 TBW / 512 GB ≈ 781 full-drive writes; at e.g. 100 GB written per day the rating lasts ≈ 4,000 days (≈ 11 years). (Inputs: web TBW; arithmetic exact.)

**Derived endurance arithmetic.** 600 TBW / 1 TB = 600 full-drive writes.

**HMB dependence on the Pi (derived from §3.2).** Raspberry Pi kernel 6.12.y boots with `nvme.max_host_mem_size_mb=0` from the device tree, so on the camera the E21T/E27T run **without HMB** unless cmdline.txt overrides it. Effect of no HMB on a DRAM-less drive: the L2P (FTL mapping) cache lives only in controller SRAM, so random/mixed I/O and mapping-heavy workloads lose performance; large sequential writes are least affected (**probable**; general DRAM-less/HMB behaviour, not measured on these drives). One Pi-forum user measured no HMB performance gain on their drive and noted HMB consumed CMA (web, snippet: https://forums.raspberrypi.com/viewtopic.php?t=385934). The E21T's 64 MB HMB request equals the Pi's default 64 MB CMA pool — exactly the exhaustion the Pi kernel commit describes (§3.2) — **derived** from the two numbers.

**What the CFe-B adapter changes thermally (derived/probable; no controlled copper-vs-aluminium test exists online as far as I found):**
1. The 2230 board is sealed in a ~38.5×29.8×3.8 mm metal shell. Convective cooling of the component side is removed; the only heat path is thermal pad/paste → shell → whatever the shell touches (camera card cage, or a CFe-B socket/adapter on the Pi). Several listings ship without the pad/paste; buyers add one — contact quality is the dominant variable (**probable**).
2. The shell adds thermal mass, which *delays* throttling onset but *raises* steady-state temperature compared with a bare 2230 on a HAT under the Pi's active cooler (**probable**).
3. On the Pi the drive runs at Gen 3 x1 (≤ ~0.9 GB/s) instead of Gen 3 x2 in a camera (≤ ~2 GB/s), so NAND-program power — and therefore heat — is roughly halved at full link rate (**derived** from throughput ratio; assumes power ∝ throughput, **probable**). In-camera 8K-throttling anecdotes therefore overstate the Pi case.
4. The MP600 Mini's thermal limit is ~80 °C (web, snippet) while its *spec* operating range ends at 65 °C; the shell's outer temperature will sit between ambient and the controller temperature — so a shell reading of ~55–60 °C implies a controller near spec limit (**probable**, no transfer coefficient available).
5. Whether the Apertar's CFe-B socket is a passive PCIe x1 adapter and how the socket conducts heat is **unconfirmed** here (KB question, not a web one).

**Synthesis (derived).** Practical Gen 3 x1 writes cluster at ~760 MB/s (range 720–780), reads ~800–900 MB/s. Both drives' pSLC write speeds (≥3.2 GB/s) are far above this, so during a take the link is the bottleneck and pSLC-vs-TLC differences are masked *as long as* post-cache TLC speed ≥ ~0.8 GB/s: true for the MP600 Mini (~800 MB/s, marginal), **unknown and probably not true** for the 512 GB KC3000 (§1). At Gen 2 x1 (~450 MB/s practical) both drives' post-cache speeds exceed the link.

### 3.2 `nvme.max_host_mem_size_mb` (HMB) on the Pi kernel

- Upstream default is 128 MiB: `static unsigned int max_host_mem_size_mb = 128;` with description "Maximum Host Memory Buffer (HMB) size per controller (in MiB)" — **measured** from https://raw.githubusercontent.com/raspberrypi/linux/rpi-6.12.y/drivers/nvme/host/pci.c (HMB allocation code is active, not `#if 0`, on rpi-6.12.y).
- December 2024: Raspberry Pi commit 4263812 "nvme-pci: Disable Host Memory Buffer usage" (Phil Elwell) wrapped `__nvme_alloc_host_mem()`/`nvme_alloc_host_mem()` in `#if 0`; message: "Some NVME drives seem to request significant amounts of DMA coherent memory" … "enough to exhaust our standard 64MB CMA allocation." … "Try disabling the feature to see what effect it has - drives should continue to function without it." Linked issue #6504 (a CMA-exhaustion audio bug: "cma: cma_alloc: linux,cma: alloc failed, req-size: 4 pages, ret: -12"; Pi 5 "CmaTotal: 65536 kB"). **web (fetched)**: https://github.com/raspberrypi/linux/commit/4263812f0e010a193c6654f75eda49220066bd57 ; https://github.com/raspberrypi/linux/issues/6504 .
- May 2025: PR #6844 "nvme-pci: Re-enable NVME Host Memory Block (HMB) support" (altserg; approved by P33M, merged offline by pelwell 2025-05-09; shipped in the 6.12.28 firmware bump 2025-05-14) reverted the `#if 0` and instead set the **default kernel command line on Pi 4/5 to `nvme.max_host_mem_size_mb=0`**, so users can opt in via cmdline.txt (and raise CMA with `dtoverlay=vc4-kms-v3d,cma-<size>`). **web (fetched)**: https://github.com/raspberrypi/linux/pull/6844 .
- Current device trees (**measured**): rpi-6.12.y `bcm2712-rpi.dtsi` chosen bootargs end with `nvme.max_host_mem_size_mb=0`; rpi-**6.18**.y `bcm2712-rpi.dtsi` ends with `nvme.max_host_mem_size_mb=32`. https://raw.githubusercontent.com/raspberrypi/linux/rpi-6.12.y/arch/arm64/boot/dts/broadcom/bcm2712-rpi.dtsi ; https://raw.githubusercontent.com/raspberrypi/linux/rpi-6.18.y/arch/arm64/boot/dts/broadcom/bcm2712-rpi.dtsi . Board files (`bcm2712-rpi-5-b.dts`, `bcm2712-rpi-cm5.dtsi`) have no `chosen` node, so the CM5 inherits the same default (**measured**).
- Why people set it to 0 / which drives: DRAM-less drives request HMB (E21T: 64 MB, §2); Pi 5 users saw "failed to allocate host memory buffer" (kernel 6.12.15) and a HA guide raised CMA 64→96 MB to cure HMB errors — **web (snippet)**: https://forums.raspberrypi.com/viewtopic.php?t=385934 ; https://jbsoft.nl/site/home-assistant-on-raspberry-pi-5-with-nvme-pcie-ssd/ . Effect of no HMB on a DRAM-less drive: see §2 (**probable**).
- Camera implication (**derived**): on 6.12.y the MP600 Mini runs HMB-less by default; a later move to 6.18.y silently turns a 32 MB HMB on (and may carve 32 MB out of the 4 GB CM5's CMA/coherent pool).

### 3.3 `nvme_core.default_ps_max_latency_us=0`, `pcie_aspm=off`, "Disabling device after reset failure"

- Kernel text (**measured**, same pci.c): `"Disabling device after reset failure: %d\n"` is a `dev_warn` at the `out:` label of `nvme_reset_work()`; it fires when `nvme_pci_enable()`, `nvme_init_ctrl_finish()`, `nvme_setup_host_mem()`, `nvme_setup_io_queues()` or the transition to LIVE fails; the controller is then set DELETING and `nvme_dev_disable(dev, true)` runs — the block device disappears. `-19` is `ENODEV` (derived). The hint "Does your device have a faulty power saving mode enabled?" / "Try \"nvme_core.default_ps_max_latency_us=0 pcie_aspm=off pcie_port_pm=off\" and report a bug" is printed by `nvme_warn_reset()` only when `CSTS == ~0` (device unreachable on the bus).
- `nvme_core.default_ps_max_latency_us=0` disables APST (autonomous power-state transitions) — consequence: higher idle power, no deep-sleep link glitches (**derived** from the parameter's documented purpose). `pcie_aspm=off` disables Active State Power Management (L0s/L1) on the link. The Pi 5 DT already applies `aspm-no-l0s` to the RP1 link (`&pcie2`) but *not* to the external `pciex1` unless `dtparam=pciex1_no_l0s` is set (**measured**, dtsi above).
- Pi 5 field reports (all **web, snippet**): a 6.12-kernel "survival guide" where `pcie_aspm=off` + `default_ps_max_latency_us=0` + forcing Gen 2 stabilised the link but reads still produced I/O errors under load (https://medium.com/@eddieoz/the-nvme-ghost-in-the-machine-a-raspberry-pi-5-kernel-survival-guide-0f243b9720a3); a March 2026 blog where the fix was capping `dtparam=pciex1_gen` to a lower generation (https://blog.michael.kuron-germany.de/2026/03/raspberry-pi-5-losing-pcie-link-to-nvme-ssd/); forum threads on drives going offline randomly (https://forums.raspberrypi.com/viewtopic.php?t=382183 ; https://forums.raspberrypi.com/viewtopic.php?t=383253 ; https://forums.raspberrypi.com/viewtopic.php?t=395256 ; https://forums.raspberrypi.com/viewtopic.php?t=372811 ; https://dietpi.com/forum/t/raspberry-pi-5-nvme-problems-new-install/21851). Responders repeatedly point to FFC seating, PSU capacity and heat as the real causes.
- GitHub issue search for the phrase in raspberrypi/linux (**web, fetched** search page https://github.com/raspberrypi/linux/issues?q=%22Disabling+device+after+reset+failure%22) returns #7635 (open, 2026-09-21: NVMe behind a PCIe switch port lost since 6.18.39 / 6.12.96, Target-Speed quirk) and #6821 (closed, 2025-05-09: ASM1806 switch). Neither is a plain M.2-HAT case.
- **Separate, serious 6.18 bug (web, fetched)**: silent NVMe data corruption on rpi-6.18.y (6.12.y clean) from a DMA-unmap bug in `nvme_free_sgls` on the non-cache-coherent BCM2712; affects drives that advertise SGL support (Biwin `sgls: 0x70001` corrupt; Crucial P5 Plus `sgls: 0` clean — "5/5 with drives that don't support sgls"); corruption in 64-byte runs, no dmesg errors; workaround `nvme.sgl_threshold=0`; fix PR #7500 merged to rpi-6.18.y 2026-07-14. https://github.com/raspberrypi/linux/issues/7496 ; https://github.com/home-assistant/operating-system/issues/5005 . Default `sgl_threshold = SZ_32K` (**measured**, pci.c). Campaign implication (**derived**): stay on 6.12.y or a 6.18.y ≥ the 2026-07-14 fix; whether the KC3000/MP600 Mini advertise SGLs is **unconfirmed** (`nvme id-ctrl | grep sgls` on the camera would tell — not run here).

### 3.4 CM5 "Voltage normalised" kernel messages

- Emitted by `drivers/hwmon/raspberrypi-hwmon.c` (**measured**, rpi-6.12.y: https://github.com/raspberrypi/linux/blob/rpi-6.12.y/drivers/hwmon/raspberrypi-hwmon.c): `dev_crit(..., "Undervoltage detected!\n")` and `dev_info(..., "Voltage normalised\n")`; the driver polls `RPI_FIRMWARE_GET_THROTTLED` every 2 s (`schedule_delayed_work(..., 2 * HZ)`), passing `0xffff` to clear sticky bits, tests `UNDERVOLTAGE_STICKY_BIT BIT(16)`, logs only on a state change and raises `hwmon_in_lcrit_alarm` (`in0_lcrit_alarm` in sysfs). The messages contain no voltage; the firmware returns a flag, not a sample ("not a direct voltage sampling" — 6by9; **web, fetched**: https://github.com/raspberrypi/linux/issues/5584).
- Threshold: official documentation — low-voltage warning when "the supply voltage drops below 4.63 V (±5%)" on all models since the B+ (except Zero); "This will result in an entry being added to the kernel log." (**web, fetched**: https://raw.githubusercontent.com/raspberrypi/documentation/master/documentation/asciidoc/computers/raspberry-pi/power-supplies.adoc). Pi 4 detail: APX803 supervisor trips ~4.6 V, releases ~4.64 V (6by9, issue #5584). On Pi 5/CM5 the flag comes "directly from the PMIC" on "some variants" (6by9) — the exact Pi 5/CM5 PMIC threshold is **unconfirmed** online.
- Interpretation (**derived**): a "Voltage normalised" after "Undervoltage detected!" means the 5 V input at the CM5 dipped below ~4.63 V for at least one 2-s poll and recovered; `vcgencmd get_throttled` bit 0 = now, bit 16 = since boot (0x50000 = past under-voltage + past throttling; web, snippet: https://ohyaan.github.io/tips/raspberry_pi_get_throttled_undervoltage/).

### 3.5 5 V rail / under-voltage with 2280 drives on HATs

- Official power facts (**web, fetched**, power-supplies.adoc): Pi 5 recommended PSU 27 W (5 V/5 A); with a 5 A PD supply USB peripherals get 1.6 A, otherwise "restricts downstream USB devices to 600 mA"; `vcgencmd get_config usb_max_current_enable` shows the limiter state; "total power consumption can exceed these figures if additional USB devices or a HAT are attached."

Third-party boards repeat "limited to 5V/1A as per the Pi 5's PCIe interface limit" (https://electropeak.com/raspberry-pi-5-pcie-to-m-2-nvme-ssd-hat).
- Official M.2 HAT+: "Up to 3 A supply to connected M.2 devices"; supports 2230/2242 only (Compact: 2230) (**web, fetched**, m2-hat-plus/about.adoc). The page does not state the source of its 5 V; since 3 A at 3.3 V (~10 W) exceeds the FFC's 5 W, the HAT+ must draw 5 V through its GPIO stacking header (**derived/probable**). 2280 drives are therefore outside official support and sit on third-party boards whose power path is either the FFC (≤1 A/5 W) or the 40-pin header.

- CM5 IO board M.2 3.3 V budget: a garbled datasheet snippet reads "600mA Max +3.3v" (= 2 W, which would be insufficient for a KC3000's 4.1 W rating) — **unconfirmed**; the datasheet must be read directly (https://datasheets.raspberrypi.com/cm5/cm5io-datasheet.pdf).

### 4.1 Directory lookup cost in large directories
- On-disk format: 32-byte entries (`DENTRY_SIZE 32`); a file = 1 file entry + 1 stream entry + ⌈len/15⌉ name entries (max 19 entries for a 255-char name, "19 entries x 32 bytes/entry = 608 bytes"). Entry types: `EXFAT_UNUSED 0x00 /* end of directory */`, deleted = 0x01–0x7F, `EXFAT_FILE 0x85`, `EXFAT_STREAM 0xC0`, `EXFAT_NAME 0xC1`.
- Limit: `#define MAX_EXFAT_DENTRIES 8388608` ("exFAT allows 8388608(256MB) directory entries"); `exfat_find_empty_entry` refuses to grow a directory past it ("exFAT spec allows a dir to grow up to 8388608(256MB)"). **Derived**: with 3 entries per short-named file, max ≈ 2.79 M files per directory; a 43,200-frame take (30 min × 24 fps) uses ~130 k entries ≈ 4.1 MB of directory, i.e. 1.5 % of the limit.
- Lookup (`exfat_find_dir_entry`) is a **linear scan**: starts at `hint_stat` if set, else entry 0; walks clusters (`exfat_get_next_cluster`, or `clu++` for `ALLOC_NO_FAT_CHAIN` contiguous dirs); per entry: `TYPE_UNUSED` ends the scan (→ not found), deleted entries are recorded as empty candidates (`exfat_set_empty_hint`), file entries record `hint_opt`, the stream entry's `name_hash` and length are compared first, then name entries via `exfat_uniname_ncmp`. If the hinted scan hits the end without a match it **rewinds** to the first cluster and scans up to `end_eidx` (`if (!rewind && end_eidx)` … `if (rewind && dentry == end_eidx)`). There is no index, hash table or B-tree; `d_hash`/`d_cmp` hash names only for the dentry cache (case-insensitive via `exfat_toupper`).
- Negative lookup for a *new* name therefore reads every entry of the directory before `-ENOENT`. The stream `name_hash` filter makes mismatches cheap (16-bit compare), and directory clusters come from the buffer cache (`sb_bread` in `exfat_get_dentry`, with read-ahead), so repeated scans of a hot directory are CPU/RAM-bound, not disk-bound (**derived**).
- Creation path: VFS lookup (negative, full scan as above, leaving `hint_femp` at the first run of free slots or the end) → `exfat_add_entry` → `exfat_find_empty_entry` uses `ei->hint_femp` if set (O(1)), else `exfat_search_empty_slot` scans from entry 0; if no slot, one cluster is allocated (`exfat_alloc_cluster(inode, 1, …)`), **zero-filled** (`exfat_zeroed_cluster`), chained, and `i_size` grows by one cluster. Comment: "exfat_find_empty_entry must be called before alloc_cluster()".
- Aggregate cost: creating N files in one directory ≈ N²/2 entry visits (one negative scan per create). Upstream developers describe it the same way in 2026 patch cover letters: "Negative name lookups scan a directory from the beginning. Repeating this scan before creating each file makes bulk file creation approach O(N^2)" (**web, snippet**: https://ratatoskr.run/lkml/2026/09/17499136/t "[PATCH v3 0/3] exfat: speed up file creation…"; v2 adds a 64 KiB per-directory Bloom filter built lazily at 1024 entries, https://ratatoskr.run/linux-fsdevel/2026/06/17128596/t ; a related hint patch reports 20,000 creates in one directory going from 3,879 s to 3,050 s on the author's unstated hardware, https://ratatoskr.run/linux-fsdevel/2026/06/17128597/t ). None of these is in 6.12 (**derived** from dates). The 2022 series "exfat: hint the empty entry which at the end of cluster chain" (Yuezhang Mo) *is* reflected in 6.12's behaviour of saving `hint_femp` with `count = 0` after a failed search (**measured** in namei.c; thread: https://lkml.kernel.org/lkml/4eaa01d8ef82$ef0f1680$cd2d4380$@samsung.com/T/ ; https://lkml.iu.edu/hypermail/linux/kernel/2211.0/01540.html).
- **Derived estimate for a frame-per-file take**: at 43,200 files the last create scans ~130 k entries × 32 B = 4.1 MB from RAM; at a few ns per 32-byte entry that is ~1–7 ms per create, and ∑ over the take ≈ 43,200 × (half of that) ≈ 0.5–2.5 CPU-minutes spread over 30 min (≈ 3–8 % of one core). This is **probable**, assumes a hot buffer cache and no `dirsync`; the 2026 benchmark above (≈190 ms per create) shows that slow media or synchronous directory writes can make it two orders of magnitude worse.

### 4.2 `hint_femp` / `hint_stat` / iversion behaviour
- `struct exfat_hint_femp { int eidx; int count; struct exfat_chain cur; }` = "first empty entry hint": index, count of contiguous empties, cluster; `EXFAT_HINT_NONE -1`. `struct exfat_hint { clu; off|eidx }` is the last-lookup position (`hint_stat`) and the readdir cluster-offset hint (`hint_bmap`).
- `exfat_find` compares `ei->version` with `inode_peek_iversion_raw(dir) & 0xffffffff`; on mismatch it resets `hint_stat.clu`, `hint_stat.eidx` and `hint_femp.eidx`. `exfat_create`/`exfat_mkdir` call `inode_inc_iversion(dir)` after `exfat_add_entry`; `exfat_unlink`/`exfat_rmdir` call `inode_inc_iversion(dir)` and store `inode_query_iversion(dir)` in the dentry's `d_fsdata` (`exfat_d_version_set`).
- Consequence (**derived**): in a directory that is being appended to, every create bumps the version, so the *next* lookup starts from entry 0 (hint discarded) — the per-create full scan in §4.1 is structural, not a cache miss. Within one create the `hint_femp` left by the negative lookup survives (same version), so the empty-slot search is O(1).
- `exfat_d_revalidate`: positive dentries always valid; negative dentries are dropped for `LOOKUP_CREATE | LOOKUP_RENAME_TARGET` ("in order to make sure to use the case" of the new name) and otherwise validated with `inode_eq_iversion(d_inode(dentry->d_parent), exfat_d_version(dentry))` — any create/unlink in the parent invalidates all negative dentries there (**measured**).

### 4.3 "dir cache"
- Two caches exist, neither indexes names: (a) the per-inode **FAT-chain cache** (`fs/exfat/cache.c`): `EXFAT_MAX_CACHE 16` LRU entries of (file-cluster → disk-cluster, `nr_contig`) so `exfat_get_cluster` can skip part of a FAT walk; "Don't use exfat_cache if zero offset or non-cluster allocation"; contiguous (`ALLOC_NO_FAT_CHAIN`) files/dirs need no FAT walk at all. (b) the **entry-set cache** (`struct exfat_entry_set_cache`, `DIR_CACHE_SIZE` = sectors covering 19 entries, ≤3 sectors) holding the buffer heads of one file's entry set while it is read or updated. Directory data itself lives in the block-device buffer cache (`sb_bread`), so a 4 MB directory stays RAM-resident on a 4 GB CM5 under normal memory pressure (**probable**).

### 4.4 `discard` mount option vs `fstrim`
- Mount options parsed in super.c (**measured**): uid, gid, umask, dmask, fmask, allow_utime, iocharset (`utf8` sets `opts->utf8`), errors (continue|panic|remount-ro; default **remount-ro**), `discard` ("Issue discard requests on deletions"), `keep_last_dots`, `sys_tz`, `time_offset` (±1440 min), `zero_size_dir`; deprecated/ignored: utf8, debug, namecase, codepage. `discard` is **off by default** (kzalloc'd). If requested on a device without discard: "mounting with \"discard\" option, but the device does not support discard" and it is turned off.
- With `discard` (balloc.c `exfat_clear_bitmap`): **one `sb_issue_discard` per freed cluster** (`1 << sect_per_clus_bits` sectors), issued synchronously inside the free path after the bitmap bit is cleared; `-EOPNOTSUPP` disables discard for the mount ("discard not supported by device, disabling"); other errors are ignored. **Derived**: deleting a 10 GB file on a 128 KB-cluster volume issues 81,920 discard commands inside `unlink()`; at even 50 µs each that is ~4 s of unlink latency, and the commands compete with recording I/O. Do not record with `discard` mounted.
- `fstrim` (FITRIM → `exfat_trim_fs`): walks the allocation bitmap under `bitmap_lock`, **coalesces contiguous free clusters into one discard per run**, honours `minlen` (`trim_minlen = range->minlen >> cluster_size_bits`; `count >= trim_minlen`), returns bytes trimmed; aborts on the first discard error. **Derived**: run `fstrim` between sessions (not during a take — it holds `bitmap_lock`, blocking allocation while it walks).
- Context (web, snippet): `mkfs.exfat` discards the device at format time unless `-K/--no-discard` (https://manpages.debian.org/experimental/exfatprogs/mkfs.exfat.8.en.html).

### 4.5 Cluster size effects
- Defaults (`mkfs.exfat`, exfatprogs): 4 KB < 256 MB; 32 KB for 256 MB–32 GB; **128 KB for ≥ 32 GB**; `-c` sets any power of two (web, snippet: https://man.archlinux.org/man/mkfs.exfat.8 ; https://manpages.debian.org/experimental/exfatprogs/mkfs.exfat.8.en.html). Kernel maximum: `EXFAT_MAX_SECT_PER_CLUS_BITS(x) (25 - (x)->sect_size_bits)` → 2²⁵ B = **32 MiB** cluster cap (**measured**, exfat_raw.h; arithmetic derived).
- Mechanisms (**derived** from the source): allocation is per cluster via the bitmap (`exfat_find_free_bitmap`), so larger clusters mean fewer bitmap updates and fewer FAT entries for a given file (contiguous files use `ALLOC_NO_FAT_CHAIN` and have no FAT chain at all); directory growth and zero-filling happen one cluster at a time (128 KB zero write per ~1,365 new short-named files at 3 entries each); `discard`/`fstrim` granularity is one cluster; slack averages half a cluster per file (43,200 files × 64 KB ≈ 2.7 GB on a 128 KB volume — ~0.3–0.5 % of a 12–25 MB-per-frame take, derived).
- Evidence online is thin (web, snippet): no controlled 4/32/128 KB benchmark for large sequential files was found; vendor guides recommend 128–256 KB for large media; one camera user found recording only worked at 128 KB (device-specific), https://electricrcaircraftguy.github.io/exfat-clusters/ reports ~390 MB/s writes with 128 KiB clusters and large small-file overhead. Treat cluster size as a second-order lever; keep the 128 KB default unless the recorder's own tests say otherwise (**probable**).

## 5. NVMe SMART `percentage_used` vs rated TBW

- Spec text as reproduced in libnvme (**web, fetched**: https://raw.githubusercontent.com/linux-nvme/libnvme/refs/heads/master/src/nvme/types.h, `struct nvme_smart_log`): *Percentage Used* "Contains a vendor specific estimate of the percentage of NVM subsystem life used based on the actual usage and the manufacturer's prediction of NVM life. A value of 100 indicates that the estimated endurance of the NVM in the NVM subsystem has been consumed, but may not indicate an NVM subsystem failure. The value is allowed to exceed 100. Percentages greater than 254 shall be represented as 255. This value shall be updated once per power-on hour (when the controller is not in a sleep state)." *Data Units Written*: 512-byte units "reported in thousands … and is rounded up", excludes metadata; Write Zeroes/Write Uncorrectable do not count; `0` = not reported.
- Relationship to TBW (**derived**): host bytes written = `data_units_written × 1000 × 512`; host-write fraction of rating = that / TBW. `percentage_used` is the *vendor's* wear estimate (typically P/E cycles consumed, which includes write amplification and pSLC-folding writes), so it can run ahead of the host-write fraction; the two agree only if the vendor's model assumes WAF ≈ 1 at the rated TBW.
- Field observations (web, snippet, secondary): a 2 TB drive at 5.0 % of TBW by host writes showed 7 % `percentage_used` (https://www.netdata.cloud/guides/smartctl-disk-monitoring/smartctl-nvme-percentage-used/); Samsung 970 EVO Plus 2 TB units reportedly hit 100 % at ~370 TB of 1,200 TBW (single secondary source, https://www.netdata.cloud/guides/nvme/nvme-percentage-used-high/); a FireCuda 520 thread where Percentage Used exceeded the host-write fraction (https://forums.tomshardware.com/threads/seagate-firecuda-520-smarts-percentage-used-is-above-data-units-written-drives-tbw.3610027); Intel/Solidigm: 100 "may not indicate a device failure", value may exceed 100 (https://www.intel.com/content/www/us/en/support/articles/000056596.html ; https://www.solidigm.com/support-page/maintenance-tools/ka-00079.html). Kingston's SMART attribute guide (not fetchable here): https://media.kingston.com/support/pdf/ssd-smart-attribute.pdf .
- Campaign use (**derived**): log both counters per session; the wear budget should be tracked on `percentage_used` (the warranty-relevant quantity) and the host-write fraction kept as the cross-check; a sustained sequential-write workload with large files should keep WAF near 1, so a widening gap flags pSLC folding or unexpected write amplification. Also watch `avail_spare` vs `spare_thresh`, `critical_warning`, media errors — a reading of 5 % is a wear estimate, not a failure probability.

## 7. Cross-cutting conclusions for the campaign (derived / probable, from the labelled inputs above)

1. **The link is the ceiling.** Gen 3 x1 ≈ 760 MB/s practical writes (720–780); Gen 2 x1 ≈ 450 MB/s. Both drives write pSLC far faster than that. The only drive-side risk to sustained throughput is post-cache TLC speed: ~800 MB/s for the MP600 Mini 1 TB (fine at Gen 2, marginal at Gen 3), **unknown and probably 0.4–0.8 GB/s** for the KC3000 512 GB — measure it before relying on takes longer than the pSLC window (~176 GB on an empty drive, shrinking as the drive fills).
2. **Thermal.** Desktop throttling data (KC3000 after 60–90 s at >5 GB/s; MP600 Mini "quickly" under full load) is for 4–7× the Pi's write rate; at ≤0.9 GB/s both drives are far from those regimes (probable), but a 2230 sealed in a CFe-B shell has no convection and depends on pad contact — thermal logging (`nvme smart-log` temperature, composite) is the cheap safeguard. Spec operating limits: KC3000 70 °C, MP600 Mini 65 °C; firmware throttle points ~80–84 °C.
3. **Power.** A 2280 KC3000 at full write is ~0.9–1.0 A at 5 V — at an FFC-only board's limit; a header-powered carrier and a 5 V/5 A supply remove that risk. "Undervoltage detected!/Voltage normalised" pairs mean the input dipped below ~4.63 V for ≥ one 2-s poll — treat any occurrence during a take as a rig fault.
4. **Kernel.** On rpi-6.12.y: HMB off by default (`nvme.max_host_mem_size_mb=0`), SGL corruption bug absent; moving to rpi-6.18.y changes both (32 MB HMB default; corruption fixed only from 2026-07-14). "Disabling device after reset failure" = controller reset failed → device deleted; if preceded by the `CSTS == ~0` hint, try the APST/ASPM flags, but the community record says cable, power and Gen 3 instability are the usual causes.
5. **exFAT.** Per-file creation in a hot directory is a full linear scan (iversion resets the lookup hint after each create); at 43 k files it is milliseconds per create from RAM — acceptable unless directory I/O is synchronous or the cache is cold. Keep `discard` off during recording (one discard per cluster on every delete); `fstrim` between sessions; 128 KB clusters are the sane default; the 256 MB / 8,388,608-entry directory limit is ~2.8 M short-named files.
6. **Wear accounting.** Track `percentage_used` (vendor model, includes amplification) and `data_units_written × 512,000 / TBW` (host fraction) together; divergence = amplification/folding.
