## 1. The result in one paragraph

The target was 4K Clear HDR 16-bit uncompressed cDNG at 25 fps with **no** lost frames while the touch UI shows the live
picture (peaking and zebra on). The losses were single frames missing at capture (Core's `dropped_gap_estimate`; the
write queue never filled). Most of the evening was spent on the touch UI's GPU work, because stopping or freezing the UI
removed the losses. After a reboot the same setup was clean once and then drifted again, and the drift followed **page-
cache pressure**: Core's DNG writer called `posix_fadvise(DONTNEED)` right after each write, on still-dirty pages, which
frees nothing and drains the per-CPU page lists on every core per frame, while the page cache filled and `kswapd`
reclaimed ~13 GB per 3-minute take. Setting `APERTAR_DNG_DONTNEED=sync` (drop the pages after the once-a-second `fsync`)
took the 3-minute takes to 0 lost and a 10-minute take to 25 of 15,023 (0.17 %, 18 of them in the last minute with the
drive 97 % full); with CineMate's dirty-page limits added (`vm.dirty_bytes` 1 GiB, `dirty_background_bytes` 256 MiB,
`min_free_kbytes` 64 MiB) a 10-minute take on the empty drive lost **0 of 15,025** and kswapd reclaimed nothing (#80). The UI was the last straw on an overloaded memory system, not the root cause (probable). Upstream
Apertar has the same per-frame `DONTNEED` call hard-coded (KB `lessons/upstream-issues.md` #44).

## 8. Inspection (2026-11-02, cloud session): summary

The full inspection is [inspection-2026-11-02.md](inspection-2026-11-02.md): verdict, the five question groups, the test
plan with every setup and decision rule, the code recommendations, and the corrections to the record. It was written from
the desk (no Pi) by five examiners (statistics, kernel 6.12 `mm/`, Core `adac040`, the six UI commits, co-factors), a

### 8.1 Verdict

**`sync` removes the reclaim regime (measured). That it removes the losses is probable, not proven. The stated mechanism
is partly wrong, and how reclaim reaches capture is open.**

| Claim of 2026-11-01 | Status now | In one line |
| --- | --- | --- |
| `sync` keeps the cache from filling | **measured** | kswapd 47-58 k pages per 3 min against 3.02-3.45 M under `writer`; low-watermark hits 8-11 against 948-1805; no overlap |
| `writer`'s DONTNEED "frees nothing" | **probable** | it starts writeback of the whole file, then skips every folio still under writeback (`mm/fadvise.c:113-115`, `mm/filemap.c:2121-2125`); folios that finish in the milliseconds before the walk can go, and 18-24 GB per take were freed by something other than kswapd |
| "... and drains the per-CPU LRU lists on every core per frame" | **refuted** for folios under writeback | the drain needs a counted failure (`mm/fadvise.c:166-170`), and folios under writeback are never counted (`mm/truncate.c:521-531`); its cost would be at most 0.2 ms per frame anyway |
| kswapd reclaimed "~13 GB per 3-minute take" | **corrected** | the 2712 kernel runs 16 KiB pages (`bcm2712_defconfig:50`): 49.5-56.5 GB, 67-76 % of each take's writes |
| the regime causes the capture losses | **unproven** | the likeliest link has a measured precedent on this rig (2026-10-26, hardware log): memory contention slows libcamera's serial per-frame cycle past 40 ms, the CFE buffers drain, single frames skip at a steady rate. That is the 11-01 signature, and it needs no stall anywhere (mechanism G) |
| the touch UI is "the last straw" | **probable**, as an interaction | under `writer` the losses scale with the UI's GPU work: preview held 0 %, 12 fps 2.9 %, 25 fps about 7.5 % (n = 1 each); under `sync` the unmodified UI was clean three times |
| `sync` beat `writer` | **suggestive** | take-level one-sided p = 0.057 (4 vs 3; frame-level tests are invalid, losses cluster); confounded by order, the Core restart and its trims, and the start memory state, after about 20 interventions |
| #80's sysctls carried its 0 of 15,025 | **not supported** | no watermark was reached in #80 (kswapd 0, low-watermark hits 0), so `min_free_kbytes` could not act, and the dirty pair is inert for Core's 11 MB of dirty pages. The likely carriers are the start state (MemFree 2,758 MB after the format) and the empty trimmed drive. `min_free_kbytes` is Apertar's own knob, not CineMate's |
| A0 was clean because it was "early in the boot" | **refuted** (empty cache fills in 6 s) / boot age **unconfirmed** | A0's time stamps straddle a crash and a reboot. A0, #69 and #74 share one position: first take of a fresh Core on a freshly trimmed drive |
| the evening drifted with uptime | **not supported** | boot 1 is flat until 21:03, then a step to 11-18 % on a freshly formatted drive |
| 2026-10-30: "the per-frame writeback hint is needed" | **does not follow** | `a40112a` already had the per-frame DONTNEED, which starts writeback itself; A2 is one unexplained run |

Also new: every post-reboot take ran the RAM write buffer (`queue_budget` 1.40-1.55 GB); the imx585 driver changed
`24172e6` -> `cd548ef` on 11-01; the kernel runs fake NUMA (`CONFIG_NUMA_EMU=y`, probably 8 nodes, so 8 kswapd threads and
per-node watermarks); rp1-cfe's interrupt cannot be moved and `/proc/irq/154/smp_affinity` must not be written; the
`rp1_cfe` dynamic-debug line is compiled out; PSI needs `psi=1` on the kernel command line.
