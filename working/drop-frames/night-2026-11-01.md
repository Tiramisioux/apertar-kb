## 1. The result in one paragraph

The target was 4K Clear HDR 16-bit uncompressed cDNG at 25 fps with **no** lost frames while the touch UI shows the live
picture (peaking and zebra on). The losses were single frames missing at capture (Core's `dropped_gap_estimate`; the
write queue never filled). Most of the evening was spent on the touch UI's GPU work, because stopping or freezing the UI
removed the losses. After a reboot the same setup was clean once and then drifted again, and the drift followed **page-
cache pressure**: Core's DNG writer called `posix_fadvise(DONTNEED)` right after each write, on still-dirty pages, which
frees nothing and drains the per-CPU page lists on every core per frame, while the page cache filled and `kswapd`
reclaimed ~13 GB per 3-minute take. Setting `APERTAR_DNG_DONTNEED=sync` (drop the pages after the once-a-second `fsync`)
took the 3-minute takes to 0 lost and a 10-minute take to 25 of 15,023 (0.17 %, 18 of them in the last minute with the
drive 97 % full). The UI was the last straw on an overloaded memory system, not the root cause (probable). Upstream
Apertar has the same per-frame `DONTNEED` call hard-coded (KB `lessons/upstream-issues.md` #44).

Useful facts from this part that do not depend on the drift:
- 4K Clear HDR 16-bit **lossless JPEG** encodes at ~17.5 fps (`estimated_capacity_fps` 15-19 in #2, #66-#68): a 25 fps
  take fills the RAM buffer and the safety stop ends it (#2). SDR 12-bit lossless (COMP1) manages 43-66 fps.
- The drive (Corsair MP600 Mini, exFAT) sustained ~550 MB/s in #25 (derived from the buffer growth, probable): 4K SDR
  12-bit uncompressed 50 fps (~620 MB/s) is over it regardless of the losses.
- All of CPU0 serves rp1-cfe (IRQ 154), v3d (173, 174), hvs (175, cannot be moved), USB (~700/s) and I2C bus 1 (~570/s,
  the NeoRotary 4 encoder board polled every 30 ms). Moving v3d to CPU2 did not help (#61-#62).
- The CFE logs `DPHY: Datarate 1782 Mbps out of range` at every stream start (891 MHz link above the RP1 PHY's range).
  Clean with the UI stopped and at 1080p, so not the cause tonight.
- Memory was fragmented by the end of the first boot (`/proc/buddyinfo` no free block >= order 8); compaction was just as
  busy in the clean takes after the reboot, so it is not the cause.

## 6. Method notes (traps hit tonight)

- Another session compiled on the Pi during two takes (#6, #7): check `ps` for `cc1plus|gmake|cmake` before AND after.
- An open WebUI tab costs a lot (#4, #37, #61, #76): the scripts refuse to start with a client on `:8000`.
- `pkill -f "<pattern>"` over ssh matches its own command line and kills the ssh: kill by pid.
- `sudo -n` works only while Patrik has a cached sudo ticket; after a reboot it asks for the password.
- Freezing the UI before `record_start` hangs the start at the audio open (the UI holds the shared audio input): freeze
  after the start.
- With `hdmi_external_only=true` the main window is hidden; renderer-level switches must reach the external-monitor
  renderer (the plane claim is lazy for that reason).
- Short takes are not comparable at these rates: use 3 or 10 minutes, and watch the per-minute counts.
