## 2. Tools (ready in the KB, `working/tools/`)

- `tdn_strip.py SRC DST`: copies a PiSP tuning with each `rpi.denoise` `tdn` member cut out of the text (diff shows the
  `tdn` lines only). Refuses: SRC not strict JSON or not `"target": "pisp"`; DST = SRC, inside a `defaults*` directory, not
  `.json`, or existing with other content; any difference other than the `tdn` paths. Writes via temp file + fsync + rename
  and reads back. Tested on cinemate's `imx585_mono.json`: 3 blocks removed, `-15 +0` lines (measured).
- `be_overlap.py RAWDIR --prefix e3 [--take NAME[:LIB]]`: any unit now (takes found from `<prefix>-<NAME>.out`), take length
  and delivered frames from the console, the frame period from the take's own SOF interval (25/30/33 fps), and each take
  aligned on the clock pair `take3v3.sh` prints at `record_start` (evening-2 output unchanged).
- `take3v3.sh`: the mode from the environment (`TAKE_CLEAR_HDR=true|false TAKE_BITS=16|12 TAKE_FPS=25
  TAKE_COMPRESSION=none|lossless_jpeg`, defaults = the B1 rig), a `mode:` line with what Core reports at the start
  (fps, Clear HDR, bit depth, compression, `tuning_file`), the `clocks at record_start: epoch= mono=` line, and the UI
  binary's threads in the 1 Hz log.

```

# restore, after the last TDN-off take, not recording:
$C set_tuning_file path=        # "path": "" = automatic (or path=<the value noted before>)
TF; J; grep -n 'tuning_file=' ~/.config/apertar-core/camera_settings.conf
```

How it behaves (confirmed: App:12685-12692, CC:1373-1431, CC:11360-11427, `ControlProtocol.cpp:62-73,156-162`,
`tools/core.py:7-14`):
- `path=` sends an empty string = automatic. The path must be absolute, `.json`, readable, under 4 MiB, with `"target":
  "pisp"`; there is no directory allow-list. Refused in Standby, while recording, and while stills or a timelapse are pending.
  A new path restarts the camera; on failure Core returns to the previous file with "Could not apply tuning file: ..." (or
  the Error state). The same path again is a no-op.
- It is saved (`~/.config/apertar-core/camera_settings.conf`, CC:965, CC:12613-12620) and survives Core restarts,
  `b1-arm.sh` and reboots (CC:10372-10394). `take3v3.sh`, `b1-arm.sh`, `apertar-tune`, fps, ladder, Clear HDR, bit depth,
  compression and format switches never change it (CC:10547, 10909, 11205-11219, 11253, 11430, 11475).
- Loading a preset applies the preset's `cameraTuningFile` (App:13787-13788, CC:12486-12494): presets saved before tonight
  carry automatic and would turn TDN back on. Load and save no presets during the unit.
- **A chosen file is used as given in every mode** (CC:7205-7214): while it is set, SDR12 (between P1 and P2, after the
  unit, every SDR12 rung of the ladder) also runs on the Clear HDR copy, with no TDN and no `rpi.hdr`: a noisier preview that
  may render slightly differently (probable); no black-frame risk is documented in this direction (DTS:183-185 is the
  reverse case). **Restore automatic before target 2, before any other unit and before the Pi goes back to User**: add
  "Core `tuning_file` back to automatic (`set_tuning_file path=`), read back" to the restore list.
- A non-Standard preview colour profile derives `~/.cache/apertar-prores/<profile>.json` from the chosen file; it keeps
  `rpi.denoise`, so TDN stays off (`ProresIspProfile.cpp:170-227`). Evening 2 loaded the defaults file directly (Standard).
