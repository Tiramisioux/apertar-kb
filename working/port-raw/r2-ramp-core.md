# r2-ramp-core — Speed ramping (fps change during a take), Apertar-Core side

Reader: r2. Tree: apertar-core branch `clearhdr-fixes`, HEAD `25397cd` (base `f60e301`). Every line below was opened with `sed -n`/`grep -n` on that tree. Where a file is byte-identical at `f60e301` (`git diff --quiet f60e301 HEAD -- <file>`), the line is the same there and is marked "=f60e301". For files that changed, the `f60e301` line of the same anchor is given in parentheses where it matters. Abbreviations: `CC` = `apertar-core/src/camera/CameraController.cpp`, `App` = `apertar-core/src/ApertarCoreApp.cpp`, `WCP` = `apertar-core/src/web/WebControlPage.cpp`, `Audio` = `apertar-core/src/audio/AudioRecordingSession.cpp`, `Cdng` = `apertar-core/src/cdng/CdngEncoder.cpp`, `Mlv` = `apertar-core/src/mlv/MlvEncoder.cpp`. Tags: CONFIRMED (line opened and read), PROBABLE (derived, reason given), UNKNOWN.

Short version: the only thing that stops a ramp today is one `if` in `setFps` (CC:8543-8546). Below it, an fps-only change is already a one-shot control write (`applyControls` -> `pendingControls_` -> next `requeueRequest`), the DNG `FrameRate` tag is already patched per frame from the live `settings_.fps`, MLV frame times are already real sensor microseconds, and the phase lock already re-arms itself on an fps change. Four places assume one fps per clip and would misbehave: `DngRecordingQueue::nextFrameIndex` (elapsed x clip-start fps), `AudioRecordingSession::observeVideoFrame` (frame end snapped to the clip-start fps grid), the RecRun/FreeRun timecode (count or wall fraction x the *live* fps, so TC jumps at every step), and the H.264/ProRes containers (one `time_base`). The port is: relax the gate for raw formats, make frame numbering count-based (or duration-integrated), end the WAV at the last frame's real end, pin `FrameRate`/timecode to the clip's base fps, add a stepper command and a log line.

### Corrections that change substance

1. **Control latency / queue depth (row 29).** Not 3 requests and ~4-5 frames. `requests_` holds `rawCameraBufferCount(clearHdr)` entries: 4 on ext4, 6 on exFAT/FAT/NTFS, 8 (ClearHDR) or 10 (ClearHDR on exFAT/NTFS), env-overridable 3..16 (CC:1055, 1059, 1173-1181, 7131-7149@25397cd; MediaProfile.hpp:136-140@25397cd). With the 2-frame VBLANK delay, a step lands ~N+1 frames after acceptance: ~5 / ~7 / ~9-11. Everything the reader derived from "4-5" (the `metadata.fps` lead in §3, the stepper period in §4 row 9, the "+5 frames" at record start in §2 #11) scales with N. The reader's PROBABLE label was right to be cautious; the number came from a brief via p2, not from source.
2. **WAV end error (row 36).** `1/B - 1/L` is the mean; the real value is `1/B - 1/L +/- 1/(2B)` because the grid rounding term `round(x) - x` is not zero once the live rate differs from the base. 24->48: 0..+41.7 ms; 24->12: -62.5..-20.8 ms. The port fix (row 3 of §4: end = last frame + its `FrameDuration`) is unchanged and removes both terms.
3. **Stepper cadence (row 64).** The "each step seen before the next" rule is both violated by the reader's example and unnecessary, because `pendingControls_` is replaced, not accumulated (CC:6140). A ramp can issue one `setFps` per frame safely; only read-back/stop-on-no-move logic needs the N+1-frame delay.
4. **Exposure clamp attribution (row 61).** Real, but in libcamera-qbc (`ipa_base.cpp:1804-1810`, `agc_channel.cpp:398/:983`), not in p2 §1. Consequence for the shutter-policy row: a "keep exposure" ramp-up past `1/L` is clamped by the IPA per frame, so Core should clamp `shutterUs` to the new frame duration itself (or report it) rather than rely on the sensor silently shortening it.

Line drifts (no substance): rows 11, 13, 20, 21, 24, 30, 50 (1-17 lines; the right lines are given in the table).

### Settled unknowns

- **U1 — which frame's `FrameRate` Resolve/Premiere sample from a cDNG sequence:** UNVERIFIABLE from the repos (no NLE source). The reader's option (b) (write the clip's base fps in every frame) avoids the question entirely.
- **U2 — whether MLV App honours per-frame VIDF times over the header rate:** UNVERIFIABLE here (no MLV App source). Source facts stand: per-frame times are real (Mlv:1307-1312@25397cd), the header holds one rate (Mlv:1092-1093).
- **U3 — is `FrameDuration` metadata at the step frame the programmed length of that very frame (false-gap risk, §2 #10)?** Settled as far as source goes, PROBABLE: on the qbc fork `FrameDuration` is computed from `deviceStatus->frameLength` (libcamera-qbc/src/ipa/rpi/common/ipa_base.cpp:1594-1595@7e9fef0), and `deviceStatus` comes from `DelayedControls::get(sequence)`, documented as "controls in effect at a sequence number" (libcamera-qbc/src/libcamera/delayed_controls.cpp:189-205@7e9fef0) — i.e. frame n's own programmed length, not a lagging copy. The single residual hardware question is whether `SensorTimestamp(n) - SensorTimestamp(n-1)` reflects frame n's or frame n-1's length (SOF-to-SOF spans the *previous* frame's VMAX). Hard bound regardless of that: the gap rule needs `delta > 1.5 x nominal` (CC:7999@25397cd), so **any single step that changes the duration by <= 1.4x (1-fps stepping, 24->25->30, 48->60, 50->60) can never produce a false `+1`**; only a single > 1.5x jump (24->48, 30->50, 24->36 is just over: 41666 > 41665) can, at most one `+1` per jump and in one direction only (ramp-up if the delta lags the metadata by a frame, ramp-down under the reader's assumption, never if both describe the same frame). A stepper built on the PCF list must therefore treat 30->50 as two steps (30->40->50) or accept one false `+1` and the clip-wide drop latch.
