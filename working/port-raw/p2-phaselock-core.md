# p2-phaselock-core — Phase lock, Apertar-Core side

Reader: p2-phaselock-core. Repos read: apertar-core @ f60e301, libcamera(qbc) @ 7e9fef0 (probable match to the Pi binary), libcamera(cinemate) @ bfe0b76, cinepi-raw @ 63a08d5, cinemate-handbook @ c99ff77, kernel-rpi @ 5bd564a (rp1_cfe via `git show`). Every line number below was read in a window after a `grep -n` anchor. Status tags: CONFIRMED = read in source; PROBABLE = derived from source with a stated inference; UNKNOWN = not derivable here.

Short version: Core already pins the frame duration ({d,d}, min == max) for video; a servo only has to override that one control per request, and the cleanest place to do it is at the end of `requeueRequest` after every existing merge. Core's video and audio are already on one clock (CLOCK_BOOTTIME, which equals CLOCK_MONOTONIC on a never-suspending Pi); CLOCK_REALTIME appears only in `RecordingClock` for file timestamps/timecode. Therefore the servo should be referenced to BOOTTIME (`SensorTimestamp`), not to `FrameWallClock` as Cinemate does, and then no audio change is needed and the existing resampler stays. The cadence gate and gap estimator tolerate a +/-150 us excursion by an order of magnitude. One Core-specific hazard: Apertar's libcamera fork carries an IMX585 `getBlanking` lattice search that re-chooses (VMAX, HMAX) for every integer-microsecond change of a pinned duration, so the "+/-1 line sigma-delta dither" model of Cinemate does not carry over unchanged.

## 1. How Core sets frame duration today

**CONFIRMED.** `controlsForSettings` (apertar-core/src/camera/CameraController.cpp:2057-2083@f60e301) computes:

- `nominalFrameDurationUs = int64_t(1000000.0 / settings.fps)` (truncation, not rounding), 41666 if fps <= 0 (:2074-2076). Examples: 24 -> 41666, 25 -> 40000, 30 -> 33333, 23.976 -> 41708, 60 -> 16666, 120 -> 8333.
- `limitedPreview` (photo mode + long exposure + manual shutter > 66,667 us, `needsLongStillExposure` :2049-2053, `stillPreviewExposureLimitUs = 66'667` :2047) lifts the minimum to `max(nominal, exposureUs)` (:2077-2078).
- `maximumFrameDurationUs`: equals `frameDurationUs` unless `photoModeEnabled && !shutterAuto`, in which case it is `max(frameDuration, exposureUs + 100000)` (+0 when limitedPreview) (:2079-2080).
- Sent as `FrameDurationLimits = {frameDurationUs, maximumFrameDurationUs}` (:2081-2083).

So for video (photo mode off) the range is already a **pin**: min == max == `int64(1e6/fps)`. Only photo mode with manual shutter opens a range. Exposure interplay: `ExposureTime` is set separately when `!shutterAuto` (:2106-2109) with `exposureUs` (the 66,667 us preview cap applies in limitedPreview); the frame duration never follows the shutter in video mode (an exposure longer than the frame is clipped by the IPA's `getBlanking`, see 5).

**Where it is (re)sent (CONFIRMED):**
- Camera start: `initialControls = controlsForSettings(settings_, ...)` then `camera_->start(&initialControls)` (:6681-6694).
- Any settings change: `applyControls()` **assigns** (replaces, not merges) `pendingControls_ = controlsForSettings(sanitized, ...)` under `sessionSettingsMutex_` (unique) then `controlsMutex_` (:5827-5856, assignment :5843-5848, `settings_ = sanitized` :5849). Reached from `CameraController::applySettingsLocked` (:9136-9200, call at :9167-9169), which every setter uses, e.g. `setFps` (:8080-8114) and `setTimecodeMode` (:8647-8653).
- One-shot delivery: `requeueRequest()` (:6833-6912) calls `request->reuse(ReuseBuffers)` (:6838), which clears the request's controls (libcamera(qbc)/src/libcamera/request.cpp:388-406@7e9fef0, `controls_.clear()` at :405), then merges `pendingControls_` with the default `MergePolicy::KeepExisting` and clears it (:6840-6844). Because the list is empty after `reuse()`, KeepExisting is effectively "set all" here (libcamera(qbc)/src/libcamera/controls.cpp:1012-1035; default policy libcamera(qbc)/include/libcamera/controls.h:414-415, :435).
- `stop()` clears `pendingControls_` (:5764-5767).
- fps itself: `setFps` refuses while recording ("Stop recording before changing FPS so video and audio keep the same timeline", :8083-8086), clamps through `sanitizeSettingsForSensor` (:8097-8099; the clamp to the probed/table maximum is at :2832-2844, `maximumSupportedFpsForResolution` :2763-2770), preserves shutter angle (:8107-8110). App entry: `set_fps` command (apertar-core/src/ApertarCoreApp.cpp:9310-9316), UI dispatches at :8531, :8716, :8790.

**Would a per-frame {d,d} pin from a servo be overwritten? (CONFIRMED mechanics, PROBABLE consequences):**
- If the servo wrote into `pendingControls_`, the next `applyControls()` would replace the whole list (assignment at :5843), dropping the servo value for that one request; harmless but a one-frame step of up to 150 us.
- The three photo paths in `requeueRequest` merge `controlsForSettings(...)` with `MergePolicy::OverwriteExisting` (:6855-6857 bracket locks/expose, :6869-6871 restore preview, :6891-6893 one-request long shutter) and would overwrite a servo pin on those requests. They are all photo-mode paths (`pendingPhotoCaptures_`, `restoreStillPreviewControls_`).
- **Where to merge so it wins:** at the end of `requeueRequest`, after the photo block and before `camera_->queueRequest(request)` (:6903-6911), do `request->controls().set(FrameDurationLimits, {d,d})` guarded by `!settings_.photoModeEnabled && pendingPhotoCaptures_.empty() && !restoreStillPreviewControls_ && !stillExposureActive_`. `ControlList::set` overwrites unconditionally. The servo value lives in a session member written on the completion thread (see 5). Alternative: give `controlsForSettings` an optional duration override; less clean because the photo paths call it too.
- IPA side (CONFIRMED): the control is parsed per request in `IpaBase::applyControls` case `FRAME_DURATION_LIMITS` -> `applyFrameDurations(min, max)` (libcamera(qbc)/src/ipa/rpi/common/ipa_base.cpp:1313-1317), which clamps both to the sensor mode's `minFrameDuration..maxFrameDuration` and **returns the validated limits in metadata** `FrameDurationLimits` (:1780-1797). The servo can therefore detect saturation at the mode minimum (at the maximum fps for a mode, the loop can only lengthen). The actual VBLANK/HBLANK are set in `applyAGC` via `helper_->getBlanking(exposure, minFrameDuration_, maxFrameDuration_)` (:1836-1846; VBLANK at :1844) and reach the sensor through `DelayedControls` with `vblankDelay = 2`, `hblankDelay = 2` for imx585 (libcamera(qbc)/src/libcamera/sensor/camera_sensor_properties.cpp:389-394; VBLANK marked priority-write in pipeline_base.cpp:883-891). Loop latency is therefore roughly 2 frames of sensor delay plus the request queue depth (3 in flight).

## 2. Per-frame timestamps and clocks

**Video (CONFIRMED):**
- `SensorTimestamp` (ns) is read in `recordRawFrame` (:7238-7242, falls back to `buffer->metadata().timestamp`), in the cadence gate (:6991), in the photo pre-trigger check (:7321-7322) and in the processed-video path (:7740-7744). Core divides by 1000 and treats it as CLOCK_BOOTTIME microseconds: it is compared with `clockMicroseconds(CLOCK_BOOTTIME)` (:6995, `recordingStartBootUs_` set at :5967/:5978) and `PendingPhotoCapture::earliestSensorTimestampNs` is sampled with `clock_gettime(CLOCK_BOOTTIME)` (:7034-7038, :6887-6889).
- `FrameDuration` (metadata) is read at :7244-7248 and :7746-7750 and normalised by `normalizeFrameDurationToUs` (:3044-3070: accepts us or ns, choosing the candidate within 1/8..8x of `1e6/fpsHint`). On the qbc fork it is emitted in **microseconds** from the delayed device status (`helper_->exposure(frameLength, lineLength).get<std::micro>()`, libcamera(qbc) ipa_base.cpp:1594-1595), i.e. the frame length actually programmed for that frame.
- `FrameWallClock`: Core never reads it (grep over apertar-core/src: no hits). The qbc fork does produce it: pisp.cpp:1985-1996 derives it per frame from `ClockRecovery` (`wallClockRecovery_.addSample()` then `getOutput(sensorTimestamp)`), copied into request metadata at pipeline_base.cpp:1555-1560. `ClockRecovery` is a BOOTTIME -> REALTIME linear fit sampled with back-to-back `clock_gettime(CLOCK_BOOTTIME/REALTIME/BOOTTIME)` (clock_recovery.cpp:109-130; `getOutput` :219-228; defaults numSamples 100, maxJitter 2000, minSamples 10, errorThreshold 50000 at include/libcamera/internal/clock_recovery.h:18-19, units not verified here). The yaml documents it as CLOCK_REALTIME ns (control_ids_core.yaml:1269-1283). The cinemate fork also has it (libcamera(cinemate)/src/libcamera/pipeline/rpi/common/pipeline_base.cpp:1507-1508@bfe0b76).
- Kernel origin of `SensorTimestamp` (CONFIRMED from kernel-rpi @ 5bd564a, `git show HEAD:drivers/media/platform/raspberrypi/rp1_cfe/cfe.c`): the CSI-2 frame-start ISR stamps `node->ts = ktime_get_ns()` (:692) and copies it to `vb2_buf.timestamp` (:714); the queue declares `V4L2_BUF_FLAG_TIMESTAMP_MONOTONIC` (:1950). libcamera copies it to `metadata.timestamp` (libcamera(qbc)/src/libcamera/v4l2_videodevice.cpp:1899-1900) and pisp.cpp:1992-1995 publishes it as `SensorTimestamp`. libcamera's yaml says CLOCK_BOOTTIME (control_ids_core.yaml:778-788). **The two agree on a Pi that never suspends** (BOOTTIME = MONOTONIC + suspended time); Core's BOOTTIME assumption is therefore correct in practice (PROBABLE: assumes no system suspend, which Core's standby does not use as far as read here).

**Audio (CONFIRMED):** ALSA capture is opened with `SND_PCM_TSTAMP_TYPE_MONOTONIC` (apertar-core/src/audio/TimestampedAudioCapture.cpp:195), `snd_pcm_htimestamp` (:218) gives the MONOTONIC stamp of the newest available sample; it is converted to BOOTTIME by adding `clockMicroseconds(CLOCK_BOOTTIME) - clockMicroseconds(CLOCK_MONOTONIC)` and backed off by `available / rate` to the first sample (:227-228). The reader loop records `audioStartBootUs_` from the first block (AudioRecordingSession.cpp:427) and tracks `audioEndBootUs_` (:441), padding discontinuities > 10 ms with silence (:431-440).

**Are video and audio on one clock?** Yes: both are BOOTTIME microseconds (video via the kernel MONOTONIC stamp, equal to BOOTTIME without suspend; audio via explicit MONOTONIC -> BOOTTIME conversion whose offset is 0 in the same situation). Gyro uses CLOCK_MONOTONIC (apertar-core/src/hardware/Mpu6050RecordingSession.cpp:536-545) and anchors at the first recorded frame's sensor timestamp (:1451-1464, called from :7281-7282), so it sits on the same timeline under the same assumption.

**Is CLOCK_REALTIME involved in sync?** No. It appears once: `RecordingClock` samples one BOOTTIME -> REALTIME offset (apertar-core/src/audio/RecordingClock.hpp:36-41) at `startRecording` (`recordingClock_ = RecordingClock()` :5871) and the same object is handed to audio (:5914, copied at AudioRecordingSession.cpp:227). `wallTime(bootUs) = bootUs + offset` (:42-45) feeds `wallClockForSensorTimestamp` (:7183-7187) -> `metadata.wallClockTimestampUs` (:7253, :3258-3275) -> DNG `DateTimeOriginal`/`TimeCodes` (apertar-core/src/cdng/CdngEncoder.cpp:1394-1400, tag at :1626), MLV RTCI/INFO (apertar-core/src/mlv/MlvEncoder.cpp:1102-1106) and the WAV bext/iXML start (AudioRecordingSession.cpp:577-589, `timeReferenceSamples` :732). All of `finalizeWav`'s alignment arithmetic is in BOOTTIME microseconds. Core does not follow NTP slew inside a clip; one constant offset per clip.

## 3. What Core's audio alignment assumes, and what a lock changes

**Assumptions as coded (CONFIRMED):**
- `options_.fps = recordingFps(settings.fps)` (AudioRecordingSession.cpp:226; `recordingFrameRate` snaps 23.976/29.97/59.94/119.88 to N000/1001, RecordingClock.hpp:13-25). `resolvedAudioOptions.fps = settings.fps` at CameraController.cpp:5910.
- `observeVideoFrame(sensorBootUs, frameDurationUs)` (:342-356): `videoFirstBootUs_` = first frame's stamp; frame end = `first + (llround((ts - first) * fps / 1e6) + 1) * 1e6 / fps` (:351-354); `frameDurationUs` is only used when fps <= 0. So the video end is **nominal cadence snapped**: frame k is assumed to lie within +/-half a period of `first + k/fps`. Called from `recordRawFrame` only after a successful enqueue (:7293-7294), from ProRes (:7771) and from the H.264 timestamp callback with duration 0 (:5951-5953).
- `finalizeWav` (:501-647): if `videoFirstUs > 0` and captured duration >= 10,000,000 us, `measuredRate = frames * 1e6 / (audioEnd - audioStart)` (:526-527) and the source is resampled only when `0.00002 < |drift| < 0.002` (20..2000 ppm) (:529-530), logged as `ApertarCore audio clock: measured_drift_ppm=... correction=resample|none` (:531). Trim = `(videoFirst - audioStart) * sourceRate / 1e6` when video starts later (:538), else pad `ceil((audioStart - videoFirst) * rate)` (:540). `desiredFrames = (videoEnd - videoFirst) * rate / 1e6` (:550). Linear-interpolation resample in 4096-frame blocks (:605-640). Log `ApertarCore audio sync: video_boot_us=... trim_samples=... pad_samples=... output_samples=...` (:560).
- Frame numbering: `DngRecordingQueue::nextFrameIndex(ts)` = `max(counter, llround((ts - first) * settings_.fps / 1e6))`, counter = index + 1 (:3627-3635). RecRun timecode = frameIndex / nominal integer fps (CdngEncoder.cpp:330-345; AudioRecordingSession.cpp:122-128 for the WAV); FreeRun timecode = local time of `wallClock` with `frame = floor(frac_second * fps)` (CdngEncoder.cpp:348-360; AudioRecordingSession.cpp:130-135; MLV uses `recordingTimecode` RecordingClock.hpp:50-61). MLV per-frame time = `ts - firstTimestampUs_` in real sensor microseconds (MlvEncoder.cpp:1294-1304, written at :1024 with `frameIndex` at :1025).

**Consequence today without a lock (PROBABLE, derived):** the qbc IMX585 helper already makes 24/25/30/50/60 exact on the sensor's own 74.25 MHz clock (see 4), so the residual cadence error vs BOOTTIME is the sensor-crystal vs Pi-crystal offset, typically tens of ppm, sign unknown. If the sensor runs slow by e ppm: (a) `nextFrameIndex` skips an index (a hole in the DNG/MLV numbering with no real drop and no log) when `k * e >= 0.5`, i.e. first hole after 0.5/e frames (e = 30 ppm at 24 fps: frame ~16,667, ~11.6 min; then every 1/e frames); (b) `observeVideoFrame` rolls the WAV one frame longer at the same point; (c) FreeRun TC occasionally skips a frame number. If fast: indices stay consecutive (the counter wins), the WAV is nominal-length, but audio (measured against BOOTTIME) drifts against the picture by e x clip length (30 ppm x 1 h = 108 ms). The 20 ppm resampler floor leaves up to 72 ms/h of ALSA-crystal error uncorrected in either case.

**If the cadence becomes exactly nominal in BOOTTIME (servo referenced to `SensorTimestamp`):**
- Holds and improves: `observeVideoFrame` rounding is exact (phase bounded by the servo clamp, 150 us = 0.0036 period at 24 fps; typically within the 6 us deadband plus one lattice step); `nextFrameIndex` never skips an index; WAV length = N x nominal period exactly; A/V long-term drift from the sensor crystal is removed because the picture is now disciplined to the clock the audio is measured against; FreeRun TC frame numbers are monotonic except for a first-frame phase within ~15 us of a TC-frame boundary (probability about 15/41667).
- Breaks: nothing. The trim/pad logic is unchanged (first frame stamp still real).
- Resampler: **keep**. It corrects the ALSA crystal against BOOTTIME, which the video lock does not touch. Optionally lower the 20 ppm floor later; unrelated to the lock.
- Cadence-dependent fields: nothing else to change. `RecordingClock` keeps its constant offset, so the wall-clock stamps stay `boot + const`.

**If the cadence becomes exactly nominal in REALTIME (servo referenced to `FrameWallClock`, as Cinemate):**
- `FrameWallClock` follows NTP slew (ClockRecovery refits continuously, 100-sample window). REALTIME - BOOTTIME then changes at the slew rate (zero with no time daemon; a few ppm steady-state; up to 500 ppm during an `adjtime`-style correction, more with chrony's default maximum slew). Everything BOOTTIME-based in Core then sees the sensor drift by that rate: `nextFrameIndex` holes and WAV roll-over reappear after 0.5/slew frames, A/V drift = slew x clip length (10 ppm x 1 h = 36 ms), and `RecordingClock`'s constant offset disagrees with `FrameWallClock` by the accumulated slew inside a clip.
- To make a REALTIME lock sync-neutral Core would have to resample audio by the REALTIME/BOOTTIME ratio or stamp audio in REALTIME: more code, and a dependency on NTP state. Cinemate picked `FrameWallClock` because its audio clock is wall time (cinepi-raw/cinepi/cinepi_controller.cpp:733-737@63a08d5 "FrameWallClock = the audio clock"); Core's audio clock is BOOTTIME, so the analogous choice for Core is **BOOTTIME**. Recommendation: reference the servo to `SensorTimestamp` directly and keep the audio path untouched.

## 4. Cadence gate and gap estimator vs a dithering FrameDuration

**Cadence gate (CONFIRMED, CameraController.cpp:6984-6997):** active only while `waitingForRecordingCadence_` is true, i.e. from `startRecording` (set at :5967/:5978) until the first accepted frame (`if (ready) waitingForRecordingCadence_ = false;` :6996). Conditions (:6994-6995):
- `!timestamp || *timestamp / 1000 >= recordingStartBootUs_` (frame started after record start), and
- `!duration || |normalizeFrameDurationToUs(*duration, fps) - expected| <= max(500, expected / 50)` with `expected = llround(1e6 / settings_.fps)` (:6993).
Frames that fail are **neither recorded nor counted**; they are requeued (:7004) and the gate retries on the next completion. After the first pass the gate is never re-evaluated during the clip.

**Gap estimator (CONFIRMED, `trackRecordingCadence` :7520-7561):** `deltaUs = ts - lastTs` (:7536); `nominalFrameUs` = the frame's own `FrameDuration` metadata if > 0, else `1e6/fps` (:7539-7543); gap if `deltaUs > (nominalFrameUs * 3) / 2` (:7545); `estimate = (deltaUs + nominal/2) / nominal - 1` (:7546); accumulates `recordingGapEstimate_`, latches `dropWarning_.markDropped()`, logs `ApertarCore drop[capture-gap]: +N frame(s) estimate dt_us=... nominal_us=... total_estimate=...` (:7556-7562). Non-monotonic timestamps just reset `lastTs` (:7531-7534). Summary at stop: `ApertarCore capture stats: dropped_gap_estimate=... requeue_failures=...` (:5998-6002).

**Thresholds (computed from the source formulas):**

| fps | FrameDurationLimits sent `int64(1e6/fps)` | gate `expected` | gate tolerance `max(500, expected/50)` us | gap threshold `(nominal*3)/2` us |
|---|---|---|---|---|
| 23.976 | 41708 | 41708 | 834 | 62562 |
| 24 | 41666 | 41667 | 833 | 62499 |
| 25 | 40000 | 40000 | 800 | 60000 |
| 30 | 33333 | 33333 | 666 | 49999 |
| 48 | 20833 | 20833 | 500 | 31249 |
| 50 | 20000 | 20000 | 500 | 30000 |
| 60 | 16666 | 16667 | 500 | 24999 |
| 120 | 8333 | 8333 | 500 | 12499 |

**Dither magnitudes:** line time at the mode-minimum HMAX 550 is 550 / 74.25 MHz = 7.407 us (74.25 MHz from `kClock` in libcamera(qbc)/src/ipa/rpi/cam_helper/cam_helper_imx585.cpp:132; HMAX=550 on all imx585 modes per dmesg in cinemate-handbook/lessons/hardware-log.md:1151@c99ff77). The helper's comment says the driver rounds VMAX even (cam_helper_imx585.cpp:100-102) so the VMAX quantum is 2 lines = 14.8 us at HMAX 550 (the imx585 kernel driver is not in the sparse kernel checkout: UNKNOWN from driver source, PROBABLE from the helper comment). Cinemate's servo clamp is +/-150 us with a 6 us deadband (cinepi-raw/cinepi/phase_lock_core.hpp:27-32: kp 0.06, ki 0.0015, deadbandUs 6.0, clampUs 150.0; clamp applied at :149; PI at :144-150; integer rounding = dither at :154-162).

**Verdict (CONFIRMED arithmetic):** worst-case excursion 150 us + one lattice step (<= ~17 us) = ~167 us is 3x below the smallest gate tolerance (500 us) and about 0.4 % of a 24 fps period against a 50 % gap threshold. The gate will not skip a servo frame and the estimator will not count a gap. `nextFrameIndex` needs an accumulated phase error of +0.5 period (20,833 us at 24 fps) to skip, which a clamped servo cannot reach. Because the gate only runs once at record start, and Cinemate runs the servo in preview as well, the frame duration at record start is already within the clamp of nominal and passes on the first frame.

**Core-specific hazard (PROBABLE, read from the fork, not tested):** Apertar's libcamera fork overrides `CamHelperImx585::getBlanking` (cam_helper_imx585.cpp:119-226, commit 4cff971 "imx585 exact frame-rate getBlanking", 2026-06-02; the cinemate fork's helper is 71 lines with no override, libcamera(cinemate)/src/ipa/rpi/cam_helper/cam_helper_imx585.cpp@bfe0b76). When `min == max` (:127-129) it (a) snaps a request within 1 us of an integer rate's exact period to that period (:160-167: 41666 and 41667 both become exactly 1/24 s), (b) searches the integer lattice for even VMAX x HMAX in [HMAX_min, 1.5 x HMAX_min] (:144-145, :187-204) with HMAX free, preferring an exact hit or the lowest HMAX within half a microsecond (:183, :207-210), and (c) re-fits exposure to the new line length (:220-223). Worked example for the 4K mode (HMAX_min 550): 24 fps exact needs an even VMAX x HMAX = 3,093,750 ticks; HMAX 550 gives odd 5625, so the search lands on HMAX 625 x VMAX 4950 (line 8.42 us) - i.e. Core today probably runs 24 fps at HMAX 625, not 550. A servo request of 41665 us (outside the snap window) has target 3,093,626 = 2 x 17 x 90,989 ticks with no divisor in 550..825, so it jumps to some other (VMAX, HMAX) pair, changing the line length (rolling-shutter skew) and the exposure fit by up to a few percent per dither step, while 41666/41667 both collapse to the identical exact period. The effective dither alphabet is therefore not "+/-1 line" but {~41665.x, 41666.67, ~41668.x} with changing HMAX. A port must decide between: dithering in whole VMAX steps at a fixed HMAX by requesting exactly `V x H / 74.25e6` durations the search will hit; adding a "hold HMAX near the last value" rule to the helper; or accepting line-length changes. This needs a hardware check of `FrameDuration` metadata and the HBLANK control readback before choosing. Default `CamHelper::getBlanking` (no override) floors the frame length to whole lines of the mode-minimum line length (libcamera(qbc)/src/ipa/rpi/cam_helper/cam_helper.cpp:96-97, :121), which is the Cinemate regime.

## 5. Where the servo step runs and how its control reaches the next request

**Thread and order (CONFIRMED):** `requestComplete` (:6915-7005) runs on libcamera's completion thread with `sessionSettingsMutex_` held shared for the whole callback (:6926; comment "Keep the settings -> controls lock order consistent"), reads metadata (white balance :6938-6950, exposure/gain :6956-6957), `capturePhotoFrame` (:6967), preview publish (:6982), then the recording block under `recordingFrameMutex_` (:6984-7002) and finally `requeueRequest(request)` (:7004). The servo step belongs right after the metadata read and before `requeueRequest`: read `SensorTimestamp` (ns), compute the phase error against `t0 + k x period` in BOOTTIME, run the PI step, and store the requested duration in a session member. Lock order is safe: the callback already holds the settings shared lock; `applyControls` takes settings (unique) then `controlsMutex_` (:5841-5842); the servo takes `controlsMutex_` only.

**Delivery (CONFIRMED):** `requeueRequest` (:6833-6912): `reuse()` clears controls (:6838) -> `pendingControls_` merged and cleared (:6840-6844) -> photo block under `photoCaptureMutex_` (:6846-6901, the three OverwriteExisting merges at :6855-6857, :6869-6871, :6891-6893) -> `camera_->queueRequest` (:6903-6911, `drop[requeue-failed]` log). The servo pin goes **after** the photo block (so it wins by `set()`), skipped whenever `settings_.photoModeEnabled`, `!pendingPhotoCaptures_.empty()`, `restoreStillPreviewControls_` or `stillExposureActive_` (members :7866-7869). Then: IPA `applyControls` FRAME_DURATION_LIMITS (ipa_base.cpp:1313-1317) -> `applyFrameDurations` clamp + metadata echo (:1780-1797) -> `applyAGC` -> `getBlanking` -> `V4L2_CID_VBLANK`/`HBLANK` via `DelayedControls` (vblank/hblank delay 2 frames, camera_sensor_properties.cpp:389-394). Expect the new duration to show in `FrameDuration` metadata about 2 frames after the request is queued, plus the 3-deep request queue (`requests_` :7827; "3 requests in flight" per the brief).

**Interplay to respect:** `applyControls` can replace `pendingControls_` at any time (fps changes only happen outside recording, :8083-8086); re-arm the servo whenever `settings_.fps` changes or `reconfigure` runs; disable it in photo mode (ranges, long exposure, brackets); the cadence gate at record start is unaffected (4). The IPA echoes the clamped `FrameDurationLimits` in metadata, so the servo can detect saturation at the mode minimum (at the maximum fps of a mode the loop can only lengthen frames).

## 6. What a port needs (Core)

1. **Hook points.** (a) Servo step in `requestComplete` after the metadata read, before `requeueRequest` (CameraController.cpp:6915-7004); input `SensorTimestamp` ns (BOOTTIME), output `std::optional<int64_t> servoFrameDurationUs`. (b) Apply in `requeueRequest` after the photo block, before `queueRequest` (:6901-6903) with `request->controls().set(FrameDurationLimits, {d,d})`. (c) Re-arm on `applyControls` when fps changed (:5827-5856), on `reconfigure`, and at `start`; clear in `stop()` next to `pendingControls_.clear()` (:5764-5767). (d) Read back the IPA-validated `FrameDurationLimits` and `FrameDuration` metadata each frame for saturation detection and telemetry.
2. **Per-session state object** in `CameraSession` (members block :7830-7875), e.g. `struct FramePhaseLock { bool enabled, active; double targetFps, baseDurUs, reqDurUs, integral; int64_t t0Ns, lastTsNs; uint64_t frameCount; int64_t lastDurUs; int64_t minDurUs, maxDurUs /* from metadata clamp */; int64_t maxAbsErrUs; uint64_t controlChanges; }` guarded by `controlsMutex_` (or atomics for the telemetry).
