## G2-core-record-path (/home/user/apertar-kb/working/merge-review/hdr12/G2-core-record-path.md)

Traced the IMX585 Clear HDR 12-bit frame through Core at cinemate-port 01f170c from the mode request to the cDNG and MLV bytes, and ran the real CdngEncoder, LosslessJpegEncoder and MlvEncoder on this host (no camera). Core requests SRGGB12_CSI2P with sensor bit depth 12 (transport size = active size), skips the bit-depth test of its exact-mode check in Clear HDR, and assumes without any check that libcamera hands back unpacked 16-bit linear samples (black 3200, white 65520). For cDNG the copy worker maps each linear sample back to its 12-bit CCMP code and the encoder writes BitsPerSample 12, a 4096-entry LinearizationTable ([0..201]=3200 ... [4095]=65520), BlackLevel 3200 and WhiteLevel 65520, both in the linearised domain; the port's own reader returns the input with 0 differing samples, uncompressed and lossless, and Log on gives a composed table with at most 69 LSB16 error. MLV has no table, so 12-bit Clear HDR is stored as linear 16-bit (RAWI 16 / 3201 / 65535); Log is refused in MLV and Lossy DNG is refused in all Clear HDR. One real defect sits in this path: the storage depth (12 for cDNG, 16 for MLV) is fixed at configure time from the recording format, and set_record_format cDNG <-> MLV does not reconfigure when size, depth and Clear HDR are unchanged, so an MLV take after cDNG stores only the low 12 bits of the linear samples (wrapped picture, RAWI 12 / 200 / 4095) and a cDNG take after MLV fails at its first frame with "Invalid RAW linearization table.". That defect hits only 12-bit Clear HDR, dates from fork main 57c8fb0 and is carried, not introduced, by the port; upstream 1.6.0 made the storage depth a function of the bit depth alone. The port did not change the 12-bit arithmetic: ClearHdrCcmp.hpp is byte-identical to fork main, the new direct-write path is not taken by 12-bit views, the black/white helpers give the same numbers, and the MLV black for 16-bit containers was fixed (200 -> 3201). Outside that defect Core stores what libcamera delivers to within one table step, so a strange file recorded right after a configure points before Core (libcamera's expansion, the binned mode's curve, the sensor knobs) or at the reader; an MLV of the same scene is the split test. The other inconsistencies found are latent (one fact decided in three places, a black clamp in the wrong domain, depth-only branches, an IFD template cache key that ignores the table). The relayed user request about reinserting the GPIO chip definition is outside this step and was not acted on.
