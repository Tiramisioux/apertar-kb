## 0. Short answer

Core at `9d4f7fb` does not ramp: one `if` in `setFps` refuses any change while recording (`src/camera/CameraController.cpp:8543-8546@9d4f7fb`, message "Stop recording before changing FPS so video and audio keep the same timeline.") — **confirmed**. Below that gate everything an fps change needs is already a one-request control write: `applyControls` → `pendingControls_` → the next `requeueRequest` carries the new `FrameDurationLimits`, no camera stop, no buffer reallocation (`CC:6124-6157`, `:7271-7277`) — **confirmed**. Four things assume one rate per clip and would misbehave if the gate were simply removed: the recorder's elapsed-time frame numbering, the WAV endpoint model, the per-frame `FrameRate` tag and timecode that follow the *live* fps, and the H.264/ProRes containers (one `time_base`) — **confirmed** from the lines in §2.

Cinemate ramps because cinepi-raw has no gate at all: `set fps` → Redis `fps` → a `FrameDurationLimits` push on the next request (`cinepi/cinepi_controller.cpp:968-979@63a08d5`), frames numbered by count (`dng_encoder.cpp:474`), timecode counted at the start rate (`:2119-2136`), the WAV left in real time (`cinepi_sound.cpp:1527-1538`) — **confirmed**. It also has two defects worth not inheriting (§1.3): a ramp *down* registers as a dropped frame on every frame for the rest of the take, and the "keep angle" shutter mode is a GUI statement only, the sensor keeps its absolute exposure in both modes — **confirmed** from the lines, hardware effect **probable**.

The port (commit `d4ad539`, §3) lifts the gate for cDNG, lossy DNG and MLV takes behind a setting `fps_ramp` (off by default), numbers frames by count, pins every frame's `FrameRate` tag and timecode to the rate the take started with so the sequence is one clip at that rate (a faster segment plays as slow motion), ends the WAV at the last frame's own duration, makes the shutter policy explicit (`angle` = Core's existing rescale, `exposure` = Cinemate's mode 1), keeps the capture-gap estimate and the phase lock quiet for N+6 frames after each change (N = the raw request count), writes one `fps-ramp.txt` per take with the requested and the actually-applied frame of each change, keeps ramp steps out of the settings file and returns to the start rate at stop, and adds a `ramp_fps {to, seconds}` stepper. Host syntax checks pass for every touched file except `CameraController.cpp` (libcamera); nothing ran on a Pi.

## 1. What Cinemate does (r1)

### 1.1 Operator path — confirmed

- `set fps <v>` → `CinePiController.set_fps` (`cinemate/src/module/cli_commands.py:69`, `cinepi_controller.py:1747-1857@d6cc93e`). The only gate is `fps_lock` (`:1756-1758`); recording is not a gate.
- Mid-take the value is capped to what the running sensor mode can deliver (`_in_take_fps_ceiling`, `:904-930`, applied `:1792-1797`) and the mode ladder is asked about the fps that will actually be commanded (`ff59dd8`, `:1799-1810`). A same-class live reconfigure mid-take **splits the clip** into two folders and two WAVs (`cinepi_raw.cpp:68-76`, `:365-375`) — the reason the ceiling exists.
- The value reaches the sensor as `FrameDurationLimits = {1e6/fps, 1e6/fps}` (truncated `long`) via `SetControls` on the next request (`cinepi_controller.cpp:968-979`, `core/rpicam_app.cpp:1020-1023`).
- `set_fps_double` (`:4074-4117`) toggles 2× when the doubled rate fits the current mode; `_ramp_fps` (`:4119-4136`) steps ±1 fps every 0.2 s to a constant 48 and has no caller (72 Redis publishes for a 24-step ramp, r1 verification #23) (experimental, as the doc says: `docs/speed-ramping.md:7-25`).

### 1.2 Shutter policy — confirmed from source (hardware picture still open)

`shutter_a_sync_mode` 0 recomputes the angle table and snaps the displayed angle; mode 1 recomputes the angle from a stored nominal exposure time (`:1831-1852`, doc `:27-35`). **But** `set_fps` never writes the `shutter_a` key, and cinepi-raw recomputes `ExposureTime` only in its `shutter_a`/`shutter_speed` handlers (`cinepi_controller.cpp:851-868`); the helper that would re-push the angle (`update_shutter_angle_for_fps`, `:1707-1719`) has no caller. So across any `set fps` the sensor keeps its previous absolute exposure in both modes until the shutter is next touched; mode 0's "constant angle" is display-only. The verifier settled the mechanism from source (r1 verification #38): cinepi-raw runs the IPA in manual exposure mode (`core/rpicam_app.cpp:825-828@63a08d5`), the IPA stores the last `ExposureTime` as a fixed value (`src/ipa/rpi/common/ipa_base.cpp:851@bfe0b76`) and a `FrameDurationLimits` change only re-clamps it to the new frame's maximum (`ipa_base.cpp:1638-1667`, `agc_channel.cpp:1030`; frame-length clamp `cam_helper.cpp:107-108, 123-124`). Brightness step: none on a ramp down; on a ramp up none until the old exposure exceeds the new frame, then ≈ log2(old_exposure × new_fps) stops darker (180° at 24 → 48 fps lands at ≈ 360°, same brightness; → 96 fps clamps to 1/96 s, ≈ 1 stop darker). What the operator sees on hardware is still **unknown**.

### 1.3 What the files do under a ramp — confirmed lines, probable numbers

- **DNG `FrameRate` (0xC764)**: per frame from the live `options_->framerate` (`dng_encoder.cpp:1678-1692`), read when the encode worker reaches the frame, so it follows the ramp with an encode-queue lag. Cinemate's own playback reads the tag from the take's first frame only (`playback.py:163-180`).
- **Timecode**: `tc_fps_` fixed at the clip's first frame from the configured rate (`:2062-2121`); later frames add `max(1, llround(Δts × tc_fps_ / 1e6))` and count `raw_elapsed − 1` as dropped when ≥ 2 (`:2126-2136`). Ramp up 24→48: +1 per frame, TC runs at 2× wall clock, no holes. Ramp down 48→24: `raw_elapsed = 2` on every frame → **a false dropped frame per frame for the rest of the take**, TC skipping every other count, and a Tier-1 drop flash per frame once the `user_changing_fps` leeway expires (`redis_listener.py:1153-1169`).
- **File numbering**: `index_++` per queued frame (`:474`), independent of fps.
- **WAV**: PCM never retimed, BEXT at the take-start rate (`cinepi_sound.cpp:149-154`, `:816-820`, `:1527-1538`). Real time, honest.
- **Sync verdict**: an fps change mid-take suppresses the live sync warning (`redis_listener.py:604-621`, `:1866-1870`) — no false verdict, and no true one either.

### 1.4 Phase lock — confirmed

`phaseLockStep` re-arms when the target fps changes (`phase_lock_core.hpp:96-111`; test `tests/phase_lock_core_test.cpp:256-265`). A stepped ramp re-arms per step, so the lock contributes nothing during the ramp and re-converges after the last step (**probable** from the law; not simulated). The gap test uses the *new* target's period (`phase_lock_core.hpp:92`), so a ramp-down step is not even a big gap — no phantom missed frames (r1 verification #65).

### 1.5 Lessons Cinemate recorded (commit bodies)

(a) choose the mode for the fps you will actually command (`ff59dd8`); (b) a take-scoped cap must not become the operator's new target (`ff59dd8`); (c) derive the TC base from the configured rate, keep DNG and WAV rounding identical (`3c6477e`, F-253); (d) per-frame TC stepping under one mutex with the frame's own timestamp (`dcd2b65`); (e) count drops only on ≥ 2-period gaps (`05eb4a0`); (f) silence the sync verdict on a mid-take change (`a4d511c`, 2026-05-24; the verifier corrected the attribution from `8ee9059`). Also from the verification: cp_stats `frameCount` is the index of the last frame the encoder dequeued, not the capture counter, so it lags a ramp by the queue depth (#51); the ×1000 `FrameRate` fix and the removal of the per-frame `FrameDuration` path landed silently inside "silence all compiler warnings" (`210d0fb`, #43). Not recorded anywhere: the exposure gap of §1.2, the stale TC base of §1.3, that `_ramp_fps` targets 24×2. The handbook has no speed-ramping entry (grep: only highlight "ramps").

## 4. What to expect on the Pi

What to expect in the first test (T31 §5):

- 25 fps cDNG take, `ramp_fps to=50 seconds=5` at 10 s, `ramp_fps to=25 seconds=5` at 20 s, stop at 30 s: file count ≈ 25×10 + 50×5 (ramp mean ≈ 37.5 → ~188) + … ; more usefully, **contiguous numbering with no holes** and `fps-ramp.txt` with 50 lines (25 steps up, 25 down), each with an applied frame — **probable** (arithmetic).
- `ApertarCore fps ramp: frame=N frame_us=20000 delta_us=... lag_frames=L superseded=S` lines: `lag_frames` about N+2 — 6 on ext4, 8 on exFAT, 10-12 with Clear HDR (**probable** ±1, critic K5); the stepper's 200 ms steps are 5-10 frames apart, so two requests can collapse into one period change (`superseded=1`). The `delta_us`/`frame_us` pair on the first transition line settles whether a delta spans the previous frame (critic K4).
- No `drop[capture-gap]` lines caused by the ramp; `dropped_gap_estimate` unchanged from a non-ramp take.
- WAV length = real elapsed (30 s ± one frame); the picture on a 25 fps timeline is longer (the 50 fps segment plays at half speed). In Resolve the sequence imports at 25 fps with one `FrameRate` throughout; RecRun TC continuous; FreeRun TC continuous and counting at 25.
- Phase lock on: no "released" line (the release in applyControls is silent); "armed" N+6 frames after the last step up and again after the last step down; `max_abs_err_us` at stop no worse than a non-ramp take after the settle.
- `policy=exposure`: brightness constant through the ramp, the same blur per frame (the angle doubles at 50), until the exposure would exceed the frame — then the line says `(shutter clamped to the frame)`, the picture is as bright as the frame allows, and the ramp back down returns to the operator's exposure;
- A take stopped while ramped: `take ended at 50 fps, restoring 25`, `get_state` shows 25, the settings file was written once at stop and not during the take; `policy=angle`: blur constant, one stop darker at 50 (as Cinemate's doc describes for its mode 0, which its sensor does not actually do — §1.2).

## 5. Limits and unknowns

- **MLV**: ramp allowed; the file carries real per-frame times and the start rate in the header. Whether MLV App plays by the header rate (conform, slow motion) or honours VIDF times is **unknown**; test one take before relying on it.
- **Which `FrameRate` an NLE samples** from a sequence is unknown; the port sidesteps it with a constant tag.
- **Lossy DNG** under a ramp up: the encoder budget is per frame; 50 fps lossy at 4K may hit the same ceiling as a steady 50 fps take (`enforceLosslessCaptureLimits`, `CC:2874`) — the clamp applies, the ramp stops at the ceiling.
- **Drops in a ramp take** do not leave numbering holes (count-based). Use the counters.
- **Stepper granularity**: one fps per step; sub-fps ramps need `set_fps` calls from a script. Steps faster than one frame simply replace the pending control (`applyControls` assigns `pendingControls_`, `CC:6140@9d4f7fb`); the sensor sees the latest, nothing is corrupted (r2 verification, row 64). A single jump of more than 1.5× (30→50) is the one case the gap estimator could misread; the stepper never makes one.
- **Grace vs a window-free rule** (critic Q2): `gap iff delta(n) > 1.5 × FrameDuration(n−1)` would need no window and would keep the estimator armed through a stepper's whole ramp (the grace keeps it and the phase lock off for the ramp plus N+6 frames — the same suppression r1 faulted in Cinemate's sync verdict, though here only for the duration of the ramp). It rests on the delta spanning the previous frame (K4, **probable**); the `delta_us`/`frame_us` pairs on the Pi decide it. Kept as the grace for now; the window-free rule is T31 §8's exercise.
- **FreeRun timecode semantics change for every take with `fps_ramp` on** (critic Q12), ramped or not: it counts at the start rate from the first frame's wall time, so without the phase lock it drifts from wall time like RecRun (30 ppm → 108 ms/h, T27). Turn the setting off for takes that need wall-clock FreeRun.
- **Writer budget at the new rate** (critic Q11): the T29 profile has no fps term; 25 → 50 at 4K uncompressed doubles the write rate, and queue-full drops in a ramp take leave no numbering holes — only the counters show them.
- **Lossy DNG** encoder throughput at 2× is unknown (critic Q23); the tags are pinned the same way as cDNG.
- **What the WAV says**: nothing marks it as a ramped take (critic Q17); `fps-ramp.txt` next to it does.
- **Which imx585 driver the rig runs** decides the SHR/VBLANK facts the exposure clamp rests on (critic Q21: README says `apertar@e5b74d3`, the local checkout is `cinemate-modes@18c1eb2`, the T26 worktree `98b9862`).
- **Not verified on hardware**: everything above. The grace length (requests + 6 frames of the slower rate, at least 10) is derived from the queue depth and the DelayedControls chain, not measured; `APERTAR_FPS_RAMP_GRACE_FRAMES` is there for the day the `lag_frames=` figure says otherwise.
