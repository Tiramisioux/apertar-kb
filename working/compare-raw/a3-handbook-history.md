# a3-handbook-history — what Cinemate recorded about frame drops, disk writes and per-frame budgets

Reader: THEORY A/B part 3 (handbook + docs + commit history). Status: COMPLETE.
Commits read: cinemate-handbook@c99ff77, cinemate@d6cc93e, cinepi-raw@63a08d5, libcamera(cinemate)@bfe0b76, libcamera(qbc)@7e9fef0 (PROBABLE base of the Pi binary, not confirmed).
Every line number below was opened and read (grep anchor + sed window). Nothing was run on a camera.

Headline for Theory A/B:
- Cinemate's record contains NO episode that links single-frame gaps to page-cache writeback, dirty pages, O_DIRECT or "disk busy". The only disk-side drop mechanisms Cinemate ever recorded are (a) sustained write bandwidth too low (NTFS-over-FUSE 16-bit soak stalls, USB-SSD SLC cliff) and (b) short write()/close() failures on NTFS. The dirty_bytes/scheduler/nr_requests profiles were written as design reasoning (balance_dirty_pages stall theory), never measured.
- Cinemate's one confirmed single-frame-gap mechanism (commit 31126f2, 2026-05-31) is "RAM permits momentarily exhausted -> camera buffers held -> sensor starved for one frame period", i.e. the recorder's completion path blocking libcamera's buffer return. Their fix was more libcamera buffers (6 -> 8/10), justified by reasoning and "field observation", no measurement.
- Cinemate's 2026-09-15 4K 16-bit drop episode was a second full software render per frame on the preview (post-processing) stage; measured 6.25 fps / 208 drop events at 25 fps; fixed by making 16-bit an in-place highlight correction. The suspected measurement pass was timed at 0.38 ms/frame and exonerated.
- Cinemate's libcamera fork does the 16-bit rev16 swap in cfeBufferDequeue but has NO RawStatsProducer/CcmpUnwrap (grep: zero hits in libcamera(cinemate)@bfe0b76 pipeline dir). The qbc fork (probable Apertar base) has both and runs them in the same cfeBufferDequeue after the swap — two CPU passes per frame on the pipeline thread. Cinemate therefore never saw, and never recorded, the second pass that Core 94ac68d worked around.

## Q1. Every recorded episode of dropped frames

### E1 — 2026-08-27/28: 16-bit soaks stall when the RAM pool fills (sustained NTFS/FUSE write bandwidth)
- CONFIRMED cinemate-handbook/lessons/hardware-log.md:945@c99ff77 heading "RP1 overclock IS compatible with mono ClearHDR; the real limits are storage and a shutter-apply delay".

The libcamera completion callback itself only pushes to encode_queue_ (:479-481) — it does not block — so the "camera buffers held" claim is about the encode queue holding libcamera's request buffers until encode finishes.

## Q4. Why --buffer-count 8, and cinepi-raw's "6 buffers is better than 4"

- cinemate commit 31126f2 (2026-05-31): quoted in E4. Reasoning only: "+2 over base", "Each extra buffer is ~25 MB of CMA at 4K".
