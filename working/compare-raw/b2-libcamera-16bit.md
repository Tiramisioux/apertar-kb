### The WHY (sensor BE? CFE MSB-first? packing bit?)
- Cinemate fork: no explanation beyond "HW missing this feature" (:1450-1451). UNKNOWN from that fork alone.
- qbc fork IPA gives the mechanism (CONFIRMED text): libcamera(qbc)/src/ipa/rpi/pisp/pisp.cpp:699-706@7e9fef0: "RAW14 / RAW16 path: the CFE->FE input is big-endian (omitted byte-swap in CSI2AXI) while FE pixel blocks assume little-endian, so any non-trivial FE pixel processing corrupts the data. Per upstream guidance (libcamera issue #99 — comment by njhollinghurst), Decompand/BLA/DPC/Downscale/Compress must be disabled or no-op'd. SW endian-swap fixes the FE output buffer before BE consumes it." Gate :695-697 `mode_.bitdepth >= 14 || imx585HdrCcmp`; FE BLA+BLC zeroed :715-719, per-channel pedestal moved to BE BLC :721-726. The cinemate IPA has no such gate: libcamera(cinemate)/src/ipa/rpi/pisp/pisp.cpp applyBlackLevel (grep SetBla :618, SetBlc :624-625) always programs FE BLA with the pedestals.
  => Mechanism (PROBABLE, from that comment + kernel table below): the sensor sends CSI-2 RAW16 (MSB byte first on the wire); RP1's CSI2->AXI block omits the byte swap for 16-bit, so the FE/CFE writes the bytes in wire order = big-endian u16 in memory, while V4L2 SRGGB16 (and the PiSP BE input) expect little-endian. It is not a packing bit and not a sensor option.
- Kernel side (CONFIRMED, extra source): kernel-rpi/drivers/media/platform/raspberrypi/rp1_cfe/cfe_fmts.h:197-227@5bd564a: all four Bayer 16 entries have `.csi_dt = 0, /* Avoid RP1 HW mismatch for 16-bit modes. */` (:200, :208, :216, :224), `.flags = CFE_FORMAT_FLAG_FE_OUT`, remap to {SxxxX16, PISP_COMP1_xxxx}. The Y16 entry :283-290 still has `.csi_dt = MIPI_CSI2_DT_RAW16` (:287). This matches cinemate-handbook/lessons/hardware-log.md:836-841@c99ff77 ("Bayer 16-bit entries carry csi_dt = 0 ... but the Y16 entry kept csi_dt = MIPI_CSI2_DT_RAW16 — the 6.12.93 16-bit workaround was never applied to mono") and :868 (fix stack: "rp1-cfe Y16 csi_dt=0 kernel patch"). The commit that introduced csi_dt=0 is not in the 1-commit shallow kernel clone (UNKNOWN).

## Q6. Could the swap be avoided?

1. Little-endian 16-bit CFE output format: NONE exists (CONFIRMED in the kernel table + libcamera format tables). kernel-rpi cfe_fmts.h:197-227@5bd564a: the only 16-bit Bayer fourccs are V4L2_PIX_FMT_S{BGGR,GBRG,GRBG,RGGB}16 (remap to themselves or PISP_COMP1_*); no _BE variants; libcamera(cinemate)/src/libcamera/formats.cpp:851-884@bfe0b76 and bayer_format.cpp:164-170, :190 (R16 <-> Y16) list only these; the only "_BE" format in libcamera is RGB565_BE (formats.cpp:162). The qbc IPA comment (ipa/rpi/pisp/pisp.cpp:699-701) attributes the byte order to an "omitted byte-swap in CSI2AXI" — a hardware limitation, so no V4L2/csi_dt knob produces LE (PROBABLE: the comment is second-hand, citing libcamera issue #99).
2. PiSP BE reading big-endian directly: PROBABLE NO. kernel-rpi pisp_types.h:44-70@5bd564a `pisp_image_format` has BPS_8/10/12/16, PLANARITY, SAMPLING, ORDER_NORMAL/ORDER_SWAPPED (:61-62) and SHIFT_n; ORDER_SWAPPED is channel order (used with the Bayer-order comment :26-30 and PISP_IMAGE_FORMAT_order_swapped :125-126), not byte order. No byte-swap flag. libpisp itself is a wrap (subprojects/libpisp.wrap -> v1.3.0) and not checked out, so UNKNOWN whether libpisp exposes anything beyond these bits.
3. COMP1 route (CONFIRMED mechanism): with the CFE compressing to PISP_COMP1 (1 B/px) there is no swap in the cinemate fork (bcdd7e1 guard, pisp.cpp:1457-1459) and the BE "decompresses it natively" (:1453-1454); cinepi-raw maps `16:P` to BGGR_PISP_COMP1 (rpicam_app.cpp:132). Cost: lossy companding ("16/32/64 quantisation steps", bcdd7e1 message). Cinemate's own sensors.json nevertheless selects "U" for imx585 (resources/sensors.json:162), so Cinemate currently takes the swapped path. In qbc the route is closed: Packing::None is forced for WDR (:1662-1690), and the HEAD commit message says "PISP-COMP1 companding is itself unreliable at >=14-bit" (7e9fef0). Tension (PROBABLE, unresolved): the qbc IPA comment says FE "Compress must be disabled or no-op'd" for RAW16, while bcdd7e1 says the INNO-MAKER COMP1 route produces working 16-bit DNGs.
4. Swap only for consumers that need host order:
   - BE/ISP preview path consumes the Output0 buffer as ISP input (beInputDequeue re-queues it to CFE, cinemate :1800-1813 / qbc :2039-2052 region) and the qbc comment says the swap "fixes the FE output buffer before BE consumes it" — so as long as the preview/ISP runs from that buffer, the in-place swap is required (PROBABLE, given item 2).
   - RawStatsProducer could consume big-endian data by adding a `vrev16q_u8` after each `vld1q_u16` (raw_stats.cpp:220-221) — would remove the dependency of stats on the swap but not the BE's (opinion/PROBABLE; no such code exists).
   - DNG writers: both write little-endian TIFF headers — apertar-core/src/cdng/CdngEncoder.cpp:1741-1742@f60e301 `header[0] = 'I'; header[1] = 'I'`; cinepi-raw/cinepi/dng_encoder.cpp:1138@63a08d5 `write_pod(buf, "II", 2); /* little-endian */`. TIFF/DNG permit "MM" (big-endian) files, so an application COULD write the unswapped buffer with an MM header — but only if libcamera stopped swapping, which needs a code change in the fork (no env/flag exists, Q4). For Core this would also have to keep the preview working (BE) — i.e. the swap would have to become per-consumer, which the current single-buffer design does not support. All PROBABLE/opinion; nothing in either fork implements it.
   - Skipping the swap for an "External"-flagged raw stream when no ISP output is configured: not implemented in either fork (the condition at :1456/:1561 looks only at bit depth). PROBABLE opportunity, not confirmed safe (IPA still consumes CFE stats/BE).
5. Bottom line: CONFIRMED there is no format or switch in either fork or the kernel table that delivers host-order 16-bit without the CPU pass; the only swap-free 16-bit path is COMP1 (cinemate fork only, lossy).

### 3840x2160 12-bit CCMP ClearHDR
Cinemate fork: no swap (bitsPerPixel 12), no SW stats -> 0 passes; buffer format = whatever the app requests (cinepi-raw `12:U` -> SBGGR12 16-bit container 16.6 MB, or `12:P` -> SBGGR12_CSI2P 12.4 MB) — the HW stats are used.
