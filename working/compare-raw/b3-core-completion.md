## 0. Which thread runs requestComplete (CONFIRMED in libcamera source; binary match PROBABLE)

- Therefore everything in Core's `requestComplete` (:6915) runs synchronously on the same CameraManager thread that does libcamera's own per-frame CPU passes (fact 1: rev16 swap / CcmpUnwrap in `cfeBufferDequeue`, `RawStatsProducer::process`). ## 2. The buffer loop (CONFIRMED)

- Constants: `kConfiguredBufferCount = 4`, `kActiveRequestCount = 3` (:1047-1048). Preview config `bufferCount = configuredBufferCount` (:6411-6413, :6418); raw config `bufferCount = configuredBufferCount` (:6444) — i.e. **4 raw + 4 preview buffers** for cDNG. For processed formats the count comes from `h264CameraBufferCount()` (default 4 hw / 6 sw, env `APERTAR_H264_CAMERA_BUFFERS` 3..12, :1148-1152) or `proresCameraBufferCount()` (default 12, 8..32, comment "Cover frame-thread borrows, the worker/queue, and camera pipeline headroom", :1154-1158).
- Requests: `makeRequests` (:6788-6831): `activeRequestLimit` = `kActiveRequestCount` for raw modes (:6796-6797); `requestCount = min(previewBuffers.size(), activeRequestLimit, rawBuffers.size())` (:6798-6802); request i gets `previewBuffers[i]` and `rawBuffers[i]` (:6820-6822). → **3 requests in flight; the 4th raw and 4th preview buffer are never attached to any request.** All 3 are queued at start (:6700-6708).
- Consequence (confirmed from source): raising the buffer count alone (the "8 raw buffers" experiment, fact 3) cannot raise the in-flight count above 3 — the extra buffers are allocated and mapped but idle. For processed formats the limit follows the buffer count (:6796-6797); for raw it is hard-wired to 3.
- Hold time: `requeueRequest` is called at the very end of `requestComplete` (:7004), after the copy and the LUT. A libcamera buffer pair (raw + preview) is therefore held by Core for the whole callback: ≈ 8 ms (16-bit) / ≈ 16 ms (12-bit) + pool/web-preview extras, then `queueRequest` posts the request back to the CameraManager thread, which processes the message only after the callback returns. The two other requests stay with libcamera/CFE meanwhile. Steady state is fine as long as the callback finishes within one frame period; a callback that runs longer than ~2 periods leaves the CFE with no queued buffer.
- Who may requeue from another thread today: the ProRes path hands the mapped pointer to `proresRecorder_.enqueueFrame` with a completion lambda doing sync END + `requeueRequest(request)` (:7758-7767), and the H.264 path's `releaseRequest` lambda does the same (:7795-7804). `H264PreviewRecorder` runs `copyThreadCount_` (= `h264CopyThreadCount()` → 1, comment "One memory-copy worker preserves capture order", :4585-4589; member default 2 at :5120) `copyLoop` workers (:4297-4298) that `acquireFrameBuffer` → `copyYuv420Frame` → `releasePreviewJob(job)` (:4963-4978) — **copy on a worker, then release the libcamera request from that worker**; cancelled jobs are released on stop (:4831-4832, :4926-4927). That is the exact pattern the raw path lacks.

## 3. rawCopy: allocation, free, pool (CONFIRMED mechanism; costs est.)

- Allocated on the completion thread by `DngRecordingQueue::acquireRawBuffer(size)` (:3657-3679): under `mutex_`, picks the smallest pooled vector in `rawPool_` whose `capacity() >= size`; otherwise `return std::vector<uint8_t>(size)` (:3669) — a fresh, zero-initialised 16.9 MB heap block (glibc serves this size by mmap, so each new block is first-touch page-faulted and each free returns it to the kernel).
- Moved into `FrameJob.rawBytes` by `enqueue` (:3709-3714; struct :3727-3732). The worker re-points `job.frame.data = job.rawBytes.data()` (:3841), calls `encoder.writeDngFile(job.path, job.frame, job.metadata)` (:3851) and then `recycleRawBuffer(std::move(job.rawBytes))` (:3873; MLV path :3954).
- Pool policy `recycleRawBuffer` (:3970-3989): keep unless capacity > 1.5× expected, or `rawPool_.size() >= preferredRawPoolSize()`, or pooled bytes would exceed expected × maxRetained. `preferredRawPoolSize = min(maxQueuedFrames_, max(workerCount_ + 2, 4))` (:3992-3995). On a 4-core Pi 5: lossless 12-bit → min(24, 5+2) = **7 buffers (~118 MB)**; uncompressed 16-bit → min(12, 4+2) = **6 buffers (~101 MB)**.
- Consequences: (a) the pool is empty at the start of every take (`startAtFolder` (:3388) resets `pooledRawBytes_`/`expectedRawBufferSize_` :3417-3418; vectors freed by `stop()` joining workers), so the first 6-7 frames each pay a fresh allocation on the completion thread; (b) whenever the queue runs deeper than the pool (queue may hold 12/24 frames but only 6/7 vectors are retained), the surplus vectors are freed by workers and re-allocated by the completion thread — every such frame costs the zero-fill + page-fault (5-8 ms est.) **on the camera thread**, precisely when the encoder is already behind. This is a positive-feedback cost in the Open B regime (PROBABLE; the mechanism is confirmed, the magnitude estimated).

## 4. Hand-off to the encoder (CONFIRMED)

- Queue: `DngRecordingQueue` (declared :3358-4035 in CameraController.cpp; `CdngEncoder.cpp` has no threads or queue — grep for `std::thread|worker|queue` in src/cdng/CdngEncoder.cpp returns nothing). `maxQueuedFrames_` default member 12 (:4029); at start: `defaultQueueFrames = compressedDng && hardwareThreads >= 4 ? 24 : 12` (:3437), env `APERTAR_CDNG_QUEUE_FRAMES` clamp 4..64 (:3438-3439). → Pi 5: **24 frames for 12-bit lossless, 12 for 16-bit uncompressed** (each queued frame owns a 16.9 MB vector: up to ~405 MB / ~203 MB of heap at full queue).
- Workers (:3432-3459): `hardwareThreads = hardware_concurrency()`; `normalWorkerCount = clamp(2..4)`; lossless default `min(8, threads+1)` (comment "One extra lossless worker overlaps tile-write and scheduling stalls") → **5 on Pi 5**, env `APERTAR_CDNG_WORKERS` 1..8; uncompressed cDNG → `normalWorkerCount` = **4**; lossy `min(4, threads)`; MLV 1. One `CdngEncoder` instance per worker (:3820). Worker nice: `APERTAR_CDNG_WORKER_NICE`, default 0 for lossless, 5 for lossy, applied only when > 0 (:3808-3818) — so lossless workers run at nice 0 against the completion thread's nice -5. Log line "workers= queue= tile_rows= encoder=quad_single_pass" (:3467-3472).
- Back-pressure: `hasCapacityForFrame` (:3637-3655) under `mutex_`: false if stopping/inactive/no workers; true iff `queue_.size() < maxQueuedFrames_`; otherwise `++droppedFrames_`, `dropWarning_->markDropped()`, log "drop[queue-full]" (first and every 30th). `enqueue` re-checks the same condition (:3688-3698). **What is dropped: the newest frame (never copied); nothing is evicted from the queue; the libcamera request is still requeued** (:7266 returns before the copy, :7004 runs regardless). `RecordingDropWarning::markDropped` is a clip-scoped latch (one UI notification per clip) — apertar-core/src/util/RecordingDropWarning.hpp:9-19@f60e301.
- Numbering: `nextFrameIndex` keeps `max(counter, time-derived index)` (:3627-3635), so a dropped/gapped frame leaves a hole in the DNG sequence numbers rather than renumbering.
- Where the bytes go: `CdngEncoder::writeDngFile` (apertar-core/src/cdng/CdngEncoder.cpp:1211@f60e301). Uncompressed: `::open(O_WRONLY|O_CREAT|O_TRUNC[|O_CLOEXEC])` (:1748-1753), `posix_fadvise(SEQUENTIAL)` (:1758), header, `writeRawPayload(fd, frame, layout)` (:1773), padding, IFD, `posix_fadvise(DONTNEED)` (:1779), close. Lossless: open at :1273, `rowsPerStrip = losslessTileRows()` (:1237), row-at-a-time decode/encode (comment :1279-1280), `pwrite` header fix-up (:1763-1769). No further whole-frame copy in the uncompressed path (buffered write of the vector).
- Stop: `DngRecordingQueue::stop` sets `stopping_`, notifies, **joins the workers** (drains what is queued) and prints "recording stats: enqueued= written= dropped_queue_full= discarded_on_stop= ... peak_queue=" (:3499-3532, the log at :3525). `CameraSession::stop` disconnects `requestCompleted` and `camera_->stop()` **before** `recorder_.stop()` (:5756-5772); `stopRecording` closes the gate then stops the recorders (:5990-6010) — relevant to §6 because requests held by workers must be returned before `camera_->stop()`.

## 5. Preview path cost on the completion thread (CONFIRMED mechanism; costs est.)

- Resolution: `previewSizeForSensorMode` bounds the preview to `kPreviewWidth 1280 × kPreviewHeight 720` keeping aspect (:2920-2931, constants :1043-1044); YUV420, Rec709 (:6415-6419). For the 3856×2180 Clear HDR modes → 1280×720 (≈1.38 MB per buffer).
- UI preview: zero-copy. `publishPreviewFrame` (:7567-7712) sends dmabuf fds: at first sight of a request cookie it dup()s the plane fds into a registration descriptor (:7588-7659, `publishedPreviewSlots_`), afterwards each frame is a descriptor with fd numbers/offsets/pitches (:7664-7711). The app queues it latest-only (ApertarCoreApp.cpp:6986-6998) and `previewThread_` (`runPreviewPublisher` :11013) writes a JSON `preview_buffer`/`preview_frame` event, fds attached only on registration via `controlServer_.broadcastWithFds` (:10958-11010). Preview buffers are **not** mmapped by CameraController in cDNG modes (`mapPreviewBuffers` only in `processedYuvMode`, :6669-6676). Cost on the completion thread: tens of µs (est.).
- Web/MJPEG preview: only with a connected MJPEG client; the **downsample runs on the completion thread** (comment ApertarCoreApp.cpp:8119-8120), 1280×720 → ≤640×360 nearest-neighbour (`downsampleNearestPlane` :4024-4060) reading a `mmap(PROT_READ, MAP_SHARED)` of the preview dmabuf (:8082), ≤30 fps; JPEG on `mjpegThread_`. Cost 1-4 ms (est.; UNKNOWN whether libcamera's preview buffers come from a CPU-cached heap — Core only gives the raw/ProRes streams the `vidbuf_cached` heap, :6649-6665, :6736). Whether a web client was attached during the Open A/B takes is UNKNOWN from source; it is a variable to control on the Pi.

## 6. Plan: move the copy and the 12-bit mapping off the completion thread, Core-native (design statements PROBABLE unless marked)

Template: Core's own H.264 copy-worker (`PreviewJob` with pointer + `release` callback :4040-4048; `copyLoop` copies then `releasePreviewJob` :4963-4978; buffer count raised and in-flight limit following it :6796-6797, :1148-1158). Apply the same shape to `DngRecordingQueue`.

1. **Object that holds the libcamera request** (confirmed what exists; the design is probable): a new `CaptureJob` in `DngRecordingQueue` holding `libcamera::Request *request`, `libcamera::FrameBuffer *buffer`, `const uint8_t *source` (= `mapped.data + activeOffsetBytes`), `rawSize`, `int cachedFd` (−1 when `cachedRawBuffers_` is empty), `rawInfo` snapshot, `metadata`, `RawFrameView` geometry, `bool mapCodes12`, and a `std::function<void()> release` built by `CameraSession` exactly like the ProRes lambda (:7763-7766: sync END then `requeueRequest(request)`). `recordRawFrame` then stops at step 9d: it does `hasCapacityForFrame`, builds metadata, enqueues the `CaptureJob` and **returns true so `requestComplete` does not call `requeueRequest`** (the same early-return the processed path uses at :6999). The `Request` object itself lives in `requests_` (:6827) for the session's lifetime, so holding a raw pointer is safe until `CameraSession::stop`.
2. **Copy stage**: a dedicated copy thread inside `DngRecordingQueue` (not the DNG workers): pops `CaptureJob`, `syncCpuReadBuffer(fd, START)`, `acquireRawBuffer`, `memcpy`, `compressClearHdrFrame` when `mapCodes12`, `syncCpuReadBuffer(fd, END)`, **`release()` (→ `requeueRequest`) immediately**, then pushes the existing `FrameJob` to the DNG workers. Rationale (probable): copy+LUT is memory-bound (~8-16 ms), one thread at nice −5 suffices for 30 fps and preserves capture order (same reasoning as `h264CopyThreadCount` comment :4587); the DNG workers (nice 0, CPU-bound in lossless) would delay the requeue unpredictably. Keep `rawPool_`/`recycleRawBuffer` unchanged; raise `preferredRawPoolSize` to at least `maxQueuedFrames_` so the completion/copy thread never page-faults a fresh 16.9 MB block mid-take (§3) — or pre-fill the pool in `startAtFolder`.
3. **Requeue from the worker**: call `requeueRequest` directly from the copy thread (precedent: ProRes/H.264 lambdas :7763-7766, :7795-7797; `Camera::queueRequest` is thread-safe via `invokeMethod(ConnectionTypeQueued)` libcamera(qbc)/src/libcamera/camera.cpp:1376-1377). Requirements found in source: `requeueRequest` reads `settings_`, `sensorFamily_`, `camera_->controls()` (:6855-6870) — on the completion thread these are protected by the `sessionSettingsMutex_` shared lock (:6925), so the worker must take the same shared lock around `requeueRequest`; `controlsMutex_` (:6839) and `photoCaptureMutex_` (:6847) already serialise the control merge and the bracket state machine. Caveat (probable): the bracket logic assumes "Apply the slow shutter to one request only. The following request restores preview timing" (:6883-6884) — with requests requeued from two threads the order could interleave; with a single copy thread, and with the completion thread no longer requeueing raw requests, order is preserved. Do **not** drain releases from the completion thread: if all in-flight requests are held by workers, no completion arrives to drain them (deadlock).
4. **Buffer count**: in-flight requests R = `min(buffers, limit)`; with k requests held by the copy stage, libcamera/CFE keeps R − k. The CFE needs ≥ 2 queued (one being written, one armed) — probable; the rp1-cfe "has no buffer" diagnostic is the Pi-side check (apertar-kb/working/clearhdr-compare-answer.md:122). So R ≥ 3 + k. With k = 2 (copy ~8-16 ms per frame, a second slot absorbs a late requeue), R = 5-6: make `kActiveRequestCount` follow the configured count for raw (as :6796-6797 already does for processed formats) and set the Clear HDR raw/preview `bufferCount` to 6 (cached heap: 6 × 16.9 MB ≈ 101 MB + 6 × 1.4 MB preview; whether `/dev/dma_heap/vidbuf_cached` has that headroom on the 4 GB Pi is UNKNOWN — `allocateCachedBuffers` logs "count= frame_bytes=" or "cached DMA allocation unavailable" :6752-6758). Bound k explicitly: if the copy stage already holds k requests, drop the new frame (count it as "drop[copy-busy]") and requeue immediately on the completion thread, never hold a third.
5. **Keep the preview independent**: the preview and raw buffers travel in the same `Request`, so holding the request for the copy also holds the preview buffer; that is harmless to the UI preview (fd-passing, latest-only, no deadline). Keep `publishPreviewFrame` before `recordRawFrame` as now (:6984 vs :7000). Move the MJPEG downsample off the completion thread too: in `captureWebPreviewFrame` hand the slot pointer to `mjpegThread_` (it already owns the JPEG encode) or copy only when `mjpegClientCount_ > 0` on that thread — this removes the one remaining per-frame image pass from the camera thread. Also note (confirmed) `mapPreviewBuffers` is not needed for this.
6. **Stop ordering** (confirmed problem, probable fix): `CameraSession::stop` calls `camera_->stop()` before `recorder_.stop()` (:5759-5772); with requests held by the copy stage, drain/release them first (as `H264PreviewRecorder` does with `releasePreviewJob` for cancelled jobs :4831-4832, :4926-4927) or make `release` a no-op once `running_` is false (`requeueRequest` already checks `running_.load() && camera_` :6904).
7. **What to measure after each step** (tools exist in apertar-kb/working/tools per apertar-kb/working/handoff-mac-cinemate-compare.md:22 and diagnose.md:36):
   - Baseline + after step 2/3: `usample.py <pid> <CameraManager tid> 5` while recording 30 fps 16-bit and 12-bit — Core's symbols (`copyRawBytes`/`memcpy`, `compressClearHdrFrame`, `captureWebPreviewFrame`/`downsampleNearestPlane`) should fall to ~0 % on that tid; the tid should show only libcamera's two passes (≈14 ms/frame ≈ 42 % at 30 fps in 16-bit). `top -H` for the new copy thread (expect ≈ 25 % at 30 fps 16-bit, ≈ 50 % in 12-bit).

## Surprises
- `kActiveRequestCount = 3` is hard-wired for raw modes while buffers are 4; the "8 raw buffers" experiment could not have changed the in-flight count (:6796-6802).
- Core already contains the needed architecture (copy worker + release callback + buffer count following the pipeline) for H.264/ProRes; only the raw path copies on the completion thread.
- The raw pool is smaller than the queue (6-7 vs 12-24), so when the encoder falls behind the completion thread starts paying a fresh 16.9 MB allocation per frame — a feedback loop in exactly the Open B regime.
- The MJPEG web-preview downsample runs on libcamera's completion thread (by design, per comment) whenever a browser preview is open.
- Core's completion-thread nice −5 also boosts libcamera's own swap/stats passes, since they share the thread; DNG workers run at nice 0 (lossless) by default.
