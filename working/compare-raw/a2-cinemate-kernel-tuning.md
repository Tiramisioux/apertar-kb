## Q1. Per-device-class IO tuning (storage-automount.py) — CONFIRMED FROM SOURCE

### Where / when it is applied
- The service is a long-running root daemon (`User=root`, `Type=simple`, `Restart=always`, `Nice=-10`) started `After=local-fs.target` and `Before=cinemate-autostart.service` — cinemate/services/storage-automount/storage-automount.service:4-5,9-15,30@d6cc93e. It is a pyudev listener (`import pyudev`, `_udev_ctx = pyudev.Context()`) — storage-automount.py:33,96.
- Tuning is applied **at mount time, per device**, inside `_mount()` via `_apply_media_tuning(dev, kind, mount_path)` — storage-automount.py:466,480 (also after a successful repair, :496). `_mount` builds `["mount", "-t", fstype, "-o", opts, dev, mount_path]` — :470.
- `_apply_media_tuning` (storage-automount.py:364-380): docstring says per-device block-queue tuning is applied to every drive ("it only touches that device's own queue"), while "The *global* write-smoothing knobs — the VM dirty cushions and the NVMe power-latency parameter — are applied ONLY for the active RAW recording target (/media/RAW)" (:366-373). Code: `_apply_block_tuning(dev, kind)` always; `if mount_path == RAW_ACTIVE_PATH:` then `_apply_nvme_power_tuning(kind)` if dev starts with `/dev/nvme`, then `_apply_sysctl_cushions(kind)` (:376-379). `RAW_ACTIVE_PATH = MOUNT_BASE / RAW_LABEL` = /media/RAW (:50-52).
- Sysctls are **restored when no mounts remain**: `_apply_sysctl_cushions` saves the original six values on first call into `_sysctl_saved` (:321-325); `_restore_sysctls()` writes them back only when `_active_mount_kinds` is empty (:351-363), called from `_unmount` (:535). So the dirty-byte cushions are NOT boot-time defaults; they live only while a RAW drive is mounted.
- Sysctl writes go through `/proc/sys/<key with . -> />` (`_sysctl_set`, :187-188); block writes go to `/sys/block/<root>/queue/...` (:288).

### Values written (PROFILES dict, storage-automount.py:108-157)
Common to all classes when RAW is mounted (`_apply_sysctl_cushions`, :327-333):
- vm.dirty_ratio = 0 (:328); vm.dirty_background_ratio = 0 (:329)
- vm.dirty_writeback_centisecs = 150 ("1.5s flush") (:330)
- vm.dirty_expire_centisecs = 3000 ("30s max age") (:331)
- vm.dirty_background_bytes = profile dirty_bg_bytes (:332); vm.dirty_bytes = profile dirty_bytes (:333)

Per class:
| class | ext4 mount opts | dirty_bytes | dirty_bg_bytes | scheduler | nr_requests | rq_affinity | nvme_ps_latency_us | lines |
|---|---|---|---|---|---|---|---|---|
| cfe_nvme (CFexpress via PCIe, CFE HAT) | rw,noatime,nodiratime,commit=60 | 1 GiB | 256 MiB | none | 512 | 2 | 0 | :109-117 |
| usb_nvme (UAS bridge) | rw,noatime,nodiratime,commit=60 | 512 MiB | 256 MiB | none | 256 | 2 | 0 | :118-126 |
| usb_ssd (SATA via UAS) | rw,noatime,nodiratime,commit=60 | 256 MiB | 128 MiB | none | 256 | 2 | (none) | :127-139 |
| nvme_hat (M.2 via HAT) | rw,noatime,nodiratime,commit=60 | 1 GiB | 256 MiB | none | 512 | 2 | 0 | :140-148 |
| other (fallback) | rw,noatime | 256 MiB | 128 MiB | mq-deadline | 128 | 1 | (none) | :149-156 |

- usb_ssd comment (:129-133): "Smaller dirty cushion than NVMe on purpose: a USB SSD's write speed falls off a cliff once its SLC cache is exhausted (~90 s into a 4K take). A large dirty buffer would then fill and block writers in one long balance_dirty_pages stall — a burst of dropped frames. A smaller cushion trades that for shorter, more frequent stalls (smoother)." Matching runtime log at :338-341 ("if frames drop ~90 s in, the SSD cannot sustain the data rate").
- Block tuning writes (`_apply_block_tuning`, :285-307): `<queue>/scheduler` (:294), `<queue>/rq_affinity` (:299), `<queue>/nr_requests` (:304). Nothing else under /sys/block is written (no read_ahead_kb, no max_sectors_kb, no wbt_lat_usec).
- NVMe power: `_apply_nvme_power_tuning` writes `/sys/module/nvme_core/parameters/default_ps_max_latency_us` (fallback `/sys/module/nvme/...`) = "0" (:309-317); if not writable it only logs "add nvme_core.default_ps_max_latency_us=%s to cmdline.txt" (:317) — i.e. APST-off is best-effort and PROBABLY fails on a running kernel (module param is read-only after load; the comment itself anticipates this). Not confirmed on the Pi.
- Non-ext4 filesystems use FS_MOUNT_PROFILES (:161-166): ntfs/ntfs3/exfat/vfat all get `uid=,gid=,dmask=022,fmask=133,rw,noatime` (no commit=, no class dependence). Unknown fstype → "rw,noatime" (:349).

### How the class is detected (`_classify_media`, storage-automount.py:238-270)
- `/dev/nvme*` with a `usb` ancestor subsystem → `usb_nvme` (:246-250); any other `/dev/nvme*` → `nvme_hat` (:252-255), comment: "CFE HAT typically uses specific PCIe addresses; for now treat as nvme_hat ... CFE will be detected via I2C" — so in this function **`cfe_nvme` is never returned**; a PCIe NVMe (the Apertar/Cinemate NVMe HAT case) is classed `nvme_hat` (1 GiB / 256 MiB / none / 512).
- Non-NVMe with a `usb` ancestor: `ID_USB_DRIVER == "uas"` → `usb_nvme` ("Treat UAS as potentially NVMe-backed"), else `usb_ssd` (:258-264). Anything else → `other` (:266).
- Root block name: `nvme0n1p1 → nvme0n1`, `sda1 → sda` (`_root_block_name`, :197-202).


## Q2. Kernel command line (cinemate-install.sh `configure_cmdline`, :1246-1314) — CONFIRMED FROM SOURCE
- Target file `/boot/firmware/cmdline.txt` (:1247). Tokens are only added **when `nproc` == 4** (:1267-1268): `audio_core = ncores-1` = 3, `house = "0-2"` (:1269-1270), and the four tokens are
  `isolcpus=managed_irq,domain,3`, `nohz_full=3`, `rcu_nocbs=3`, `irqaffinity=0-2` (:1272-1275). Log line: "Audio-core isolation: reserving CPU 3 for capture (IRQs/housekeeping on 0-2)" (:1277).
- Stated reason (comment :1257-1265): "cinepi-audio-capture pins itself to the last core at SCHED_FIFO 80. CPU affinity alone does not stop kernel threads, the timer tick, RCU callbacks and device IRQs from sharing that core and jittering ALSA capture ... dedicate the last core (CPU 3) to audio and keep IRQs + housekeeping on CPUs 0-2. isolcpus / rcu_nocbs / irqaffinity take effect on stock kernels; nohz_full needs a NO_HZ_FULL (RT) kernel and is harmless otherwise." → the isolation is for **audio**, not camera.
- Also always adds `fsck.mode=skip` (:1280) and, with Plymouth, `quiet splash loglevel=1 plymouth.ignore-serial-consoles vt.global_cursor_default=0 logo.nologo` (:1253-1255); the `video=HDMI-A-N:<mode>` token (:1249-1250). The embedded python re-manages `isolcpus=`, `nohz_full=`, `rcu_nocbs=`, `irqaffinity=` only when re-adding them (:1298-1302).
- **Nothing for rp1-cfe / pispbe / camera IRQs specifically**: repo-wide grep for `smp_affinity`, `/proc/irq`, `irqbalance`, `CPUAffinity`, `IOSchedulingClass`, `.rules` files finds no IRQ pinning, no udev rules and no sysctl.d files anywhere in cinemate (only matches are the cmdline comment :1263/:1275/:1302, the cinepi_multi comment :736, and the storage-automount sysctl functions). The only kernel-side effect on camera IRQs is the implicit one: `irqaffinity=0-2` keeps **all** IRQs (including rp1-cfe/pispbe, which the Pi shows on CPU0) off CPU3; it does not spread them.
- No sysctl.conf/sysctl.d written by the installer (grep `sysctl` in cinemate-install.sh: no hits). No `udev` rules (grep: only `python3-pyudev` package, :601).
- config.txt: generated by `configure_boot_config` (:1074-1244). Relevant keys: `arm_boost=1` (:1191); optional **commented-out** `#dtoverlay=rp1-overclock` (:1196-1206: "Will Whang's RP1 SYS/PLL 300 MHz overclock (Pi 5 only) ... Left commented so stock clocks are the default"); `dtparam=pciex1` + `dtparam=pciex1_gen=3` only `if enable_pcie` (:1221-1226, "# CFE Hat PCIe 3.0"). The overlay itself is compiled/installed by `configure_rp1_overclock` (:734-748: "raises the imx585 ClearHDR frame-rate ceiling ... left commented out in config.txt ... companion libcamera pixel-rate cap is lifted in build_libcamera"). docs/overclocking.md:13 "The overclock ships installed but off". Note Apertar's Pi uses `dtoverlay=rp1-clk-333mhz` (given); Cinemate's overlay is named `rp1-overclock` (300 MHz per comment) — different overlay, PROBABLY different clock (300 vs 333 MHz); not verified beyond the comment.
- Kernel pin: `KERNEL_BASELINE_ABI_2712=6.12.93+rpt-rpi-2712` (:166) because older rp1-cfe "corrupts 16-bit CSI-2 capture (fixed mid-2025 by 'cfe: Avoid unpack operation for 16-bit formats' and the 16-bit hardware mismatch workaround)" (:161-165).
- Swap: `configure_boot_optimizations` disables `dphys-swapfile.service` (:1829-1833, loop :1842-1848) along with NetworkManager-wait-online, triggerhappy, ModemManager, systemd-rfkill, man-db/apt/e2scrub timers. Build-time zram swap is removed after build "so the running camera never swaps (swapping during a recording would drop frames)" (:688-690). docs/installation-steps.md:918 "Disable swap — not needed on Pi 4/5, and saves SD card writes".

## Q3. Process scheduling of the camera process — CONFIRMED FROM SOURCE
Launch prefix (cinemate/src/module/cinepi_multi.py `run()`, :294-313):
- `chrt -f 70` for the whole cinepi-raw process **if `_rt_permitted()`** (:297-300; comment "SCHED_FIFO 70 for the whole process (capture threads benefit most)"); `_rt_permitted` probes `chrt -f 70 /bin/true` (:105-114) — needs the RTPRIO limit. Otherwise warning "RT scheduling not permitted; running without chrt" (:302).
- `ionice -c2 -n0` (best-effort class, highest priority) if available (:304-306).
- `taskset -c 1-3` — "Keep the entire process off CPU0; allow 1–3 (GUI/OS left on 0)" (:308-310). NOTE: this conflicts in spirit with the audio-core invariant (CPU 3 is the SCHED_FIFO 80 audio core); the worker-level `--encode-affinity`/`--disk-affinity` then narrow DNG workers to 1-2, but the libcamera/camera threads of cinepi-raw are allowed on 1-3 by this taskset. Introduced in 2294d25 (2025-10-14, `git log -S chrt`/`-S taskset`).
- RT limit source: `cinemate-autostart.service` `LimitRTPRIO=80` (cinemate/services/cinemate-autostart/cinemate-autostart.service:27) — the docs and installer comments still say 30 (docs/installation-steps.md:611; cinemate-install.sh:1881). Installer also writes `/etc/security/limits.d/cinemate-audio.conf` with `@audio - rtprio 80` and `@audio - memlock unlimited` and adds the pi user to `audio` (:1876-1894), reason: "cinepi-audio-capture uses SCHED_FIFO to stay ahead of DNG-writer I/O" (:1878).
- storage-automount daemon itself runs `Nice=-10` (storage-automount.service:30).

Per-profile DNG worker arguments (cinemate/src/module/storage_profiles.py `RECORDER_PROFILES`, :50-95; emitted by `recorder_profile_args`, :156-171 as `--encode-workers`, `--disk-workers`, `--encode-affinity`, `--disk-affinity`, `--encode-nice`, `--disk-nice`):
| profile (by filesystem) | label | encode_workers | disk_workers | encode_affinity | disk_affinity | encode_nice | disk_nice | buffer_count | lines |
|---|---|---|---|---|---|---|---|---|---|
| default (none/unknown fs) | default-safe | 4 | 2 | 1-2 | 2 | -10 | -5 | 8 | :51-60 |
| ext4 | ext4-throughput | 4 | 8 | 1-2 | 1-2 | -10 | -5 | 8 | :61-73 |
| exfat | exfat-conservative | 4 | 2 | 1-2 | 2 | -10 | -5 | 10 | :74-83 |
| ntfs | ntfs-conservative | 4 | 2 | 1-2 | 2 | -10 | -5 | 10 | :84-94 |
- Profile selection is **by filesystem, not by device class**: `recorder_profile_name_for_filesystem` (:138-142). So an NVMe formatted ext4 gets `ext4-throughput` (8 disk workers on cores 1-2); an exFAT NVMe gets `exfat-conservative`. The device-class profiles (nvme_hat etc.) live only in storage-automount (Q1). cinepi_multi reads the fs from Redis and logs "Storage recorder profile: filesystem=%s profile=%s" (cinepi_multi.py:814-833), then `args += recorder_profile_args(storage_fs, is_pi4=self._is_pi4())` (:834).
- Pi 4 caps disk workers at `PI4_MAX_DISK_WORKERS = 4` (:149-163) because xHCI is shared with the USB mic; "Pi 5 routes NVMe over PCIe — a separate bus from USB — so it keeps the full worker count" (:151-152).
- AUDIO-CORE INVARIANT comment (:41-49): audio capture pins to core N-1 at SCHED_FIFO 80; "No profile's encode_affinity or disk_affinity may include that core"; "worker affinity must stay within 0-2 (practically 1-2, leaving core 0 for the camera pipeline and IRQs)"; ext4/ntfs disk_affinity "Was '2-3'" (:66-69, :89). cinepi_multi.py:728-738 comment: profile is "the single source of --encode-affinity / --disk-affinity ... cinepi-raw also strips the audio core as a backstop, and the installer's boot-time isolcpus/nohz_full/rcu_nocbs/irqaffinity complete the isolation."

## Q4. --buffer-count — CONFIRMED FROM SOURCE
- Default per profile: 8 (default, ext4), 10 (exfat, ntfs) — storage_profiles.py:59,72,82,93. Fallback if the key is missing/invalid: 8 (cinepi_multi.py:845-847).
- Override key: `sensors.raw_buffer_count` in settings.jsonc (cinemate/settings.jsonc:80, default `0` = no override); read at cinepi_multi.py:849-853 (`_settings().get("sensors").get("raw_buffer_count")`, applied only if > 0). The comments/log call it "camera.raw_buffer_count" (:841, :856) — the actual key path is `sensors.raw_buffer_count`.
- Emitted as `args += ["--buffer-count", str(buffer_count)]` (cinepi_multi.py:866) with log "Camera raw-buffer headroom: --buffer-count %d (profile %s)" (:861).
- Comment on libcamera base and memory (storage_profiles.py:32-39): "libcamera's base for the video+raw path is 6. More buffers absorb transient disk-write latency spikes that would otherwise starve the sensor and drop a frame. Slower / spikier filesystems (exFAT, NTFS) get more headroom than ext4, which has flatter write latency. Each extra buffer costs ~25 MB of CMA at 4K (raw + video streams share the count) ... confirm CMA headroom with `grep Cma /proc/meminfo`." cinepi_multi.py:836-844 repeats it: a starved sensor drops "a single frame (visible as a one-tick hole in the DNG timecode)"; "too high exhausts CMA and the camera fails to start".
- History: 31126f2 2026-05-31 "Add camera raw-buffer headroom to reduce transient frame drops"; a61a589 2026-06-01 "Make raw-buffer headroom per storage profile" (`git log -S buffer-count`).

## How cinepi-raw consumes what Cinemate emits — CONFIRMED FROM SOURCE (cinepi-raw @ 63a08d5)
- `--buffer-count` is an rpicam-apps option, default 0 (`cinepi-raw/core/options.hpp:199@63a08d5`). In the video configuration the raw/video stream gets `cfg.bufferCount = 6; // 6 buffers is better than 4` then `options_->buffer_count` if > 0 (`cinepi-raw/core/rpicam_app.cpp:630-632@63a08d5`); raw stream count follows stream 0 (:657). So "libcamera's base of 6" is really rpicam-apps' hard-coded 6, overridden to 8 (ext4) / 10 (exFAT, NTFS) by Cinemate. Apertar Core uses 4 raw + 4 preview (given).
- `--encode-affinity/--disk-affinity/--encode-nice/--disk-nice` parsed at `cinepi-raw/cinepi/cinepi_options.cpp:212-221,500-540@63a08d5` into RawOptions (raw_options.hpp:61-64); copied into DngEncoder (dng_encoder.cpp:294-297) and applied per worker thread by `configureThreadContext` for "dng-enc-" (:2015) and "dng-dsk-" (:2316): it strips the audio core (`audio_core = online_cpus-1` when >2 CPUs, :386; comment :380-383 "so a storage recorder profile can never place workers on it (a stale ext4 "2-3" on a 4-core Pi would)"), round-robins one CPU per worker (:398-403), `pthread_setaffinity_np` (:411), `setpriority(PRIO_PROCESS, 0, nice)` (:432).
- Audio helper: `tryElevateRealtimePriority` sets SCHED_FIFO 80 (`CINEPI_AUDIO_RT_PRIORITY` override) and pins to the last CPU (`cinepi-raw/cinepi/cinepi_audio_capture.cpp:245-289@63a08d5`); comment :236-242: "On Pi 4/5 the NVMe SSD and USB mic share the same xHCI USB controller; a 4K DNG burst causes USB interrupt latency that stalls ALSA reads even with SCHED_FIFO if the capture thread is competing for CPU time with DNG workers."

## Synthesis for the Apertar comparison
What Cinemate's image does that Apertar's Pi (as described in the givens) does not:
1. **At RAW mount, for an NVMe HAT (the class a plain PCIe NVMe lands in):** vm.dirty_bytes=1 GiB, vm.dirty_background_bytes=256 MiB, dirty_ratio=0, dirty_background_ratio=0, dirty_writeback_centisecs=150, dirty_expire_centisecs=3000; `/sys/block/nvme0n1/queue/scheduler=none`, `rq_affinity=2`, `nr_requests=512`; ext4 mounted `rw,noatime,nodiratime,commit=60`; nvme APST latency 0 attempted. Writes are fire-and-forget (`_write` result ignored, storage-automount.py:291-304). Restored when the last drive is unmounted.
   - PROBABLE relevance to Open A: Apertar's dd-through-page-cache repro and buffered DNG writes run under stock dirty limits (ratio-based, i.e. ~20 %/10 % of RAM on a 4 GB Pi ≈ 800/400 MB PROBABLE, not read from the Pi). Cinemate starts background writeback earlier (256 MiB) and caps dirty at 1 GiB, flushing every 1.5 s, which smooths the writeback bursts that balance_dirty_pages would otherwise impose; `rq_affinity=2` completes block IO on the submitting CPU (the disk worker's core 1-2), keeping completion work off CPU0 where rp1-cfe/pispbe IRQs live. Neither effect is measured here; they are the mechanisms Cinemate's comments claim.
2. **Kernel cmdline:** `isolcpus=managed_irq,domain,3 nohz_full=3 rcu_nocbs=3 irqaffinity=0-2` — for the audio core only; nothing targets camera IRQs. The side effect is that all device IRQs stay on 0-2 (they are on CPU0 on Apertar's Pi anyway).
3. **Process scheduling:** cinepi-raw runs `chrt -f 70` (whole process SCHED_FIFO 70), `ionice -c2 -n0`, `taskset -c 1-3`; DNG encode workers (4) nice -10 on cores 1-2, disk workers (8 on ext4) nice -5 on cores 1-2; audio helper SCHED_FIFO 80 on core 3. Apertar Core's scheduling is a different reader's question (UNKNOWN here).
4. **Buffers:** `--buffer-count 8` on ext4 (10 on exFAT/NTFS), vs rpicam-apps base 6 and Core's 4 raw + 4 preview. (Given: 8 raw buffers changed nothing for Open A.)
5. **No** udev rules, sysctl.d, irqbalance, IRQ pinning for rp1-cfe/pispbe, or config.txt memory/CMA tuning. `arm_boost=1` is set; `rp1-overclock` (RP1_PLL_SYS and RP1_CLK_SYS to 300 MHz, cinemate-install.sh:767-777) is installed but commented out.
